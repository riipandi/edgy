# Observability gaps — signals the eight dashboards cannot answer

Source: the dashboard set provisioned from `container/clickstack/dashboards` (eight files, `Application Overview`, `Application SLI`, `Application Errors`, `Application Traces`, `Redis Database`, `ClickHouse Database`, `Pipeline Collector`, `Node.js Runtime Metrics`). Every claim below was re-checked against the tree and the running stack on 2026-10-23; a dashboard that reads a metric this file says is missing is a contradiction, so the metric name is given where it exists.

## O1 — no container or host resource metrics

- status: resolved (2026-10-24, plan-20261024_0105 phase 6, commit 6a908825b)
  evidence: the compose stack runs seven services with the app among them (mem_limit 256m, port published on 127.0.0.1); the collector scrapes cAdvisor through a dedicated metrics/cadvisor pipeline; ClickHouse holds the three container series with the compose service label — working set 112 MiB against the 256 MiB spec limit, throttled seconds, restarts (verified live); the Node.js Runtime Metrics dashboard carries the three tiles; cAdvisor survived a compose restart and kept exporting.
  plan: plan-20261024_0105
  trigger: the first deployment where the process runs inside a container with a memory limit, or the first OOM kill.

## O2 — request metrics cannot separate 429 from other 4xx, or one route from another

- status: resolved (2026-10-24, plan-20261024_0105 phase 1, commit 5ac5cba71)
  evidence: `http_requests` is labelled `{method, status_code, route}` — exact code, route template derived from the HttpApi contract and bounded by the route table — and `http_request_duration_seconds` carries `{method, route}`; the class label and `statusClass` were removed; five SLI queries and the `429 rate (%)` tile were rewritten to the new shape and a `Mean latency by status code (ms)` tile was added; verified live in ClickHouse.
  plan: plan-20261024_0105
  trigger: the first rate-limit incident, or the first time per-route latency is needed and traces alone are too coarse.

## O3 — `/api/health` is readiness only; there is no liveness endpoint

- status: resolved (2026-10-24, plan-20261024_0105 phase 2, commit 71217ffe4)
  evidence: `GET /api/live` lives in the `HealthApi` group, answers `200 {status:'ok'}` with no `Database` in the handler; `/api/health` keeps its readiness meaning and fails closed on `DatabaseError`; two unit tests pin both; the Health probe tile reads `SpanAttributes['http.route']` (span names are method-only) and shows both probes; probed 200 on a freshly built standalone binary.
  plan: plan-20261024_0105
  trigger: the first deployment behind a supervisor that restarts on a failed probe.

## O4 — dependency calls are neither traced nor timed

- status: resolved (2026-10-24, plan-20261024_0105 phase 3, commit 76d8a1c20)
  evidence: `dependency_duration_seconds {store, op}` with stores `{sqlite, postgres, redis}` and six fixed ops; spans and metrics on the database adapter (query/read/ping), the cache (get/bypass/invalidate with `cache.status`), and the limiter (consume with `limiter.verdict`; the database-backed consume span carries no metric — the adapter already times its own SQLite traffic); four test files pin the spans and histogram via a recorder tracer; the series is visible in ClickHouse.
  plan: plan-20261024_0105
  trigger: the first latency incident where traces end at the handler and the cause sits one layer down.

## O5 — telemetry loss has no expected-versus-received signal, and nothing alerts

- status: resolved (2026-10-24, plan-20261024_0105 phase 5, commit e56218c22)
  evidence: the `Telemetry freshness` tile renders fresh (≤2 min) / stale / silent (>10 min) per signal table and was verified live in both directions (fresh at 4 s during a live pump, silent at ~14 min); two alerts ship in `container/clickstack/alerts` — no spans for two consecutive 5m windows (the v2 interval enum has no 10m; absence is `thresholdType: below` at 1) and collector refused/failed above zero per 5m; the provisioner applies them behind `CLICKSTACK_ALERT_WEBHOOK_URL` (verified: gate-off logs the skip, gate-on creates the webhook channel and both alerts against the live v2 API) and the probe objects were deleted afterwards.
  plan: plan-20261024_0105
  trigger: the first incident where a dashboard looked healthy because telemetry had stopped.

## O6 — no capacity projection: growth is measured, disk-full is not predicted

- status: resolved (2026-10-24, plan-20261024_0105 phase 4, commit cfd737472)
  evidence: the `Days of headroom` tile in `ClickHouse Database` divides `system.disks.free_space` by the `system.query_log.written_bytes` rate over a 7-day window (read-only SQL, verified live — it returns a real days figure); the provisioner round-trip applied the dashboard. When the figure drops below the retention window, O7's trigger fires.
  plan: plan-20261024_0105
  trigger: the first environment with a sustained ingest rate, or disk used above 70%.

## O7 — the retention window is fixed and not configurable

- status: resolved (2026-10-24, commit `feat(clickstack): apply the retention window from CLICKSTACK_RETENTION_DAYS`)
  area: observability/infra
  summary: The 30-day TTL was created with the tables by the HyperDX image and was not read from any environment variable. Changing it means either recreating the tables or issuing `ALTER TABLE ... MODIFY TTL`, which the provisioner could do at start the same way it reconciles connections and sources.
  evidence: `CLICKSTACK_RETENTION_DAYS` (default 30, from compose) is reconciled by `provision.sh` through the ClickHouse HTTP interface — each `otel_*`/`hyperdx_*` table's TTL is rewritten only when it differs from the configured value; verified live: 14d applied to all 10 TTL-carrying tables, a second run at the same value skips, and the compose default (30) healed the tables back. When the configured window drops toward what the Days of headroom tile projects, the disk — not the retention — is the next thing to revisit.
  note: how long telemetry is kept remains the owner's policy call; the variable only makes the policy expressible.

## Settled records

- The eight dashboards themselves are not a finding: all eight provision cleanly, every tile renders, and a Playwright pass over each dashboard recorded zero failed ClickHouse requests and zero "Error loading chart" tiles on 2026-10-23, including against an empty stack.
- `v8js.memory.heap.limit` reporting `heapTotal` instead of `heap_size_limit` was found and fixed in the same pass (`src/observer/runtime-metrics.ts`), with a test that asserts the value equals `getHeapStatistics().heap_size_limit`.
