# Fix behaviour logging — one access-log owner, dev parity, a suppressor that holds

Source evidence: `.llms/audit/audit-20261027_2042.md` (findings F1–F8). This plan settles the
audit; nothing in it touches a wire contract or a database surface.

## Objective

The owner reported the behaviour logging (request-log middleware + observer sinks) as inconsistent
between dev and production, with a poorly working suppressor. After this plan: one access-log line
per request in every environment, owned by `request-log`; quiet paths silent on success and loud on
failure; dev page requests logged through the same rules; the stdout sink degrades instead of
defecting. The plan does not change any HTTP contract, metric label set, or route.

## Current state (verified in the tree, 2026-10-27)

- **The middleware and its quiet list** — `src/middleware/request-log.ts:41-70` wraps the inner
  handler with `Effect.exit`, records metrics, and logs one line per non-quiet request; quiet paths
  return the inner effect untouched (`request-log.ts:52`).
- **The stack is defined once** — `src/kernel/http/stack.ts:20-29` merges all middlewares; serve
  (`src/kernel/http/server.ts:15-33`) and the dev handler (`src/kernel/http/api.ts:70-83`) both
  compose through it.
- **The framework logger is always installed** — `HttpRouter.serve` (`server.ts:27`) and
  `HttpRouter.toWebHandler` (`api.ts:70`) receive no `disableLogger` option, so
  `HttpMiddleware.logger` duplicates every request (audit F4) and leaks causes on failures (F3, F5).
- **The dev handler builds a second LoggerLayer** — `api.ts:70-83` merges
  `LoggerLayer.pipe(Layer.provide(Layer.succeedContext(context)))` around `toWebHandler`; in the
  vite dev process the request fibers' log emissions are lost (audit F1) while the same composition
  works in a plain node process and `applicationRuntime.runPromise` logging works in the dev
  process itself.
- **Dev pages bypass the Effect stack** — Start's dev middleware renders pages inside Vite
  (`src/builder/vite-plugin.ts:148-166` forwards only `/api/*`, `/api-docs`, `/metrics`), so
  request-log sees no page traffic in dev (F2).
- **The stdout sink is unguarded** — `src/observer/logger.ts:75-84` writes with a raw
  `process.stdout.write(chunk, cb)` inside `withinBudget`; a patched stdout defects the flush (F6).
- **Failure metrics are unclassified** — `request-log.ts:54-62` records `500` for every failure
  including interrupts (F7).
- **Existing coverage** — `tests/middleware/request-log.test.ts` already asserts metrics labels,
  defect WARN, quiet suppression, and custom quiet paths; `src/observer/logger*.test.ts` and
  `log-*.test.ts` cover the sinks; `tests/kernel/http.test.ts` boots the real serve layer.

## Decisions

- **D1 (2026-10-27, owner): dev page requests are logged from the Start-side middleware.** A
  request middleware in `src/start.ts` records page/asset access through `applicationRuntime` with
  the same format and quiet rules; the dev render architecture (Start renders pages inside Vite)
  stays untouched. The cost the pick carries: one extra middleware hop in dev and a shared
  access-record core that both stacks must call, or the two surfaces drift again.
  Rejected: accepting dev = API-only logging — leaves the reported inconsistency in place.
  Rejected: forwarding page requests through the Effect stack in dev — replaces the dev render
  architecture the tree deliberately chose.
- **D2 (2026-10-27, owner): the framework's built-in response record is disabled; request-log
  becomes the single access-log owner.** `HttpRouter.serve(..., { disableLogger: true })` and the
  dev `toWebHandler(..., { disableLogger: true })`; the failure branch of request-log carries the
  cause itself. The cost: the automatic `Sent HTTP response` record disappears everywhere, so any
  future surface that relied on it must log through request-log or its own logger.
  Rejected: keeping the framework record and fixing its rendering — keeps two records per request
  and two log shapes to maintain.
  Rejected: keeping only the framework record — loses the data-first line format and the
  `requestId` annotation the contract names.
- **D3 (2026-10-27, owner): quiet paths stay silent on success and loud on failure.** A quiet-path
  failure logs WARN with the status and records metrics; a quiet-path success emits nothing and
  records nothing (today's behavior preserved for the success case). The cost: a flapping probe on
  a quiet path now produces WARN lines by design.
  Rejected: fully silent quiet paths — a failing request is signal regardless of its path.
- **D4 (2026-10-27, owner): the remaining audit findings are in scope.** Interrupt/abort no longer
  records a `500` metric or an error line; `makeBatchedStdout` degrades to a stderr fallback on
  write failure; `requestId` consistency follows automatically from the single-owner rule (the
  annotation mechanism in `src/middleware/request-id.ts:31` already scopes it).
- **D5 (2026-10-27): no backward compatibility or legacy shims.** The owner declared the project
  early-stage; the plan replaces behavior outright rather than gating it behind flags.

- **D6 (2026-10-27, owner): the `/.well-known/` quiet entry stays devtools-probe-only.** The
  middleware's comment and `rules.md` claimed a deliberately broad `/.well-known/` prefix, but the
  list never carried it and the pre-existing quiet test failed against HEAD for
  `/.well-known/jwks.json`. The owner picked: only
  `/.well-known/appspecific/com.chrome.devtools.json` is quiet; jwks.json and the other discovery
  documents are ordinary requests and stay logged. The cost: the rules contract and the file
  comment must say the narrower truth (phase 4 syncs both).
