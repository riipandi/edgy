# Observability gaps — signals the eight dashboards cannot answer

Source: the dashboard set provisioned from `container/clickstack/dashboards` (eight files, `Application Overview`, `Application SLI`, `Application Errors`, `Application Traces`, `Redis Database`, `ClickHouse Database`, `Pipeline Collector`, `Node.js Runtime Metrics`). Every claim below was re-checked against the tree and the running stack on 2026-10-23; a dashboard that reads a metric this file says is missing is a contradiction, so the metric name is given where it exists.

## O1 — no container or host resource metrics

- status: open
  area: observability/infra
  summary: Nothing in the stack reports CPU, memory, or disk for the process that serves Edgy. `compose.yaml` defines five services — `clickstack`, `clickstack-init`, `mailpit`, `redis`, `redis-exporter` — and the application is not one of them, so there is no container to scrape and no cAdvisor or node-exporter to scrape it with. `src/observer/runtime-metrics.ts` covers the Node process from the inside (`process.cpu.utilization`, `process.memory.rss`), which cannot see a container memory limit, an OOM kill, or a restart count. `Node.js Runtime Metrics` therefore shows pressure but not the wall it hits.
  recommendation: run the application as a compose service with a memory limit, then scrape cAdvisor (or `node_exporter` for a host-run process) through the collector's Prometheus receiver. The three signals worth the scrape: `container_memory_working_set_bytes` against the limit, `container_cpu_cfs_throttled_seconds_total`, and `kube_pod_container_status_restarts_total`-equivalent — for compose, a restart counter exported by the orchestrator or a `process.uptime` drop detected in the dashboard. A cheaper first move, if running the app in compose is unwanted, is a `process.uptime` reset tile: a drop between samples is a restart, which today is invisible.
  plan: none yet
  trigger: the first deployment where the process runs inside a container with a memory limit, or the first OOM kill.

## O2 — request metrics cannot separate 429 from other 4xx, or one route from another

- status: open
  area: backend/observer
  summary: `src/observer/metrics.ts:35-42` labels `http_requests` with `{ method, status }` where `status` is the class from `statusClass` (`2xx`, `4xx`, ...) and labels `http_request_duration_seconds` with `{ method }` only. The bounded label set was deliberate — the comment at lines 33-34 says so — but the consequence is that the `Application SLI` tile is named `4xx rate (%)` rather than `429 rate`, and latency cannot be split between successful and failed requests. Rate limiting answers `429` (`src/middleware/rate-limit.ts`), and a limiter that fires on legitimate traffic is indistinguishable from a client sending malformed requests.
  recommendation: add a `route` label carrying the matched route template (for example `/api/users/:id`), not the raw path, so cardinality stays bounded by the route table rather than by traffic; add `status` as the exact code for `http_requests` only if the route label alone proves too coarse. Both changes are additive — existing series keep their meaning, and a dashboard that groups by `Attributes['status']` reads `4xx` until it is updated to read the code. Then rename the SLI tiles to `429 rate (%)` and split `Mean latency` by status class.
  plan: none yet
  trigger: the first rate-limit incident, or the first time per-route latency is needed and traces alone are too coarse.

## O3 — `/api/health` is readiness only; there is no liveness endpoint

- status: open
  area: backend/health
  summary: `src/modules/health/module.ts:9-14` registers a single `GET /health` that pings the database and answers `503` on `DatabaseError` (lines 18-22). That is a readiness probe: it correctly reports "cannot serve yet", but it also fails during a database outage while the process itself is healthy, so a supervisor pointed at it restarts a working process. There is no `/live` or `/health/live` — `grep` over `src/modules/health` and `src/kernel/http` finds no liveness surface. `Application SLI` has a `Health probe` tile that reads spans matching `%health%`, `%readiness%`, `%liveness%`; today only the first pattern can ever match.
  recommendation: add `GET /live` to the same `HealthApi` group, answering `{ status: 'ok' }` with no database access, and document the split: liveness for the supervisor, readiness for the load balancer. Keep `/health` as readiness so existing probes keep their meaning. The `Health probe` tile then shows both, and the difference between "process alive" and "process able to serve" becomes visible during an incident.
  plan: none yet
  trigger: the first deployment behind a supervisor that restarts on a failed probe.

## O4 — dependency calls are neither traced nor timed

- status: open
  area: backend/database, backend/cache
  summary: A slow SQLite query or a stalled Redis round trip shows up only as elevated request latency, with nothing attributing it. `src/database/adapter.ts`, `src/kernel/cache.ts`, and `src/middleware/rate-limit.ts` carry no span and no metric — `grep` for `withSpan`/`tracer` in those files finds nothing, and the metrics they touch are the HTTP counters only. `Redis Database` watches the Redis server itself (`redis_commands_processed_total`, memory, evictions) and `Pipeline Collector` watches the collector, but neither answers "did Redis make this request slow". This matters more because Redis is optional: `REDIS_ENABLE` defaults to false (`src/kernel/config/redis.ts:28-32`), so the dependency's effect on the application depends on configuration that no dashboard reflects.
  recommendation: wrap each database call and each cache/limiter call in a span with a small, fixed attribute set (operation name, store, hit/miss) and export a histogram of dependency duration labelled by store. That gives two things the current set lacks: a per-dependency latency series for a dashboard tile, and a trace that shows the slow segment inside a request instead of at its end. Keep the attribute set bounded — a table name is fine, a key or a query string is not.
  plan: none yet
  trigger: the first latency incident where traces end at the handler and the cause sits one layer down.

## O5 — telemetry loss has no expected-versus-received signal, and nothing alerts

- status: open
  area: observability/pipeline
  summary: `Pipeline Collector` shows accepted, refused, and exported counts and a queue percentage, but all of them are the collector's own view. If the collector stops exporting, or the application stops sending, every tile trends to zero and the dashboard reads "quiet" rather than "broken". The `Silent signal check` tile in `Application SLI` covers `http_requests` and `http_request_duration_seconds` only, and it reports a timestamp rather than a verdict. Separately, `container/clickstack/provision.sh` provisions connections, sources, and dashboards and never touches alerts, although `GET /api/v2/alerts` answers `200` on the running stack — the surface exists and is unused.
  recommendation: add a `Telemetry freshness` tile that compares the newest row per signal table against the dashboard's own clock and renders a verdict (fresh, stale, silent) instead of a raw timestamp; then provision two alerts through the v2 API from a JSON file beside the dashboards, the same way dashboards are provisioned: no spans received for N minutes, and collector refused-or-failed above zero over a window. The alert channel needs a decision (webhook target), which is why this is filed as work with an open question rather than a tile-only change.
  plan: none yet
  trigger: the first incident where a dashboard looked healthy because telemetry had stopped.

## O6 — no capacity projection: growth is measured, disk-full is not predicted

- status: open
  area: observability/infra
  summary: `ClickHouse Database` shows current size, rows written per minute, and disk free (measured 2026-10-23: 97.1 GB free of 460.4 GB), but nothing divides one by the other. The dashboard can say the disk is 79% full today; it cannot say when it will be full. Retention is fixed at 30 days per table (verified through `system.tables`: `toDateTime(Timestamp) + toIntervalDay(30)` on `otel_logs` and the metric tables, `toDate(Timestamp) + toIntervalDay(30)` on `otel_traces`), so growth is bounded in principle — but the bound depends on ingest rate, which varies.
  recommendation: add a projection tile computing bytes written per day over the selected range and dividing free space by it, rendered as "days of headroom". It is a read-only SQL tile against `system.query_log` and `system.disks`, no new component. When the number drops below the retention window, the retention setting — not the disk — is what needs attention, which is the next item.
  plan: none yet
  trigger: the first environment with a sustained ingest rate, or disk used above 70%.

## O7 — the retention window is fixed and not configurable

- status: considering (trigger: a deployment that needs a retention window other than 30 days)
  area: observability/infra
  summary: The 30-day TTL is created with the tables by the HyperDX image and is not read from any environment variable — `compose.yaml` and `.env.example` carry no retention key. Changing it means either recreating the tables or issuing `ALTER TABLE ... MODIFY TTL`, which the provisioner could do at start the same way it reconciles connections and sources. Parked because the right shape is a decision, not an implementation detail: a `CLICKSTACK_RETENTION_DAYS` value applied by `provision.sh` is the obvious option; the alternative is to leave the schema alone and treat the retention as an image concern, which keeps the provisioner from owning DDL.
  trigger: a deployment that needs a retention window other than 30 days, or a capacity projection (O6) that crosses the window.
  note: the decision is also a policy question — how long telemetry is kept is the owner's call, not a default to be invented.

## Settled records

- The eight dashboards themselves are not a finding: all eight provision cleanly, every tile renders, and a Playwright pass over each dashboard recorded zero failed ClickHouse requests and zero "Error loading chart" tiles on 2026-10-23, including against an empty stack.
- `v8js.memory.heap.limit` reporting `heapTotal` instead of `heap_size_limit` was found and fixed in the same pass (`src/observer/runtime-metrics.ts`), with a test that asserts the value equals `getHeapStatistics().heap_size_limit`.
