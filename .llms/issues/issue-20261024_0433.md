## L1 — the rate-limit middleware 503s the liveness probe when its store is unreadable

- status: open
  area: backend/security, backend/health
  summary: With the default database-backed limiter store, a database that cannot serve the
  `rate_limits` table makes the rate-limit middleware answer `503 Service Unavailable` (plain text,
  `src/middleware/rate-limit.ts:200`) for **every** API route — `/api/live` included. Verified on a
  freshly built standalone binary (2026-10-24): with the store unwritable, `/api/live` answers 503;
  with `RATE_LIMIT_ENABLED=false` the same instance answers 200 — the middleware is the source.
  This breaks the probe-split contract in `.llms/rules.md` ("`/api/live` … stays green during a
  database outage") precisely in the outage case, and a supervisor pointed at liveness would
  restart a working process. The unit tests pass because no fixture exercises the limiter's
  fail-closed path against the liveness route. Note the middleware's own comment says it is
  route-scoped, so an exclusion point already exists.
  recommendation: exclude the probe routes from the rate-limit middleware scope — liveness at
  minimum; readiness may keep its 503 semantics either way (its handler already answers 503 on a
  database failure). Alternatively fail the limiter open for probe routes only. Either way a test
  must pin the composition behavior, not just the handler.
  plan: none yet
  trigger: the first supervisor deployment pointing liveness at `/api/live` while the limiter store
  is database-backed (the default).

## L2 — the compose section in `.env.example` makes `generate:config --check` permanently red

- status: open
  area: kernel/config, compose
  summary: Phase 5 of plan-20261024_0105 hand-added a "ClickStack alerting (compose stack)"
  section to `.env.example`, but the generator owns the whole file: `writeGenerated` compares full
  content (`src/command/generate-config.ts`), so `vpr app generate:config --check` fails with "out
  of date" for every future run, and running the generator to fix it would delete the compose
  section. Verified 2026-10-24.
  recommendation: pick one ownership rule — (a) regenerate `.env.example` as pure app config and
  keep the compose variables documented in `docs/configuration.md` only (the compose defaults
  already live in `compose.yaml`); (b) teach the generator to preserve a marker-delimited
  hand-maintained region; or (c) move the stack variables to a separate compose env file passed
  with `--env-file`.
  plan: none yet
  trigger: every `generate:config --check` run until resolved.
