# Findings of the full audit (security, concurrency, performance, cleanup)

Three read-only reviews, each finding re-checked or proven with a throwaway script. Each item carries its status; what was fixed after the audit says how. Plans touched: none.

## 1. Unbounded list and a public user directory

- **status**: resolved (unbounded read); the exposure of emails stays with authentication, item 2 of `issue-20261015_2230.md`
- **what**: `GET /api/users?limit=-1` returned every row without credentials (180 KB for 2 000 rows; on 1 M rows 1.5 s and +439 MB heap).
- **resolution**: `paginationQuery(sortable, { allowAll })` refuses `-1` unless the resource opts in; `/api/users` does not (`400 VALIDATION_FAILED`). Tests in `pagination.test.ts` and `api.test.ts`.

## 2. Client address behind an appending proxy

- **status**: resolved
- **what**: with `TRUST_PROXY=true` the limiter keyed on the leftmost `X-Forwarded-For` entry, which a client controls; and `CF-Connecting-IP` was trusted on Node too, where the client writes it.
- **resolution**: `TRUST_PROXY` is now `false`, `true` or a list of addresses and CIDR ranges, `X-Forwarded-For` is read from the right skipping trusted proxies, and `TRUSTED_PLATFORM` names the header a platform sets (`CF-Connecting-IP`), read directly. The first attempt (`TRUST_PROXY_HOPS`) was replaced by this model. Tests: `ip.test.ts`, `client_ip.test.ts`, and the spoof in `rate_limit.test.ts`. `PROXY_PROTOCOL` and `CLOUDFLARE_LOCATION_HEADERS` followed (item 14).

## 3. Email enumeration on `POST /api/users`

- **status**: considering
- **what**: a duplicate email answers `409`, a new one `201`. A product decision (generic answer plus verification, or accept it and rate-limit harder); no recommendation was possible without a rule for who may create users.
- **trigger**: when users become real people.

## 4. No index for `sort_by=name`

- **status**: resolved
- **resolution**: `users_name_id_idx` on `(name, id)` in the initial migration (`EXPLAIN`: a 1.4 s deep page of a million rows becomes a few milliseconds). `user_query_plan.test.ts` fails if the plan goes back to a temp B-tree. Existing databases need `migrate:reset --up --seed`.

## 5. A write racing a cache fill repopulates stale data

- **status**: resolved (in a process); across instances the staleness is bounded by `CACHE_TTL` and `CACHE_LOCAL_TTL`
- **resolution**: `makeReadThrough` bumps an epoch on every `invalidate`; a read that was in flight across one drops what it stored. The shared-store test failed before the change. A write handled by *another* instance still cannot invalidate this one's in-flight read; versioned keys would close it.

## 6. A cancelled request's work still ran on the SQLite connection

- **status**: resolved for queries
- **resolution**: Kysely already serialises a single-connection adapter, so the fork's own mutex never had a waiter and was removed; `DatabaseService.query` now goes through `db.connection().execute(run, { signal })`, so a query still queued when its request is cancelled never runs. `cancellation.test.ts`. A `transaction` callback cannot be cancelled this way (see item 12).

## 7. Two processes migrating one SQLite file, and non-atomic migrations

- **status**: resolved
- **resolution**: `NodeSQLiteAdapter` reports transactional DDL, and the driver opens every transaction with `BEGIN IMMEDIATE`, which is what makes a second process wait (Kysely's own lock is taken outside the transaction and is not held; the first version of this fix relied on it and still failed about half of the runs). A migration that fails halfway leaves nothing; two `migrate:up` processes at once both succeed (it failed every time before). `migration_race.test.ts` spawns the processes. Not covered: D1 (item 4 of `issue-20261015_2230.md`).

## 8. Log pipeline: unbounded buffer, stalled sink, shutdown

- **status**: resolved
- **resolution**: each sink write has a 5 s budget (`observer/flush.ts`), so a stuck pipe or disk can neither grow the buffer for long nor hang shutdown; the stdout flush waits for the write callback, so the last batch survives `process.exit`; after a forced close the server waits up to 1 s for the cut-off requests to settle before the database closes.

## 9. Development stack defaults and preview deploys

- **status**: resolved
- **resolution**: the compose ports are published on `127.0.0.1` only; `wrangler.jsonc` sets `DATABASE_AUTO_MIGRATE` to `true` for every environment (a new D1 needs no separate step), and a deployment whose schema exists passes `--var DATABASE_AUTO_MIGRATE:false`. The development credentials stay as code defaults on purpose (the compose stack's own). Found on the way: `pnpm deploy` is pnpm's own command and shadows the script; the docs now say `pnpm run deploy`, and the stale `--env production` is gone.

## 10. Startup and CLI cost

- **status**: resolved
- **resolution**: a one-shot CLI command runs with telemetry off unless `OTEL_SDK_DISABLED` is set (`main.ts`), so a dead collector no longer adds over a second to `migrate:status` (1.4 s to 0.3 s measured). The Redis client is its own chunk and the entry does not load it (checked in the built `index.mjs`); a CLI start is about 90 ms. `PRAGMA synchronous = NORMAL` is on.

## 11. Housekeeping

- **status**: resolved
- **resolution**: `/.well-known/security.txt` names `aris@duck.com`; `LICENSE` (MIT, Aris Ripandi) exists and `package.json` names the author; `.gitignore` explains why `/vendor/` is listed (a tracked subtree that linters skip) and lost its template lines. `DatabaseService.transaction` stays, as `rules.md` documents it, with no production caller.

## 12. A stalled `transaction` callback

- **status**: open, latent
- **what**: a callback that never settles holds the single connection, and cancelling the request cannot stop it (Kysely's `transaction().execute` takes no signal); no caller exists outside `DatabaseService`.
- **trigger**: the first endpoint that opens a transaction.

## 13. Files to delete by hand

- **status**: resolved
- **what**: `src/database/dialect/sqlite-mutex.ts` and `src/database/query_signal.ts` were unused (the mutex was removed, the signal helper was an abandoned approach); `rm` was refused when they were found.
- **resolution**: removed with `git rm` during the Vite migration (staged, not committed).

## Fixed right after the audit (already committed)

`migrateDown` rolled back nothing once two migrations were applied (off by one); the memory limiter scanned every bucket per request once full; `redactText` was quadratic on adversarial text; an inbound `x-request-id` is accepted only from a safe charset; a stalled request body was outside `REQUEST_TIMEOUT` and held its in-flight slot (now `408`); a hung OTLP collector grew memory without bound (now a 5 s deadline per export); a failed Worker build leaked its runtime; the HTTP method label could mint metric series; an undecodable cache entry was re-read on every request; stale statements in `.llms/` and `docs/`, dead builder helpers and unused config re-exports.

## 14. `PROXY_PROTOCOL` and `CLOUDFLARE_LOCATION_HEADERS`

- **status**: resolved
- **resolution**: both implemented on the owner's instruction: `PROXY_PROTOCOL` (`kernel/http/proxy_protocol.ts`, driven by `server.ts` through srvx's `manual` option; tested with a real `http.Server` and no port) and `CLOUDFLARE_LOCATION_HEADERS` (`middleware/client_location.ts`; `country` / `city` in the request log, believed only with `TRUSTED_PLATFORM`). Not exercised on a real socket or behind a real balancer. The original description follows.
- **what**: the proxy-trust documentation the owner supplied also describes `PROXY_PROTOCOL` (accept the PROXY protocol header from listed load balancers, which needs a TCP-level wrapper around the listener) and `CLOUDFLARE_LOCATION_HEADERS` (country and city from `CF-IPCountry` / `CF-IPCity`). Nothing here uses a location (there is no sign-in or audit log), and srvx exposes no hook for the PROXY protocol, so both were left until the scope is confirmed.
- **trigger**: (was) an answer on scope.
