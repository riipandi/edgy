## Findings

### F1 — Rate-limit 429/503 responses bypass the API envelope contract (medium, confidence high)

- **Status:** resolved (7cc48e307) — local fix in `rate-limit.ts`; the stack reorder premise was disproved by a production probe (the requestId middleware wrapper sits outside the limiter, so `RequestId` already resolves the real id inside it).

- **Where:** `src/middleware/rate-limit.ts:296` (503), `src/middleware/rate-limit.ts:303-304` (429); contract in `.llms/api-response.md` (error envelope) and `src/kernel/http/envelope.ts`.
- **What:** The 503 store-failure response body is `jsonUnsafe({ _tag: 'ServiceUnavailable' })` — a flat body that `envelope.ts`'s own comment forbids for `/api/*` responses. The 429 body is plain text `Too Many Requests`. Neither carries the error envelope's `status`/`message`/`error`/`metadata` shape, so `metadata.request_id` and the documented `rate_limit` metadata ("also on a 429 and on any error under the rate limiter", `.llms/api-response.md`) never appear.
- **Failure scenario:** An API client that parses every `/api/*` error as the documented envelope throws on a 429 (plain text) or a 503 (flat `{_tag}` body); retry logic keyed on `error.retryable` and `error.details.retry_after` cannot work on the one response where `retry_after` matters most.
- **Root cause:** Middleware order in `src/kernel/http/stack.ts:20-26` — `requestTracer → cors → routes (rate-limit inside) → requestId → errorResponse → …`. The rate limiter answers before `requestIdMiddleware` runs, so `RequestId` is still `''` and a conforming envelope cannot be built in place.
- **Fix directions:** (a) move `requestIdMiddleware` ahead of the routes in the stack so the limiter can mint an envelope; or (b) mint a local request id inside the rate-limit rejection path. (a) is the structural fix; (b) is local but leaves the order trap in place.

### F2 — `ApiRateLimitedError` is dead code (low, confidence high)

- **Status:** resolved (7cc48e307) — adopted as the 429 envelope's error tag in the F1 fix.

- **Where:** `src/kernel/http/errors.ts` (definition); grep confirms zero usage outside `errors.ts`.
- **What:** The error class exists but no route, handler, or middleware raises it — the limiter answers 429 directly with a text body (see F1). Sibling classes (`ApiConflictError`, `ApiServiceUnavailableError`, `ApiNotFoundError`) are all used in `user_route.ts`/`user_handler.ts`.
- **Failure scenario:** None at runtime; it is a maintenance trap — a future contributor wiring the limiter to raise it would change the wire shape silently.
- **Fix direction:** Either delete it or use it as part of the F1 fix (the natural home for a conforming 429 envelope).

### F3 — Rate-limit key falls back to the whole `x-forwarded-for` header (low, confidence high)

- **Status:** resolved (80bf68c42) — the fallback keys on the rightmost untrusted entry via `xForwardedClient` (exported from `trust-proxy.ts`), so a list-valued header no longer merges clients into one bucket.

- **Where:** `src/middleware/rate-limit.ts` (key derivation, `remoteAddress` fallback).
- **What:** When `remoteAddress` is undefined the key becomes the raw `x-forwarded-for` header string. A client sending a list-valued header (`a, b, c`) gets a different bucket per value combination, and two clients sharing one proxy chain share a bucket.
- **Failure scenario:** Rare in production (a socket always has a remote address; the fallback exists for tests/proxies that strip it), but a spoofable-header-dependent bucket split is a correctness wrinkle worth a one-line normalization (rightmost value) if it ever fires.
- **Fix direction:** Normalize the fallback to the rightmost untrusted XFF entry (the same rule `trust-proxy.ts` already implements) or drop the header fallback entirely.

### F4 — `?nocache=1` lets any client bypass the user cache (low, confidence high)

- **Status:** resolved (7ac470e25) — gated to non-production on both surfaces (the audit's "loader path is the only consumer" claim was wrong: `user_handler.ts` honors the same param on `/api/users/:id`; scope delta approved by the owner).

- **Where:** `src/modules/identity/user/user.server.ts` (`fetchUserPage` reads the query param).
- **What:** Any unauthenticated client can force a cache miss per request. The rate limiter bounds the abuse, and the loader path is the only consumer, but the affordance is undocumented and its intent (debugging aid vs. product feature) is unstated.
- **Failure scenario:** A scripted client alternating `?nocache=1` doubles backend read load within the rate-limit ceiling; a CDN in front would also be defeated per-request.
- **Fix direction:** Document it as a debug affordance, gate it to non-production, or remove it. Owner's call.
