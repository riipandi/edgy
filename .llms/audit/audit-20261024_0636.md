# Audit: whole system

## Executive summary

The codebase is in good shape one day after the 2026-10-23 full sweep: the prior fixes held, the
test suites are green, and no dependency vulnerability or secret leaked in. But the audit found one
serious deployment defect the prior audits could not see: **the standalone container cannot render a
single page** — the SSR bundle leaves `@solidjs/web` external, which resolves locally through
`node_modules` and fails in the distroless image. Every `/` request in the container answers 500
while the API answers 200, and this has been true since the standalone build landed on 2026-10-18.
The remaining findings are a Redis boot-time availability gap, a validation-matrix blind spot that
let the SSR defect through, and two low-severity hardening items.

Findings: 1 high, 2 medium, 2 low, 1 info (6 open; 5 verified by repro, 1 by code trace).

Fix first: **F-01** (standalone SSR external import), **F-03** (Redis boot kills serve),
**F-02** (close the validation blind spot that hid F-01).

cache, vite-plus toolchain; observability via OpenTelemetry into a self-hosted ClickStack
(ClickHouse) provisioned by a compose sidecar. Audited at commit `c008135d1` on `refine-architecture`,
working tree clean. Two prior full audits exist (2026-10-23 morning and evening, all findings

(plan-20261024_0105) and the dead-code cleanup (plan-20261024_0556).

Flows audited:

1. serve boot: config load/validate → database migrate → observer (logger/tracing/metrics) → HTTP
   composition root (trust-proxy, request-id, request-log, rate-limit, security-headers, tracer) →
   SIGTERM graceful shutdown

6. observability export: OTLP spans/metrics/logs push → collector → ClickHouse; runtime gauges
7. compose provisioning: provision.sh reconciles connections/sources/dashboards/alerts/retention
8. CLI: serve, generate-config, migrate-up/down/reset/status/seed, healthcheck

### F-01 Standalone SSR bundle externalizes `@solidjs/web`; every page 500s in the container

- **Category**: defect (deployment)
- **Location**: `src/builder/vite-plugin.ts` (the `standalone` branch sets `resolve.noExternal: true`
  only on the `effect` environment); `dist/server/server.js:1`
  (`import{...}from"@solidjs/web"`, plus `@solidjs/web/server-functions`)
- **Problem**: the SSR bundle emitted beside `entry.js` still externalizes the Solid web runtime.
  Locally the import resolves through `node_modules`; the distroless image ships no `node_modules`,
  so loading the bundle throws.
- **Scenario**: build the image (`docker compose build app`), start it, request any page →
  `InternalError ... Cannot find package '@solidjs/web' imported from /app/server/server.js`, HTTP
  500. Reproduced on a fresh rebuild at this commit; the API surface answers 200 the whole time.
- **Impact**: the primary UI is down in the intended deployment artifact; only API, `/metrics`, and
  static assets work. Present since `afaf0f3ec` (2026-10-18) introduced the standalone split.
- **Evidence**: `docker logs edgy-app-1` (fresh image, built from `c008135d1`); `curl /` → 500 with
  `/api/users` → 200. `grep -o 'from"@solidjs/web"' dist/server/server.js` matches.
  **verified**
- **Fix**: in standalone mode, also inline the externals of the environment that emits
  `server/server.js` (`resolve.noExternal: true` / `ssr.noExternal` for the SolidStart SSR
  environment), or vendor the solid runtime into the image. Trade-off: a larger server bundle.
  Then add `/` (an SSR render) to the standalone validation matrix — see F-02.
- **Confidence**: high

### F-02 The validation matrix runs where `node_modules` masks externalized imports

- **Category**: test quality
- **Location**: `playwright.config.ts` (webServer runs `node dist/entry.js serve` from the repo
  root), the standalone probe routine used by recent plans (API endpoints only)
- **Problem**: every local validation path — e2e webServer, manual probes of `dist/entry.js` —
  executes inside a tree that has `node_modules`, so an externalized import in the standalone
  bundle resolves successfully and the defect (F-01) is invisible. The matrix's container-side
  probes only ever hit API endpoints, never an SSR render.
- **Scenario**: the exact sequence this audit followed: local e2e 28/28 pass, container `/` 500.
- **Impact**: deployment-artifact defects in the SSR path ship silently.
- **Evidence**: this audit's runs: e2e local 28/28 pass (17.2s) vs container 24/28 fail.
  **verified**
- **Fix**: either point e2e at the built container (the `E2E_BASE_URL` mode already exists) in CI,
  or add a standalone probe that renders `/` — e.g. run the webServer with `NODE_PATH` empty /
  `--no-experimental-fetch`-style isolation is fragile; simplest is a scripted container probe
  (`docker compose build app && compose up` then curl `/` expecting 200) as part of the validation
  matrix.
- **Confidence**: high

### F-03 Redis outage at boot kills serve instead of degrading

- **Category**: operability
- **Location**: `src/kernel/cache.ts` (`Layer.build(Persistence.layerRedis…)` wrapped in
  `Effect.orDie`), `src/middleware/rate-limit.ts` (`Layer.orDie(RateLimitCounterLayerRedis…)`),
  `compose.yaml` (`app` sets `REDIS_ENABLE: 'true'`, `depends_on: redis: service_started`)
- **Problem**: both Redis consumers build their client at layer construction and turn a connection
  failure into a defect. The module comments promise "the cache is an optimization, not a
  dependency" and "store failure answers 503" — true for runtime reads, false for boot: the process
  exits before it listens.
- **Scenario**: `REDIS_ENABLE=true node dist/entry.js serve` against a dead Redis port →
  `RedisError ECONNREFUSED` → process dead, probe 000. Reproduced. Under compose, a cold start or
  an app restart while Redis is down becomes a restart loop (`restart: unless-stopped`) instead of
  a degraded API.
- **Impact**: Redis unavailability takes the whole application down (DB, telemetry, graceful drain
  included) rather than only the cache and the limiter.
- **Evidence**: repro on the standalone binary at this commit (log captured). **verified**
- **Fix options**: (a) compose `depends_on: redis: { condition: service_healthy }` — one line,
  covers cold start but not mid-run outages followed by restart; (b) retry-with-backoff around the
  boot connection so the app waits for Redis; (c) lazy/degraded boot — start unlimited and let the
  first consume fail closed. Recommend (a) now plus (b) if restart-loops in production matter.
- **Confidence**: high

### F-04 Runtime metrics sampler runs even when metrics are disabled

- **Category**: performance (small, constant waste)
- **Location**: `src/kernel/layers.ts:9-10` (`telemetryLayer = Layer.merge(TelemetryRuntimeLayer,
  RuntimeMetricsLayer)` merged into `CoreLayer` unconditionally); `src/observer/runtime-metrics.ts`
- **Problem**: `RuntimeMetricsLayer` enables `monitorEventLoopDelay`, a GC `PerformanceObserver`,
  and a 10s sampling fiber whenever the core layer builds — even with `METRICS_ENABLED=false` and
  `OTEL_SDK_DISABLED=true` (the default outside the compose stack). The metrics go nowhere.
- **Scenario**: read of the layer graph; no config gate anywhere on this path.
- **Impact**: constant per-process overhead with no consumer; not a leak, not a stall.
- **Evidence**: code trace (`layers.ts` merge, no `metricsEnabled` check). **verified (trace)**
- **Fix**: gate `RuntimeMetricsLayer` on `config.observability.metricsEnabled` the same way the
  Prometheus HTTP layer is gated in `kernel/http/serve.ts`. Trade-off: none — the gauge data only
  matters when something scrapes it.
- **Confidence**: high

### F-05 `APP_BASE_URL=''` passes validation despite the absolute-URL contract

- **Category**: validation
- **Location**: `src/kernel/config/app.ts` (`parseBaseUrl` returns `succeed('')` for the empty
  string)
- **Problem**: the doc comment says the value "must be an absolute http(s) URL", but an empty value
  is accepted at boot. Today this is harmless — the platform hands the server absolute request URLs,
  so the consumers that parse `new URL(request.originalUrl, baseUrl)` never need the base — but the
  config contract and the implementation disagree, and a future consumer relying on the base would
  inherit a broken value silently.
- **Scenario**: `APP_BASE_URL= node dist/entry.js serve` boots cleanly (verified); every probe
  answers 200 because the base is simply unused.
- **Impact**: latent only; a validation gap, not a live failure.
- **Evidence**: live boot with the empty value + all probes 200; `node -e` confirms
  `new URL('/x','')` throws, proving the consumers only survive via absolute `originalUrl`.
  **verified**
- **Fix**: reject the empty string in `parseBaseUrl` (or document empty as "auto-resolve from the
  request" if that is the intent — then make the comment say so).
- **Confidence**: high

### F-06 `/api/users` publishes every user's email unauthenticated

- **Category**: privacy
- **Location**: `src/modules/user/module.ts` (`listUsers` maps the full row through
  `toPublicUser`, which keeps `email`)
- **Problem**: the list endpoint returns names plus emails for all users to any caller; there is no
  authentication on the API yet, so this is currently by design for a scaffold — but the moment
  auth or real user data lands, this becomes a data exposure (account-enumeration and PII leak).
- **Scenario**: `curl /api/users` → array of `{id, email, name, …}` for every seeded user.
- **Impact**: none today (seed data only); high blast radius the day real users exist.
- **Evidence**: code trace + live probe. **verified (trace)**
- **Fix**: not now. Trigger: the first authenticated endpoint or real user data. Options then:
  drop `email` from the public projection, or gate the list endpoint. Recorded so the trigger is
  explicit; pairs with the CORS note already in `middleware/cors.ts`.

## Clean bills

No memory leaks (every resource closes through scopes, finalizers, or explicit disposal; the
graceful drain drops idle keep-alive sockets before `server.close`), no SQL injection surface (all
queries parameterized through Kysely), no XSS surface (CSP with per-request nonce and
`strict-dynamic` on pages; no raw HTML sinks), error bodies carry no internal causes, the log file
rotation/pruning logic is correct (bounded by `maxFiles`, keeps the active file), the rate-limit
counter is atomic (`returning('count')` upsert), log forging is not possible (percent-encoded
pathname stays encoded in both pretty and JSON formats — probed with `%0A`), the trust-proxy chain
resolution follows the rightmost-untrusted algorithm, migrations are transactional with ordered
registration and correct reverse-order `down` scripts, the seeder is idempotent
(`onConflict doNothing`), and the config field parsers reject every malformed input probed
(milliseconds, port, trust-proxy CIDRs, CORS origins, redis URLs).
