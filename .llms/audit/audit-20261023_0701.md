## Findings

### D1 — `serve --auto-migrate` with `DATABASE_PATH=:memory:` serves a schema-less database (High)

Reproduction: `DATABASE_PATH=:memory: DATABASE_AUTO_MIGRATE=true dist/entry.js serve`, then `GET /api/health` → **500**, log line `RateLimitError: no such table: rate_limits` (`src/command/serve.ts:57` migrates on a `Layer.provide(DatabaseLayer)`, `src/command/serve.ts:65` then serves on a second `DatabaseLayer` through `ApplicationLayer`). Two `:memory:` databases are two distinct databases, so the second one has no tables. Every request fails at the rate-limit counter, before any route runs.

This contradicts two written claims: `.llms/rules.md` ("`serve --auto-migrate` applies migrations and then serves requests with the same scoped `Database` service, including when `DATABASE_PATH=:memory:`") and `docs/development.md` ("With `DATABASE_PATH=:memory:`, startup migrations and requests use the same database for the lifetime of the server"). A file-backed path hides the defect because both connections see the same file.

### D2 — `HEAD /api/*` answers 404 HTML instead of the GET route's status (High)

Reproduction on the production build: `GET /api/health` → `200 application/json`, `HEAD /api/health` → **404 `text/html`**. `HEAD /api/users` → 404. `HEAD /users` → 200. Also reproduced at handler level: with the production composition (`src/kernel/http/server.ts:16` `ssrRouter = HttpRouter.add('*', '*', renderPage)`) HEAD on an API path never reaches the router's HEAD→GET fallback (`node_modules/effect/src/http/HttpRouter.ts:217`), because the catch-all `*` route matches first and renders the SSR page, which 404s. Removing the catch-all makes `HEAD /api/health` return 200, which isolates the cause.

Impact: health probes, link checkers, and CDN revalidators that use HEAD see 404 for every API endpoint. `src/kernel/http/server.ts:16` is the single line at fault; the dev composition (`src/kernel/http/api.ts:44-56`) has no catch-all and answers HEAD correctly (verified: `HEAD /api/health` → 200 in `vpr dev`).

### D3 — `/api-docs` ships a CSP that forbids the page's own script, so the Scalar UI never boots (High)

Reproduction: `API_DOCS_ENABLED=true`, `GET /api-docs` → 200, 3,157,774 bytes, and the response CSP is `default-src 'self'; style-src …` with **no `script-src`**. `default-src 'self'` governs scripts, and the Scalar reference is an **inline** `<script>` (`HttpApiScalar.layer` inlines `internal/httpApiScalar.ts`). The browser blocks it; the reference renders an empty container. Two inline `<script>` blocks are present in the body.

Root cause is the interaction of two correct decisions: `src/middleware/security-headers.ts:37` skips a response that already carries a CSP, and `HttpServerResponse.html` sets none, so the global middleware's nonce-less policy applies. The page is the only HTML surface that is not the Solid bundle and therefore never receives the per-request nonce path from `src/kernel/renderer.ts`.

### D4 — CORS echoes any origin with `credentials: true` (Medium, owner chose to keep)

Reproduction: preflight `OPTIONS /api/users` with `Origin: https://evil.example.com` → `204` with `access-control-allow-origin: https://evil.example.com` and `access-control-allow-credentials: true`; the same echo on a plain GET. `src/middleware/cors.ts:23-27`. The default configuration (`CORS_ALLOWED_ORIGINS` empty) makes every origin a credentialed caller of the API.

No authentication exists in this tree, so today the risk is bounded: there is nothing to steal with a cookie. It becomes a real cross-site data-read primitive the moment an auth cookie lands. Owner decision this turn: keep the behavior, document the risk. Recorded as `wontfix` with a named reopen trigger in `issue-20261023_0701.md`.

### D5 — the SQLite file and its directory are created world-readable/writable (Medium)

Reproduction: after a first `serve`, `ls -l /tmp/probe.db` → `-rw-r--r--`, i.e. `0644`, while `src/database/dialect/sqlite.ts:31` chmods the _directory_ to `0775`. The database file itself is created with the process umask (022 → 0644), so on a multi-tenant host any local user can read the whole database. `-shm`/`-wal` sidecars inherit the same mode.

The container path is not affected (`USER nonroot`), which is why the Docker probe stays green; a bare-metal or shared-host deployment is.

### D6 — two redundant indexes duplicate the UNIQUE autoindexes (Medium)

Reproduction from `pragma index_list` on the migrated database:

- `users`: `sqlite_autoindex_users_2` (`unique=1`, origin `u`, column `email`) plus `idx_users_email` (`unique=0`, column `email`) — `src/database/migrations/00002_create_identity_table.ts:22`.
- `api_tokens`: `sqlite_autoindex_api_tokens_2` (`unique=1`, origin `u`, column `token_hash`) plus `idx_api_tokens_token_hash` (`unique=0`, column `token_hash`) — `src/database/migrations/00003_create_token_tables.ts:22`.

The `.unique()` column constraint already creates a covering index, so each extra index doubles the write cost of that column and buys nothing. Owner decision: fix in place by editing the two migrations (no new migration), recorded with its consequence in the issue file.

`idx_users_disabled` was checked and is **not** redundant: `disabled` is a plain integer column with no constraint-derived index.

### D7 — hashed static assets are served without a long-lived `Cache-Control` (Medium)

Reproduction: `GET /assets/index-BpvubFUJ.js` → `200`, `etag` and `last-modified` present, **no `cache-control`**. `src/kernel/renderer.ts` builds `HttpStaticServer.make({ root: clientRoot, index: 'index.html' })` without the `cacheControl` option (`node_modules/effect/src/http/HttpStaticServer.ts:97,111`), so every browser revalidates every hashed asset on every navigation. `docs/frontend.md` claims "a file's name carries its content hash, so browsers keep it for a year" — the code does not send the header that makes that true.

### D10 — a rate-limit store failure surfaces as 500, not 503 (Low)

Reproduction: the D1 `:memory:` probe — the store is unusable, so `RateLimitError` escapes the middleware and the response is a bare `500` with an empty body, while the same class of failure (database unavailable) is a documented `503 ServiceUnavailable` everywhere else (`src/modules/user/module.ts:38`, `src/modules/health/module.ts:19`). `src/middleware/rate-limit.ts:80` maps the store failure into `RateLimitError` but nothing maps it to a response.

### P1 — the Effect chunk is 3.34 MB because the CLI, HTTP server, telemetry, and DB all land in one bundle (Medium)

The standalone build emits `effect-*.js` at 3,344 kB (937 kB gzip) and `@effect__platform-node-*.js` at 872 kB (222 kB gzip), against 52 kB for `entry.js`. Everything is reachable from `src/main.ts` because `cli.ts` imports all eight commands and `serve.ts` imports the whole HTTP composition. A `serve`-only or `healthcheck`-only process still pays the full parse/compile cost. This is a cold-start cost, not a per-request one; the container has no measured cold-start budget yet, so this is recorded as a lead with a measurement first move rather than a fix.

### P2 — `users.list()` is unbounded and exposes every column (Low, previously accepted)

`GET /api/users` returned the full table with `data`, `email_verified`, `disabled`, and timestamps (verified payload). The previous audit accepted the unpaginated list "at scaffold scale"; the column exposure was not part of that acceptance. Both are recorded as one item with a named trigger.

### P3 — every Kysely query re-prepares its statement (Low)

`node:sqlite`'s `prepare` returns a new statement object per call (verified), and Kysely's SQLite driver prepares per `executeQuery` (`node_modules/kysely/dist/dialect/sqlite/sqlite-driver.js:58,73`). Every request therefore pays a compile step for its SQL. This is inherent to the driver Kysely ships and not fixable in this tree without replacing the driver; recorded for the decision record, not as work.

## Clean bills (verified this turn, no action)

- **SQL injection**: no string-concatenated SQL. Every query goes through Kysely builders; the one raw fragment is `sql\`rate_limits.count + 1\`` with no interpolation (`src/middleware/rate-limit.ts:52`).
- **Path traversal**: `GET /assets/../../package.json`, percent-encoded, backslash, and `/..%2f..%2f` variants all → 404. `HttpStaticServer` resolves inside its root.
- **XSS**: no raw-HTML sink in `src/`. The only inline scripts are the Solid hydration bootstrap (nonce-gated) and the Scalar page (D3).
- **Error bodies**: no internal cause leaks. The `UserRepositoryError`/`DatabaseError` causes stay in logs; HTTP bodies are `{"_tag":"…"}` (verified for 400/404/503).
- **Request smuggling / body limits**: an 8 MB POST body to a route that does not accept one is rejected at 404 without buffering; `node:http` header limits return 431 for an oversized query string (verified).
- **Memory leaks**: every resource closes through a scope or finalizer. The graceful-shutdown probe (`SIGTERM`) logged `shutting down` → `server stopped accepting connections` → `closing database connection` → `database connection closed` → `application terminated`, and the process exited. The static-handler memo (`src/kernel/renderer.ts:70`) is a single built handler, not per-request state.
- **Race conditions**: the rate-limit window is a single atomic upsert with `returning('count')` (`src/middleware/rate-limit.ts:44-53`), so two processes cannot read the same count. The cache's failed-fill invalidation is covered by a test (`src/modules/user/user_service.test.ts`). The stale-`ManagedRuntime` path (`user_ssr.ts`) is only reachable after disposal, which also tears down the HTTP handler; `runtime.context()` throws after disposal (verified), so a late request fails loudly rather than serving a stale context.
- **Cache semantics**: `x-cache` transitions verified live — `miss` on first API read, `hit` on the next, `bypass` with `?nocache=1`, on both the API and the SSR page.
- **Rate limiting**: verified live — `ratelimit-*` headers on success, `429` + `retry-after` past the max, and the docs endpoints are inside the limited scope (`/api/openapi.json` → 429 after the third request at `RATE_LIMIT_MAX=2`).
- **Migrations**: all four apply and roll back; `migrate:status`, `migrate:up`, `migrate:seed`, `migrate:reset`, `migrate:down` were exercised through the built CLI; `generate:config --check` reports `.env.example` in sync.
- **CSP on real pages**: the SSR responses carry the per-request nonce and `strict-dynamic` (verified on `/`, `/users`, `/users/:id`, and the 404 page); static assets carry the nonce-less policy.
