# Audit — React/TanStack Start migration surface

## Executive summary

The SolidJS → React/TanStack Start migration (plan `archive/plan-20261027_0605.md`) landed correctly: all six flows render through the single Effect listener, the D7 `x-cache` bridge works end to end, the API contract is unchanged, and the full automated baseline is green (301 unit tests, 7 E2E, clean check/typecheck, green standalone and Storybook builds, no dependency vulnerabilities, no secret-pattern hits).

The audit found no critical or high defects. Two medium findings deserve a fix: page HTML responses are missing three hardening headers the API keeps (`referrer-policy`, `x-content-type-options`, `x-frame-options`), and the hand-built D7 chain — the most fragile piece of the migration — is covered by exactly one unit test, with the `x-cache` header verified only by manual probes. Four low findings: soft-404 status codes on the detail page, internal error messages leaking onto 500 pages, the accepted per-process CSP nonce tradeoff, and stale `_app`-era comments and dead ignore entries.

### M1 — Page HTML responses miss the hardening headers the API keeps

- **Category**: OWASP A05 Security Misconfiguration. **Severity**: medium. **Confidence**: high (verified by probe).
- **Location**: `src/middleware/security-headers.ts:34-37` (`applySecurityHeaders` returns the response untouched when a CSP header is already present) and `src/kernel/renderer.ts:44-46` (`renderFromBundle` sets `content-security-policy` explicitly before the response leaves the Effect layer).
- **Failure scenario**: `applySecurityHeaders` short-circuits on an existing CSP, so every page response — which always carries the renderer-set CSP — never receives `referrer-policy`, `x-content-type-options`, or `x-frame-options`. Probe against the built binary confirms: `/users` returns only `content-type` + `content-security-policy`, while `/api/health` returns all four hardening headers. Consequences: referrer URLs leak to third-party origins linked from pages, and MIME-sniffing protection is absent on the highest-traffic surface. Clickjacking is partially covered by CSP `frame-ancestors 'none'`, which is why this is medium, not high.
- **Fix**: set the full hardening set on page responses — either have `renderFromBundle` apply all of `securityHeaders` (overriding only the CSP directive), or change `applySecurityHeaders` to always set the three non-CSP headers and only skip the CSP itself.

### M2 — The D7 bridge chain has almost no automated coverage

- **Category**: operability / test quality. **Severity**: medium. **Confidence**: high.
- **Location**: `src/modules/identity/user/user.server.test.ts` (one test: unparseable id → undefined); no tests exist for `fetchUsersPage`, the cache-meta write, the `?nocache=1` bypass, or the `pageResponseMeta` middleware (`src/start.ts`); no E2E spec asserts the `x-cache` header.
- **Failure scenario**: the bridge is hand-built ALS plumbing whose store is shared across two separately bundled modules by a `Symbol.for` global — the most fragile mechanism the migration introduced. Its correctness is currently pinned only by manual probes against a built binary, which do not run in CI. Any refactor of `user.server.ts`, `pagemeta.ts`, or `start.ts` can silently drop the header with no test failing (this exact failure shape occurred during the route restructure, though there the cause was a dropped loader).
- **Fix**: unit tests for `fetchUserPage` (meta written on found, bypass honored, meta absent when no request context), a test for `pageResponseMeta` (header set when store carries `cache`, absent otherwise), and one E2E assertion that the detail page response carries `x-cache: hit|bypass`.

### M3 — Detail page answers 200 for unknown and malformed ids (soft 404)

- **Category**: correctness / API semantics. **Severity**: low. **Confidence**: high (verified by probe).
- **Location**: `src/routes/(app)/users/$id.tsx` (loader returns `undefined` on parse failure and unknown id; no status is ever set).
- **Failure scenario**: `/users/abc` and `/users/<valid-but-unknown TypeID>` both return HTTP 200 with a "User not found" body, while the API (`/api/users/:id`) and the catch-all page correctly return 404. Monitors, crawlers, and caches treat the page as a valid resource; the inconsistency is a soft-404 pattern.
- **Fix**: in the loader, `setResponseStatus(404)` (via the isomorphic server entry, same pattern `$.tsx` already uses) when the resolved user is undefined — SSR only, matching the catch-all.

### M4 — Internal error messages leak onto 500 error pages

- **Category**: OWASP A05 Security Misconfiguration. **Severity**: low. **Confidence**: high (verified by injected failing loader in a production build).
- **Location**: Start's SSR error surface reached through `src/kernel/renderer.ts` (`Effect.tryPromise` → `InternalError`).
- **Failure scenario**: with a loader that rejects with `new Error('AUDIT-DEBUG loader failure')`, the production 500 response body contains that exact message twice (SSR markup and the hydration payload). No stack traces leak (verified: zero `at `/`node_modules` occurrences). Internal error messages can carry file paths, driver errors, or query fragments.
- **Fix**: map server-side defects to a generic client message before they reach Start's error rendering (e.g. catch in the loader wrapper and rethrow a sanitized error), or configure Start's built-in error masking if available in the pinned version.

### M5 — Per-process CSP nonce shared by every response until restart (accepted)

- **Category**: OWASP A02/CSP nonce hygiene. **Severity**: low. **Confidence**: high.
- **Location**: `src/kernel/csp_nonce.ts` (one TypeID nonce per process via a `Symbol.for` global), `src/router.tsx` (`ssr: { nonce: cspNonce }`).
- **Failure scenario**: all pages served by one process share one nonce; a nonce captured from any response is valid on every other page until restart. Start 1.169/1.171 offers no per-request nonce wiring (`fetch` context nonce is an unconsumed type; request middlewares run outside the router ALS), so the owner chose the per-process nonce explicitly during the plan (recorded in the archived plan's phase 2 note). `strict-dynamic` plus `'self'` bound the exposure.
- **Recommendation**: keep as an accepted risk; revisit when Start supports per-request nonces. No action now.

### M6 — Stale `_app`-era comments and dead generated-tree entries

- **Category**: hygiene. **Severity**: low. **Confidence**: high.
- **Location**: `src/routes/(app)/route.tsx:4-5` and `src/routes/(app)/users/route.tsx:3-4` (comments still describe the `_app` pathless layout and `users.tsx` pairing, replaced by the route-group restructure); `.gitignore:86` and `.vscode/settings.json:29,40` list `routes.gen.ts`, which no generator writes (the tree is `routeTree.gen.ts`).
- **Failure scenario**: misleading comments and dead ignore/editor entries misdirect future readers. No runtime effect.
- **Fix**: rewrite the two comments for the route-group structure; drop the `routes.gen.ts` entries.

### I1 — Deferred loaders would silently drop the x-cache header

- **Category**: correctness trap. **Severity**: info. **Confidence**: high (code-trace; current loaders are awaited so unreachable today).
- **Location**: `src/kernel/pagemeta.ts` (`getPageMeta()` returns undefined outside the middleware's ALS scope) and `src/start.ts` (the store closes when `next` resolves).
- **Scenario**: if a loader ever becomes deferred/streamed (`loader` returning a deferred promise), the handler runs after the middleware's `runWithPageMeta` scope has closed, `getPageMeta()` is `undefined`, the cache meta is silently dropped, and the page simply lacks `x-cache`. The code comment already records the trap; nothing to fix while loaders stay awaited.

### I2 — POST to a page path answers 404

- **Category**: correctness (expected behavior, recorded). **Severity**: info.
- **Location**: `src/kernel/renderer.ts` method gate; Start file routes.
- **Scenario**: `POST /users` → 404 (probed). Page routes match GET/HEAD only; API mutations have their own `/api/*` procedures. Correct for this architecture; recorded so it is not re-litigated.

### I3 — Public directory page exposes user emails

- **Category**: security / privacy (pre-existing product surface, unchanged by the migration). **Severity**: info.
- **Location**: `src/routes/(app)/users/index.tsx`, `src/modules/identity/user/user_schema.ts` (`toUserResult`).
- **Scenario**: the seeded directory lists names and emails publicly, matching the pre-migration page. Out of migration scope; flagged for a future product decision (redaction or auth-gating).

### I4 — `vite-plugin-solid` peer metadata remains in the lockfile

- **Category**: hygiene (third-party metadata). **Severity**: info. **Confidence**: high.
- **Location**: `pnpm-lock.yaml` (`@tanstack/router-plugin` declares an optional `vite-plugin-solid` peer range).
- **Scenario**: not this repository's trace; it is the published package's optional peer declaration and cannot be removed without forking. Recorded so future trace sweeps skip it.

## Outcome (phase 6)

All approved findings were fixed in three commits, each validated before the next:

- `7c7138ac2` **M1** — `applySecurityHeaders` now takes the CSP as a parameter (default `cspFor()`), always sets the three non-CSP hardening headers, and keeps any response's existing CSP; the docs middleware passes `docsCspFor()` explicitly. Verified by updated unit tests and a probe: page responses now carry `referrer-policy`, `x-content-type-options`, and `x-frame-options`.
- `f7d8a3dc7` **M3 + M4** — the `$id` loader answers 404 during SSR when the user is missing (same body inside the shell) and both page loaders chain a `.catch` that logs the real cause server-side and rethrows a safe message. Verified by probe (unknown/malformed id → 404, valid → 200, `x-cache: hit` intact) and by re-running the injected-failure repro: the original message no longer reaches the markup or the dehydration payload, and the server log carries the cause. The first masking attempt used the second `.then` handler, which does not catch its own first handler's throws — the chained `.catch` is the shape that works.
- `1c4ec3a7e` **M2 + M6** — three unit tests pin `fetchUserPage`'s contract (meta store written on found and on unknown id, `?nocache=1` bypass reaching the service) with a stubbed `UserService` and a mocked request accessor; the middleware itself is covered end-to-end by two new E2E assertions (detail page carries `x-cache: hit|miss`, `?nocache=1` carries `bypass`, unknown id answers 404). The two stale comments and the dead `routes.gen.ts` entries are gone.

Final validation after the fixes: `vpr check` green, `vpr test` 304/304 (was 301), `vpr e2e --project Chromium` 8/8 (was 7).
