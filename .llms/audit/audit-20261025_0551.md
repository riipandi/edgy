# Audit: Turso database driver refactor

## Executive summary

- The swap itself is sound: one dialect over two transports, the mutex in place of a hand-rolled lock, migrations, seeders and the rate-limit counter all run over the new driver, and 122 tests are green. The defects are concentrated in the **remote transport's failure paths** and in the **lifecycle edges** the local engine added.
- Findings: 1 high, 2 medium, 3 low, 1 info — all verified with a repro, a captured request, or a measurement.
- Fix first: (1) the remote transaction slot that is never cleared after a failed `COMMIT` (one network blip ends all database access for the process), (2) the missing timeout/cancellation path that lets one stalled request hold the only connection, (3) the cleartext `http://` transport that ships the bearer token unencrypted.

## Scope and flow inventory

Audited flows:

1. **Boot → layer acquire → first query** (`openTursoDatabase`, `DatabaseLayer`, `Database.query`/`read`/`ping`).
2. **Configuration → transport selection** (`resolveDatabaseTarget`, `parseFileUrl`, `DATABASE_URL`/`DATABASE_TOKEN`).
3. **Migration run** (`migrator.ts` → Kysely `Migrator` → `TursoConnection.beginTransaction`/`commit`/`rollback`).
4. **Transaction window under concurrency** (`Kysely.transaction`, `ConnectionMutex`, `supportsMultipleConnections = false`).
5. **Streaming** (`streamQuery`).
6. **Request-scoped query path** (`makeDatabaseService` → `db.connection().execute(run, { signal })`).
7. **Healthcheck CLI** (`healthcheck.ts` → `ping` with a 2-second budget) and the container `HEALTHCHECK`.
8. **Rate-limit counter** (`bumpWindow` insert-on-conflict through the adapter).
9. **Multi-process access** (`multiprocess_wal`, second process = healthcheck probe or a concurrent migration).
10. **Build/deploy** (`vite-plugin.ts` leak guard + native binding copy, `Dockerfile`).

Trust boundaries: `DATABASE_URL`/`DATABASE_TOKEN` (operator input), the remote HTTP endpoint (network), the database file (local filesystem, other local users), and query results entering JSON API responses.

Assumptions: no live Turso database was used except one scratch `edgy-turso-probe-*` database in group `default-ap`, created and destroyed inside the audit (per plan D9/D10). The pre-existing databases (`mapscoffee-dev`, `sosialink-stg`, `wilayah`) were never touched.

### F-01 A failed COMMIT leaves a closed transaction installed, poisoning the process

- **Category**: defect / resource lifecycle
- **Location**: `src/database/dialect.ts:66-76` (`remoteExecutor.commit` / `rollback`)
- **Problem**: `commit` awaits `transaction.commit()` and only then clears the slot. The client's `commit()` closes the transaction in a `finally` block and rethrows when `COMMIT` fails, so the slot keeps a **closed** transaction. Every later `execute` picks `transaction ?? client` and hits the client's `ensureOpen()`, which throws `Transaction is closed`.
- **Scenario**: a single transient network error at `COMMIT` (timeout, 502, connection reset). Kysely then calls `rollbackTransaction`, which throws `TRANSACTION_CLOSED` too, so the slot stays. From that moment every query — every request, the healthcheck, migrations — fails with `Transaction is closed` until the process restarts. The original error is also lost: the thrown message is `Transaction is closed`, not the network failure.
- **Impact**: total database unavailability for the process after one failed commit; the operator sees a misleading cause in the logs.
- **Evidence**: `verified` — repro script against a stubbed transport that fails exactly one `COMMIT`:
  ```
  transaction: commit failed: Transaction is closed
  query after the failed commit: FAILED — Transaction is closed
  ```
  The stub is a valid cursor/pipeline responder; only the `COMMIT` request returns 500.
- **Fix**: clear the slot in a `finally`, and treat a rollback on an already-closed transaction as a no-op so the original error survives:
  ```ts
  commit: async () => {
    const current = transaction
    transaction = undefined
    await current?.commit()
  },
  rollback: async () => {
    const current = transaction
    transaction = undefined
    await current?.rollback().catch(() => undefined)
  }
  ```
  Trade-off: swallowing a rollback failure hides a genuinely failed rollback; acceptable because the client already closed the session and Kysely surfaces the original error. Add a regression test with the same stub (a query after a failed commit must succeed).
- **Confidence**: high
- **Status**: open

### F-02 No timeout or cancellation: one stalled request holds the only connection

- **Category**: operability / availability
- **Location**: `src/database/dialect.ts:41` (`createClient({ url, authToken: token })`), `src/database/dialect.ts:63` (`close`), `src/database/adapter.ts:61` (`db.connection().execute(run, { signal })`)
- **Problem**: neither transport can be interrupted. The remote client is created with no `defaultQueryTimeout`, so `createAbortSignal` returns `undefined` and the `fetch` carries no abort signal. The local engine has no interrupt API, and `TursoConnection.executeQuery` never receives the caller's signal anyway. Kysely's `supportsMultipleConnections = false` means the whole application shares one connection behind one mutex, so a query that never returns holds it forever.
- **Scenario**: a remote database endpoint stops answering after the TCP handshake (black-holed connection, or a server-side stall). Undici's defaults let the request hang for minutes. Meanwhile every request queues on the mutex, `/api/health` returns 503 (or times out), and `Effect.timeout(Duration.seconds(2))` in `healthcheck.ts` only interrupts the Effect fiber — the `fetch` keeps running and keeps the connection. The same shape applies on shutdown: the drain waits for the query.
- **Impact**: a single stalled query takes the whole API down; the documented 2-second healthcheck budget does not bound the underlying work.
- **Evidence**: `verified` — a stub transport captured the request the client builds: `{"url":"https://probe.turso.io/v3/cursor","abortSignal":false}`. Code trace: `Session.createAbortSignal` returns `undefined` when `queryTimeout` and `defaultQueryTimeout` are both unset (`compat/index.js:366`), and `executePipeline` passes it straight to `fetch`.
- **Fix**: give the remote transport a bounded request: pass `defaultQueryTimeout` (the runtime honors it; the published `Config` type omits it, so it needs a documented cast or a local wrapper type) and set a busy/query timeout on the local side where the engine offers one. Trade-off: a slow legitimate query starts failing at the boundary; pick the value from the healthcheck budget (2 s) or make it a config key — this is a product decision, see the open question.
- **Confidence**: high
- **Status**: open

### F-03 `http://` is accepted and sends the bearer token in cleartext

- **Category**: security (A02:2021 — Cryptographic Failures; ASVS V9)
- **Location**: `src/kernel/config/database.ts:10` (`REMOTE_SCHEMES`), `src/database/dialect.ts:41`
- **Problem**: `http://` is one of the four accepted remote schemes and is passed through unchanged (`normalizeUrl` rewrites only `libsql:`/`turso:`), so the `Authorization: Bearer <DATABASE_TOKEN>` header travels unencrypted. Nothing warns, and `docs/configuration.md` lists `http://` as a supported form without qualification.
- **Scenario**: an operator copies a self-hosted endpoint as `http://db.internal:8080`, or a proxy/redirect downgrades the scheme. Every query — including writes and reads of user rows — is readable and modifiable on the path, and the token is replayable by anyone who sees one packet.
- **Impact**: full database compromise for anyone on the network path, and a long-lived credential exposed (the token is per-database and often not expiring).
- **Evidence**: `verified` — the stub captured both forms with the same credential: `{"url":"http://probe.turso.io/v3/cursor","authorization":"Bearer the-token"}` and the `https://` equivalent.
- **Fix**: keep `http://` only for a loopback/private literal and refuse it otherwise, or keep it accepted but log one explicit warning at boot ("DATABASE_TOKEN travels unencrypted over http://"). Trade-off: refusing outright breaks a legitimate local sqld on `127.0.0.1`; the warning keeps that path working. This needs the owner's call — see the open question.
- **Confidence**: high
- **Status**: open

### F-04 The sidecar `chmod` misses the engine's `-tshm` file

- **Category**: security / hardening
- **Location**: `src/database/dialect.ts:113-117`
- **Problem**: the loop narrows `-wal` and `-shm`, but this engine names its shared-memory file `<db>-tshm`. The `-shm` entry therefore never matches, and the file the engine actually creates keeps the process umask (`0644`).
- **Scenario**: a shared host (the audit's own repository database is an example). Any local user can open the WAL index, and — because the file is group/other-writable — can corrupt it while the server runs.
- **Impact**: the "sidecars hold uncommitted rows, so narrow them" intent is only half met: the WAL itself is `0600`, the index is not. Local multi-user exposure and a cheap corruption path.
- **Evidence**: `verified` — `ls -l storage/data/` on the repository database:
  ```
  -rw-------  app.db
  -rw-------  app.db-wal
  -rw-r--r--  app.db-tshm
  ```
  A probe confirmed both files exist immediately after `connect()`, so the loop's timing is fine; only the name is wrong.
- **Fix**: narrow every sidecar the engine may create — `['-wal', '-shm', '-tshm']` — or chmod by prefix scan of `basename(location)`. Trade-off: none; it is the same three `chmod` calls.
- **Confidence**: high
- **Status**: open

### F-05 `streamQuery` spins forever when `chunkSize <= 0`

- **Category**: defect
- **Location**: `src/database/dialect.ts:141-151`
- **Problem**: `for (let index = 0; index < rows.length; index += chunkSize)` with `chunkSize === 0` never advances and yields an empty chunk forever; a negative value walks backwards and does the same.
- **Scenario**: any caller passing `0` (Kysely forwards `stream(chunkSize)` verbatim). The generator yields without awaiting, so the loop is a chain of microtasks that starves the event loop: timers, HTTP handling and signal handlers never run.
- **Impact**: a pinned core and a frozen process, not merely a slow loop — no current caller passes `0`, so this is latent.
- **Evidence**: `verified` — `db.selectFrom(...).stream(0)` did not finish within 30 s and printed nothing, not even a 1-second timer that was set before the loop (killed by `timeout`, exit `124`).
- **Fix**: `const size = Math.max(1, chunkSize)` (or throw on a non-positive size) in `streamQuery`. Trade-off: none.
- **Confidence**: high
- **Status**: open

### F-06 "Open eagerly" holds for the local transport only

- **Category**: contract drift (code comment vs behavior)
- **Location**: `src/database/dialect.ts:236-238` (`openTursoDatabase`), `src/database/adapter.ts:99-105`
- **Problem**: the comment states that "a missing directory, an unwritable file, or a rejected remote URL must fail the layer that acquires the database, not the first request". The remote branch performs no I/O at all: `createClient` only stores configuration.
- **Scenario**: a typo in the host, or a revoked/expired token, boots cleanly; the container reports healthy at the layer level and fails on the first request (503 from the rate limiter or a 500), which is exactly the failure mode the comment promises to avoid. A remote URL without a token is caught earlier, in config — that part is true.
- **Impact**: operability — a misconfigured deployment looks started until real traffic arrives.
- **Evidence**: `verified` — `openTursoDatabase({ kind: 'remote', url: 'libsql://does-not-exist-xyz.invalid', token: … })` returned in **0 ms**, and the first query failed 30 ms later with `fetch failed`.
- **Fix**: either probe the remote once at open (`select 1` through the executor, bounded by F-02's timeout) so the layer fails like the local branch does, or correct the comment and the docs to say the remote transport is verified on first use. The first option is a boot-time network dependency — a real trade-off, see the open question.
- **Confidence**: high
- **Status**: open

### F-07 A stale `insertId` on UPDATE/DELETE; transports disagree on when it is set

- **Category**: correctness (low impact)
- **Location**: `src/database/dialect.ts:27-35` (local), `:55-60` (remote)
- **Problem**: the local executor always returns `insertId: BigInt(lastInsertRowid)` for a non-reader statement, and SQLite keeps the previous rowid on the connection, so an `UPDATE` reports the rowid of an earlier insert. The remote executor omits `insertId` when the server does not send one. Two transports, two shapes.
- **Scenario**: a caller using the raw result (`sql`…`.execute(db)`, or the adapter's `query`/`read`) reads `insertId` after an update and gets a value that belongs to another row. Kysely's typed results (`numUpdatedRows`) hide it, so nothing in the tree reads it today.
- **Impact**: a latent wrong-value bug for the next caller that trusts the field.
- **Evidence**: `verified` — `update probe set id = 43 where id = 42` returned `{"rows":[],"numAffectedRows":"1","insertId":"42"}`.
- **Fix**: set `insertId` only when the statement inserted (`changes === 1 && lastInsertRowid` is not the pre-statement value is not observable, so gate on the SQL prefix or drop the field for the local transport and mirror the remote shape). Simplest: report `insertId` only for `insert` statements; document the field as best-effort.
- **Confidence**: medium (the correct gate depends on how callers may use it)
- **Status**: open

## Optimization opportunities

- **O-01 Statement prepare per query** — measured: ~8 µs per `prepare` on `@tursodatabase/database` against ~5.7 µs of execution for a trivial indexed read; Kysely's driver prepares per `executeQuery` and this dialect keeps that (plan D8). Proposal: none now. Expected benefit: ~2 µs/query at best on a local file, nothing on remote (one round trip dominates). Risk: a shared statement cache across a transaction window. Effort: M. **Verdict: stay parked** (recorded in `.llms/roadmap/parked-unlocks.md`).
- **O-02 `streamQuery` buffers the whole result set** — `dialect.ts:141`. A 100k-row stream allocates the full array before the first chunk, and `rows.slice` copies each chunk. Proposal: use `statement.iterate()` on the local transport and keep the buffered path for remote (no cursor API). Expected benefit: flat memory for a large export; no benefit for the current callers (none stream a large table). Risk: two code paths to keep aligned. Effort: M.
- **O-03 Row mapping on the remote transport** — `Object.fromEntries` per row (`dialect.ts:52`). Proposal: none; the alternative (passing the client's dual-access arrays through) breaks `JSON.stringify` and `Object.keys`, which is how the phase-4 bug appeared. Effort: n/a.
