# Audit: CLI command surface (src/command) against docs/commandline.md

## Executive summary

The command surface was close to the specification: every documented subcommand and flag existed, the
documented exit codes and confirmation rules held, and the `serve` shutdown sequence produced exactly
the documented log lines with exit `0`. Four behaviors diverged from the document, two of them
materially: `migrate:up --to` silently rolled migrations **down** when the target was already applied,
and the documented global flag `--log-level` had no effect at all.

- Findings per severity: critical 0, high 2, medium 2, low 4, info 2.
- All ten findings are fixed by plan-20261025_0002; the remediation table below carries the commit for
  each. The command surface now has a 30-test suite.

## Scope and flow inventory

Audited flows, all driven through `vpr app <command>` (`node --env-file-if-exists=.env.local src/main.ts`):

1. Global flags: `--version`, `--log-level <level>`, `--help` (plus the hidden `--wizard`,
   `--completions`).
2. `serve` — `--auto-migrate`, `--seed`, signal handling, shutdown log sequence, exit code.
3. `healthcheck` — database ping, exit `0`/`1`, 2-second bound.
4. `migrate:up` — `--to <name>`, `--dry-run`.
5. `migrate:down` — `--count`, `--dry-run`, `--force`, non-interactive rule.
6. `migrate:status`.
7. `migrate:reset` — `--up`, `--seed` (requires `--up`), `--dry-run`, `--force`.
8. `migrate:seed` — `--dry-run`.
9. `generate:config` — `--output/-o`, `--overwrite`, `--check`, `--stdout`, `--force`, dotenv refusal.

Trust boundaries: the CLI writes files (`generate:config`), drops and recreates schema (`migrate:reset`,
`migrate:down`), and runs as the container healthcheck. Assumption: `docs/commandline.md` is the
authoritative specification and is not to be edited.

### F-01 `migrate:up --to <applied>` rolls migrations down

- **Category**: correctness (destructive behavior contrary to the document)
- **Location**: `src/command/migrate-up.ts:36` (`migrateTo(target)`), semantics at
  `node_modules/.pnpm/kysely@0.29.7/.../migration/migrator.js:183-192`
- **Problem**: Kysely's `migrateTo(name)` is bidirectional: when the named migration is already
  executed it returns `{ direction: 'Down', step: executed.length - index - 1 }`. The command hands
  the user-supplied `--to` value straight to it, so a command documented as "Apply migrations only up
  to this migration name" performs a rollback when the target is already applied. No confirmation is
  requested, even though the document states destructive commands must ask.
- **Scenario**: database migrated to the latest revision; run `vpr app migrate:up --to 00002_create_identity_table`.
  Expected: nothing to do. Actual: migrations `00004_rate_limits_table` and `00003_create_token_tables`
  are rolled back (their `down` functions drop tables) and the command exits `0`.
- **Impact**: silent data loss on a database that is only ever migrated forward by operators and by
  the container `CMD ... serve --auto-migrate`.
- **Evidence** (verified):
  ```
  $ node src/main.ts migrate:status           # all four executed
  $ node src/main.ts migrate:up --to 00002_create_identity_table
  INFO  Success 00004_rate_limits_table
  INFO  Success 00003_create_token_tables
  EXIT:0
  $ node src/main.ts migrate:status
  INFO  00003_create_token_tables pending
  INFO  00004_rate_limits_table pending
  ```
  `--dry-run` disagrees with the real run: the same invocation with `--dry-run` prints
  `INFO no pending migrations`, because the dry-run branch only filters the pending list upward.
- **Fix**: resolve the target against `MIGRATION_NAMES`/`migrationStatus` and fail with a
  `CliError.UserError` when the target is already executed (`migration is already applied`), keeping
  `migrateTo` for the pending case only. Mirror the same guard in the `--dry-run` branch so both
  paths agree. Trade-off: an operator can no longer use `migrate:up` as an implicit rollback — that
  is what `migrate:down --count` exists for.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-02 `--log-level` global flag is inert

- **Category**: correctness (documented surface that does nothing)
- **Location**: `src/command/cli.ts:27-40`
- **Problem**: `cli.ts` rebuilds the built-in global-flag list with `Object.assign({}, builtIn, {...})`
  for `Wizard`, `Completions` and `LogLevel`. Those copies are new objects, so `Command.run`'s
  identity check `activeFlags.includes(GlobalFlag.LogLevel)` (`node_modules/effect/src/cli/Command.ts:3455`)
  never matches, and the parsed value is never installed as `References.MinimumLogLevel`. The flag
  parses, validates and is then discarded; the level always comes from `LOG_LEVEL` via `LoggerLayer`.
- **Scenario**: `vpr app --log-level error migrate:status` still prints every `INFO` line;
  `--log-level none` likewise. `LOG_LEVEL=Error vpr app migrate:status` correctly prints nothing.
- **Impact**: the document advertises `--log-level <level>` as a global flag; operators who rely on
  it get full-volume logging (including in the Docker image, where the console sink is the only sink).
- **Evidence** (verified): two probes. In-repo probe comparing the current `cli.ts` shape against the
  untouched `GlobalFlag.BuiltIns`:
  ```
  copies + --log-level error   -> INFO info line / ERROR error line
  original + --log-level error -> ERROR error line
  ```
  and against the real binary:
  ```
  $ node src/main.ts --log-level error migrate:status
  INFO 00001_create_platform_tables ...        # unaffected
  ```
- **Fix**: do not clone the built-in flag objects. Either keep `GlobalFlag.BuiltIns` intact and hide
  the flags another way (they are already undocumented in the spec, so leaving `--completions` and
  `--wizard` visible is also an option), or, if hiding is required, hide them through the flag layer
  (`Flag.withHidden` applied to `builtIn.flag`) while preserving the setting object identity. Verify
  by asserting `activeFlags.includes(GlobalFlag.LogLevel)` still holds after the transformation.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-03 Dangling symlink bypasses the real-dotenv refusal and writes `.env`

- **Category**: security (documented guard bypassed)
- **Location**: `src/command/generate-config.ts:82-90` (existence-gated canonical check), `:117` (write)
- **Problem**: the refusal checks the canonical target only when `fs.exists(target)` is true. `exists`
  follows symlinks, so a *dangling* symlink reports `false`; the canonical check is skipped and
  `writeFileString` follows the symlink, creating the real dotenv file the document says is never
  written. The document explicitly promises "The command refuses real `.env` files, including
  through symlinks."
- **Scenario**: in a directory with no `.env`, create `ln -s .env .env.example`, then run
  `vpr app generate:config`. Expected: refusal. Actual: `Wrote .env.example (32 variables)` and a new
  `.env` appears with the generated content.
- **Impact**: writes a file the specification guarantees never to create; combined with
  `--overwrite --force` in a scripted context this becomes an unreviewed write into a real dotenv.
  The same applies to `.env.local`, `.env.production`, etc.
- **Evidence** (verified):
  ```
  $ ln -s .env .env.example
  $ node src/main.ts generate:config
  Wrote .env.example (32 variables)
  $ ls -la   # .env created, .env.example still a symlink to it
  -rw-r--r-- .env
  lrwxr-xr-x .env.example -> .env
  ```
- **Fix**: inspect the path with `lstat` semantics rather than `exists`: read the link target with
  `readlink` and resolve it (or `realPath` the parent directory and join the basename), then apply
  `isRealDotenv` to the resolved final component whether or not the file exists. A symlink whose
  resolved basename is a real dotenv name is refused before the write.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-04 A global flag before `serve` disables the graceful shutdown contract

- **Category**: correctness (documented shutdown contract lost)
- **Location**: `src/main.ts:9` (`const isServe = process.argv[2] === 'serve'`)
- **Problem**: the serve path is selected by the literal second argv token. `docs/commandline.md`
  presents `--version`, `--log-level <level>` and `--help` as *global* flags, so
  `vpr app --log-level info serve` is a documented invocation; there `argv[2]` is `--log-level`, the
  process takes the `NodeRuntime.runMain` branch, and `runMain`'s interrupt-based signal handling
  replaces the command's own shutdown sequence.
- **Scenario**: `vpr app --log-level info serve --auto-migrate`, then `SIGINT`. Expected per the
  document: `shutting down (received SIGINT)` … `application terminated`, exit `0`. Actual: no
  `shutting down` line, no `application terminated` line, exit `130`.
- **Impact**: async finalizers are detached exactly as the code comment in `main.ts` warns; the
  operator loses the log line they use to confirm a clean drain, and supervisors see a non-zero exit.
- **Evidence** (verified):
  ```
  [serve --auto-migrate]              exit=0   shutting down (received SIGINT) / server stopped accepting connections / database connection closed / application terminated
  [--log-level info serve --auto-migrate] exit=130  server stopped accepting connections / database connection closed
  ```
- **Fix**: detect the serve subcommand by scanning `process.argv.slice(2)` for the first non-flag
  token (skipping `--flag=value` / `--flag value` pairs), or better, set a marker in the serve handler
  and branch inside the Effect program instead of on raw argv.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-05 `--log-level` hidden from help; value casing differs from `LOG_LEVEL`

- **Category**: operability / docs drift
- **Location**: `src/command/cli.ts:34` (`Flag.withHidden`)
- **Problem**: the document lists `--log-level <level>` under "Global flags", but `--help` shows only
  `--help` and `--version`. Additionally the flag accepts lowercase only (`debug`), while the
  configuration variable `LOG_LEVEL` accepts capitalized values (`Debug`) — the same vocabulary in two
  casings.
- **Scenario**: `vpr app --log-level Debug migrate:status` fails with
  `Invalid value for flag --log-level: "Debug". Expected: "all" | "trace" | ...`; `vpr app --help`
  never mentions the flag.
- **Impact**: discoverability and a papercut for anyone who copies the `LOG_LEVEL` value.
- **Evidence** (verified): `--help` output lists only `--help`/`--version`; `--log-level Debug` exits
  `1` with `CliError.InvalidValue`.
- **Fix**: decide the contract. Recommended: make the flag visible (drop the hiding for `LogLevel`
  only, which also fixes F-02) and accept case-insensitively, mapping to `LogLevel.values`.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-06 "Second signal exits immediately" holds only for the same signal

- **Category**: correctness (documented behavior, narrow)
- **Location**: `src/kernel/graceful.ts:8-16`
- **Problem**: `awaitShutdownSignal` registers `process.once` for `SIGINT` and `SIGTERM`. After the
  first signal fires, only that signal's listener is removed by `once`; the other remains registered
  and its `resume` is a no-op, so a second signal of the *other* type does not terminate the process —
  the drain runs to completion. The document says "a second signal exits immediately."
- **Scenario**: `SIGINT` then `SIGTERM` during the drain window: the process keeps draining for the
  full duration and exits `0`. `SIGINT` then `SIGINT` does exit immediately (Node's default, since the
  listener is gone).
- **Impact**: an operator cannot force-exit a stuck drain with the other signal.
- **Evidence** (verified, harness driving `awaitShutdownSignal` with a 6 s drain):
  ```
  SIGINT              -> code=0 signal=null after=6514ms
  SIGINT+SIGINT       -> code=null signal=SIGINT after=1208ms
  SIGINT+SIGTERM      -> code=0 signal=null after=6509ms
  ```
- **Fix**: after the first signal, replace both listeners with a force-exit handler
  (`process.exit(130)` on the second signal) instead of leaving the other `once` listener in place.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-07 `--force` without `--overwrite` is an undocumented error

- **Category**: operability
- **Location**: `src/command/generate-config.ts:76`
- **Problem**: the document describes `--force` only as "Skip the confirmation prompt of
  `--overwrite`". The implementation rejects `--force` on its own:
  `ERROR --force only applies together with --overwrite`, exit `1`. `--stdout --force` is accepted
  (the stdout branch returns before the validation), so the rule is also inconsistent.
- **Scenario**: `vpr app generate:config --force` on a fresh directory exits `1` instead of writing.
- **Impact**: a stricter-than-documented CLI contract; scripts written from the document fail.
- **Evidence** (verified): `generate:config --force` → exit `1`, message above;
  `generate:config --stdout --force` → exit `0`, content printed.
- **Fix**: either accept `--force` alone as a no-op (document-consistent) or add the constraint to the
  document; in both cases move the validation ahead of the `--stdout` early return.
- **Confidence**: high
- **Status**: fixed (plan-20261025_0002)

### F-08 Redis close logs one line, the document promises the database's two

- **Category**: correctness (docs drift)
- **Location**: `src/kernel/cache.ts:132`, `src/middleware/rate-limit.ts:126`
- **Problem**: the document says the database logs `closing database connection` **and**
  `database connection closed`, and that "a Redis-backed rate-limit or cache store logs its close the
  same way". The Redis stores log only `closing redis cache connection` /
  `closing redis rate-limit connection`; there is no `… closed` counterpart.
- **Scenario**: `serve` with `REDIS_ENABLE=true`, then `SIGINT`: the database reports two lines, the
  Redis store one.
- **Impact**: log-based shutdown assertions written from the document will not match.
- **Evidence**: unverified at runtime (no Redis instance available); established by code trace —
  `Effect.addFinalizer(() => Effect.logInfo('closing redis cache connection'))` with the client closed
  by the enclosing scope.
- **Fix**: add the `… closed` log after the client's close completes, or soften the document.
- **Confidence**: medium
- **Status**: fixed (plan-20261025_0002)

### F-09 Help omits the documented default; `--stdout` silently overrides `--check`

- **Category**: docs drift
- **Location**: `src/command/generate-config.ts:24` (description), `:79` (`stdout` early return)
- **Problem**: the document gives `--output, -o` the description "File to write (default: .env.example;
  never a real .env file)"; `--help` prints `File to write (never a real .env file)` — the default is
  dropped even though the code takes it from the same argument. Separately, `--stdout` returns before
  the `--check`, `--force` and refusal checks, so `generate:config --stdout --check` silently ignores

- **Scenario**: `vpr app generate:config --stdout --check` in a stale directory prints the file and

- **Evidence** (verified): `generate:config --help` output; `--stdout --check` exits `0` on a stale tree.
- **Fix**: include the default in the flag description; reject `--stdout` combined with `--check`.
- **Confidence**: high

## Decisions log

- **D1 (plan-20261025_0002):** the global flags stay the canonical `GlobalFlag` objects — `builtIns` is
  `[Help, Version, LogLevel]`, no clone — so `Command.run`'s identity checks install the level.
  `--wizard` and `--completions` are removed; the document never named them.
- **D2:** the `--log-level` value is lowercased in argv before the run, matching what `LOG_LEVEL` already
  accepts capitalized.
- **D3:** `serve` is detected by parsing argv (`subcommandOf`), not by `argv[2]`.
- **D4:** `migrate:up --to` is forward-only; an applied target is an error.
- **D5:** `generate:config` resolves the link chain (`readLink`, bounded) before refusing, so a dangling
  or chained symlink to a dotenv file is caught; `--force` alone is a no-op and `--stdout --check` is
  rejected.
- **D6:** the shutdown path owns both signals (second one exits `128 + signum`) and the Redis scopes, so
  each Redis store logs `closing …` and `… closed` around the close it controls.
