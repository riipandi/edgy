# Architecture

Per-area reasoning and decision records. Read the section before changing that area.

## HTTP layer

**Decision: h3 plugins as the only composition primitive** (2026-10). Global middleware, route groups, and per-route behaviour are all `H3Plugin`s, composed in one place (`src/app.ts` → `createApp`). `defineRouteGroup` (`src/kernel/http/router.ts`) gives each group an isolated router mounted at a prefix; `mount` merges routes into the parent rou3 trie, so there is one lookup and no nested fetch hop. Consequence: app-level config/hooks do not inherit into mounted groups — that is accepted, shared behaviour goes in global middleware. Rejected: flat route tables (prefix boilerplate, group-wide middleware impossible) and nested `H3.fetch` delegation (extra hop, no trie merge).

**Decision: `runEffect` bridge on a captured service context, errors render themselves** (2026-10-15, replaces the `AppRuntime` singleton). Handlers stay thin and delegate to `runEffect(event, effect)` (`src/kernel/http/responder.ts`), which runs the program with `Effect.runPromiseExitWith(services)`, opens a span per request, annotates logs with the request id, and maps `AppError` tags to statuses with an exhaustive switch. The service context is captured once in `serveHttp` (`makeHttpRuntime`) and handed to h3 through a plugin. Consequence: one set of layers per process, no manual `dispose`, and `createApp` can be built against any `HttpRuntime` in a test. Rejected: a module-level `ManagedRuntime` (second database connection and logger, global state, import-order coupling) and per-handler try/catch mapping (drift).

**Decision: validation inside the Effect program** (2026-10-15). `decode(schema)(input)` (`src/kernel/http/decode.ts`) fails with `ValidationError`, so the 400 body and the issue list come from one place. Before, h3's `readValidatedBody` threw its own error and `ValidationError` was never constructed.

**Decision: Effect Schema as the single contract, derived per resource** (2026-10-15). `src/modules/user/user_schema.ts` declares the entity once and derives request, response and Kysely table types from it, so a column is declared in one place. Responses are encoded through the schema in `runEffect`: this is a leak guard (an undeclared column never leaves the process) and keeps the encoded wire type honest. Consequence: one small CPU cost per response, acceptable for flat structs. Rejected: hand-written interfaces per layer (drift), a monolithic validator module (grows with every endpoint), and decoding every database row (cost without a transformation to justify it). `kernel/http/` holds only code that does not grow with the endpoint count; contracts belong to the domain, so they stay in `schemas/`.

**Decision: request lifecycle is owned by `runEffect`** (2026-10-15). It forwards the request `AbortSignal` (a disconnected client interrupts the fiber), bounds the program with `REQUEST_TIMEOUT`, and answers an interrupt with 499 without logging an error. Verified in-process with an aborted `Request`; whether srvx fires the signal on a real socket close has not been exercised (port binding is blocked in the sandbox). Rejected: leaving abandoned requests to run to completion (wasted database time under load).

**Decision: one error shape for everything** (2026-10-15). `renderHTTPError` renders h3-originated errors in the same error envelope as `runEffect` (see the envelope decision below), so clients parse one format. Cost: the hook must copy `errHeaders` by hand, and not-found needs a throwing catch-all because of how h3's `onResponse` middleware materialises the not-found marker (details in `rules.md`). Rejected: leaving h3's `{status, message}` body (two formats) and a custom 404 handler per group (groups do not inherit app hooks).

**Decision: one response envelope, pagination built in from the start** (2026-10-15). Every `/api` response is `{ status, data | error, metadata, links? }` (`.llms/api-response.md`). Handlers return plain values; `defineHandler` encodes them into `data` and `runEffect` owns the envelope, so no endpoint can forget it. Collections go through `definePagedHandler`, which turns a `Page<A>` into pagination metadata and links, and `sort_by` is validated against a per-resource allow-list. Cost: two small kernel modules (`envelope.ts`, `pagination.ts`) and snake_case wire names beside camelCase code. Chosen now because retrofitting an envelope changes every client, and the pagination kit is cheaper to write once than per endpoint. `limit=-1` (all records) follows the spec and is the one unbounded path. Rejected: metadata without links (the spec is HATEOAS-first), a cursor scheme (the spec's `page`/`limit` contract is offset-based), and validating the envelope with a schema (only `data` crosses a trust boundary; trusted code builds the rest).

**Decision: `defineHandler` over per-handler plumbing** (2026-10-15). The four-overload signature gives `run` exactly the declared inputs without casts; the implementation signature is loose on purpose. Consequence: adding an endpoint is a contract plus one expression. Rejected: a request-scoped `HttpEvent` service (hidden dependency, async body read inside the Effect) and a single options type with optional params/body (leaks `undefined` into every `run`).

**Decision: Effect owns shutdown; drain on requests, not connections** (2026-10-15). srvx's signal handler is off, so finalizer order is deterministic: server drain, database, log flush. A first version awaited `server.close()` under `SHUTDOWN_TIMEOUT` and, against a live socket, always hit the timeout when any connection had never completed a request (reproduced with an idle socket and with a half-sent header: 4 s of a 4 s timeout). Counting in-flight requests (`inflight.ts`) fixed it: idle and half-header sockets now exit in ~10 ms, and a slow request that finishes during the drain is answered before exit. Rejected: `closeIdleConnections()` (does not cover never-started sockets) and `close(true)` straight away (cuts off live requests).

**Decision: services as `Context.Service` classes with `static layer`** (2026-10-15). `DatabaseService` → `UserRepository` → `UserService`, composed with `Layer.provideMerge` in `src/services.ts` (portable) and `src/layers.ts` (Node: adds the configured database) (`AppLayer`). Each level stays visible, so `migrate:*` needs only `DatabaseService` while `serve` takes the full stack. The user cache is private to `UserService.layer` rather than a separate service nobody else uses. Rejected: free functions reading `DatabaseService` from context (no seam to substitute the repository in a test).

**Decision: TypeID for request ids** (2026-10). `typeid('req')` (UUIDv7-based, sortable, prefixed) via `requestId` middleware; inbound `x-request-id` <= 128 chars is echoed for gateway tracing. Written to `res.headers` **and** `res.errHeaders` because h3 merges only the latter into error responses. Library: `typeid-js`.

**Decision: read-through cache only for hot single-row reads** (2026-10). `UserService.get` goes through an Effect `Cache` (capacity 256, TTL 30s, resolver-backed, `src/modules/user/user_service.ts`); `list` and writes go straight to the repository. Consequence: reads may be up to 30s stale — acceptable for a reference server; a real deployment would revisit per entity.

**Decision: an error owns its HTTP mapping** (2026-10-15). `AppError` is an interface (`status`, `clientMessage`, `detail`) that each error class implements, and `runEffect` only renders it. Before, a closed union plus a `toFailure` switch (with `satisfies never`) meant every new domain error edited `kernel/http/responder.ts`. We gave up the compile-time exhaustiveness of that switch; what replaces it is that an error without those members does not satisfy `E extends AppError`. Rejected: keeping the switch and widening the union per module (the kernel would import every module's errors).

**Decision: `HttpEnv` assembled by declaration merging** (2026-10-15). `HttpServices` is an empty interface in `kernel/http/runtime.ts`; each service adds one property next to its own definition and `HttpEnv` is the union of the values. This is the same technique the `Database` table registry already uses, and it removes the one place where the kernel named domain services. Rejected: threading `R` through `HttpRuntime`, `defineHandler` and `runEffect` (every signature in the kernel grows a parameter for a list that only the composition root knows).

**Decision: vertical modules** (2026-10-15). `src/modules/<resource>/` holds schema, repo, service, handler, routes and tests together; `routes/route.ts` and `services.ts` are the only files that list modules. Type-first folders (`handler/`, `service/`, `repository/`) made one resource touch four directories and would have grown linearly with every resource. The file suffixes survive, so grep-by-role still works.

**Decision: two targets, one application** (2026-10-15). Node.js (`node:sqlite`) and Cloudflare Workers (D1) share `createApp`, the modules and the configuration; they differ in composition root (`main.ts` + `layers.ts` vs `worker.ts`), logger sink and database layer. `DATABASE_DRIVER` chooses on Node; a Worker always uses D1. The seam is `DatabaseService`: both drivers are built by `makeDatabaseService`, so repositories never learn which one they run on. Costs: D1 has no transactions, the D1 introspector cannot read columns, rate-limit state is per isolate, and the Worker's import graph must stay free of Node-only modules (checked by running `pnpm preview`, not by the compiler). Rejected: a Node-only server with Workers as a later port (the seams would have been cut around `node:sqlite`), and `@cloudflare/workers-types` (its globals collide with the Node typings the rest of the project compiles against; the dialect declares the three D1 methods it uses).

**Decision: the Worker is built by our own builder, with a preset** (2026-10-15). `--target=workers` reuses the Rolldown pipeline and replaces the fields that only make sense for a Node server (`WORKERS_PRESET`) instead of forking a second builder. `deploy` ships the file we built with `--no-bundle`, and `preview` runs that same file built the same way (both with `--minify`), so what is tested is what runs; `watch:worker` keeps wrangler's own bundling of the source for a fast edit loop. The scripts are split by target (`build:node`, `build:worker`, `watch:node`, `watch:worker`) rather than one `build` with a flag, so each is greppable and `preview`/`deploy` cannot build the wrong target. Rejected: letting wrangler always bundle `src/worker.ts` (a second bundler decides which package builds and conditions you ship, with no `build:worker` equivalent to inspect) and code splitting for Workers (extra modules need wrangler rules to be uploaded).

**Decision: OpenTelemetry over HTTP/JSON, built from Effect's own exporters** (2026-10-15). Traces and metrics go out through `OtlpTracer`/`OtlpMetrics`, logs through `OtlpLogger` as one more sink, all behind one `Flusher` and one `TelemetryRuntimeLayer` that each composition root builds once. Chosen over a hand-written exporter or the OpenTelemetry JS SDK because the instrumentation already existed (`Effect.fn`, `withSpan`, `Metric`) and Effect's exporters are non-blocking, fall silent for 60 s after a failure and need only `fetch`, so the same code runs on Node and Workers. HTTP, not gRPC: no native or protobuf dependency, and every collector accepts it. Config uses the standard `OTEL_*` names. Measured on a laptop: about 7% throughput at full sampling (191 000 spans ingested for 100 000 requests, none lost), no measurable cost when off; `OTEL_TRACES_SAMPLE_RATIO` is there for the cases where that matters. Rejected: the OpenTelemetry SDK (a second span model next to Effect's), and exporting inside the request (it would put the collector on the latency path).

**Decision: client errors are answers, not failed spans** (2026-10-15). `runEffect` returns a 4xx as a value (`Outcome.refused`) from inside the span, so a 404 or a validation error ends the server span `Ok` with its status code, as OpenTelemetry asks, and error dashboards show only 5xx and defects. The inner service/repository spans still show the failing operation. Cost: one extra union in `runEffect`. Rejected: leaving them as failures (every missing user would be an error span).

**Decision: one place reports failures: `ErrorReporter`** (2026-10-15). Errors declare themselves reportable (`ErrorReporter.ignore` below 500), `runEffect` wraps the program in `withErrorReporting`, and `error_reporter.ts` holds the reporters. The default logs through the failing fiber's own logger, so it reaches console, file and OTLP alike with the request id; a Sentry-style reporter is one more entry in the list. It replaced a `tapCause` in `runEffect` that decided what was reportable by status in two places.

**Decision: refuse early under overload** (2026-10-15). `MAX_IN_FLIGHT` (1024) answers `503` + `Retry-After` before any work when too many requests are in flight. Without it a burst queues behind one event loop and every request slows down together until it times out; with it the excess fails fast and admitted requests keep their latency. It reuses the counter shutdown already needs, so the cost is one integer comparison. `/health` and `/metrics` are exempt so a busy instance is not pulled by its own balancer. Rejected: queueing with a bound (it adds latency before failing), and per-route limits (no data yet on which routes need them).

**Decision: retry reads on D1, never writes** (2026-10-15). `DatabaseService.read` repeats a transient failure twice with jittered backoff on D1, where a read crosses a network; elsewhere it is `query`. Writes are not idempotent, so they have no such entry point, and a deterministic failure is never repeated. The split is in the API (`read` vs `query`), not a flag, so a repository cannot retry a write by accident. Rejected: retrying inside `query` by statement type (Kysely hides it, and `insert … returning` looks like a read).

**Decision: a shared rate limit that fails open** (2026-10-15). `RATE_LIMIT_STORE=redis` counts through Effect's `RateLimiter` over Redis/Valkey, so the limit is global; the default stays an in-process counter because it is faster and needs nothing. The shared check has a 250 ms budget and a 10 s cooldown after a failure: a limiter must not turn a Redis outage into an API outage or into a 5-second delay per request (the Redis client waits about that long before giving up, which the first version did). Node only; Workers have no Redis store. Rejected: failing closed (a store outage would take the API down), and replacing the in-memory counter with Effect's for both (an Effect run per request costs more than the integer map it replaces).

**Decision: ClickStack all-in-one for development** (2026-10-15). `compose.yaml` runs HyperDX, ClickHouse and the collector as one container, with a one-shot that registers the development account and a fixed ingestion key, so telemetry works on the first `pnpm compose:up`. All-in-one is a development choice; production runs the pieces separately. Rejected: the multi-service ClickStack (more files and ports for no development benefit) and requiring the developer to create an account and copy a key from the UI.

**Decision: D1 dialect adapted from `kysely-d1`, with its own introspector** (2026-10-15). The driver and connection follow the MIT-licensed `kysely-d1`; the introspector is replaced because Kysely's SQLite one calls `pragma_table_info`, which D1 rejects, and the migrator introspects to find its bookkeeping tables. Migrations therefore run through the same Kysely migrator on both drivers, one migration history, instead of a second SQL-file pipeline for `wrangler d1 migrations`.

**Decision: security baseline without inventing policy** (2026-10-15). Fixed security headers, a JSON-only body (415), an in-memory fixed-window rate limiter (off by default, per instance, on `/api` only) and `/metrics` behind a flag. Authentication is deliberately absent: it needs a product rule (who may call what) that does not exist. The rate limiter is off by default because a default-on limit would silently throttle benchmarks and local scripts; production turns it on. Rejected: a shared store for a global quota (new infrastructure for a limit the platform's own WAF does better).

**Decision: cache writes invalidate their keys** (2026-10-15). A lookup of a missing id is cached as `undefined`, so `UserService.create` invalidates the new id's entry; otherwise the user just created would answer 404 until the TTL expired. Any new write path owns the invalidation of the keys it touches.

**Decision: Vitest, in-process, real stack** (2026-10-15). Tests build the real application over an in-memory database (`makeTestApp`) and call `app.fetch`, so they cover middleware order, envelope, pagination and migrations without a port. The D1 dialect is tested against a fake binding backed by `node:sqlite` that reproduces the two behaviours that matter (result shape, message-only constraint errors). Rejected: mocking repositories (the bugs found so far lived in the seams between layers).

## Configuration

**Decision: Effect `Config` schema, fail fast at layer build** (2026-10). All env parsing lives in `src/kernel/config/` (`ConfigLayer` in `service.ts`, one file per section: `server`, `database`, `logging`, `cors`; each variable is declared once with a field helper, which builds the parser and the documentation together; `AppConfig` is nested by section and inferred, not hand-written; `config:generate` derives `.env.example` from the same declarations, and a test fails when the file is stale); present-but-invalid values fail with a typed `ConfigError` while the layer builds, so a bad `PORT` or a `CORS_CREDENTIALS=true` + wildcard-origins combination dies at startup, never mid-request. Rejected: `process.env` reads at call sites (untestable, no single validation point). Consumers depend on the `ConfigService` context tag, not the layer.

## Observability

**Decision: batched, buffered stdout logger** (2026-10-15). `src/observer/logger.ts` builds the sink with `Logger.batched`: formatting stays on the calling fiber, the line goes into memory, and one detached fiber writes the whole buffer per `LOG_FLUSH_INTERVAL` (default 250 ms). Why: Effect's console loggers write synchronously per line, which puts terminal and pipe latency on the request path. Consequence: a hard crash can drop up to one window of lines; graceful shutdown drains the buffer in the scope finalizer. Formats are `pretty` (own renderer over `Logger.formatStructured`, colours only on a TTY and without `NO_COLOR`) and `json`. Rejected: `Logger.consolePretty` (synchronous, cannot be batched) and a worker-thread sink (extra moving part, no benefit at this volume).

**Decision: log transports are selected by config, file rotation is ours** (2026-10-15). `LOG_TRANSPORT=console,file` chooses which sinks `Logger.layer` receives: our batched stdout sink and a JSON-lines file sink. Effect v4 ships `Logger.toFile` but no rotation, so `src/observer/log_file.ts` writes through the `FileSystem` service itself: time-based periods (hourly, daily, weekly, monthly; default daily) named `edgy_YYYYMMDD_hh.jsonl`-style with underscores, count-based retention (`LOG_FILE_MAX_FILES`), UTC throughout. Chosen with the owner over size-based and size-plus-time rotation, because a file per period is findable by date and the name never changes mid-period; the cost is that a busy period can grow a file without a size bound, which `LOG_ROTATION=hourly` and retention keep in check. File output is always JSON, because ANSI colours and aligned columns make a file harder for tools to read; the console keeps `LOG_FORMAT`. A bad path fails startup rather than dropping logs. Rejected: a third-party rotating stream (a runtime dependency, and a layer outside Effect's scope and flush ordering), compression (more CPU and a `zcat` between a person and their logs), and `copytruncate`-style external rotation as the only option (it depends on the host).

**Decision: one observer plugin for request logs and metrics** (2026-10-15). `httpObserver` reads the final status from `onResponse`/`onError`, so metrics also count 404s and h3-level errors, which the old per-`runEffect` counter missed. `src/observer/` is where tracing exporters and further instruments land; nothing is exported yet.

## Database

**Decision: `node:sqlite` + custom Kysely dialect** (2026-10). Zero native addons — the SEA binary and the bundle carry no compiled `better-sqlite3`. `src/database/dialect/` implements the Kysely dialect/driver/connection over `DatabaseSync`, with a mutex for serialisation. Consequence: single-process SQLite only; scaling out means swapping the dialect. Rejected: `better-sqlite3` (native addon breaks the no-`node_modules` runtime story).

**Decision: static migration registry over file scanning** (2026-10). Migrations register in `src/database/migrations/index.ts` instead of `FileMigrationProvider`'s runtime `readdir`. Why: the Rolldown bundle inlines every migration (no `migrations/` folder to ship), and static imports cannot be tree-shaken away. Consequence: two places to touch per migration (file + registry) — contract in `rules.md`. Kysely's `Migrator` still owns the `kysely_migration` bookkeeping.

**Decision: thin CLI wrappers over migrator capabilities** (2026-10-15). `migrate:up/down/status/reset` map to `Migrator.migrateToLatest/migrateTo/getMigrations`; `migrateDown(steps)` is built on `migrateTo` because Kysely's native `migrateDown` is single-step. `migrate:validate` and `migrate:create` were **skipped on purpose**: Kysely validates migration ordering internally, and file scaffolding is not a runtime capability. Seeders are a separate named registry (`src/database/seeder.ts`) with idempotency as a contract, not a Kysely concern.

## Build pipeline

**Decision: own Rolldown pipeline, independent of `src/`** (2026-10). `builder/` bundles the server (ESM + chunks, per-package splitting), keeps native packages external and traces them, emits a minimal `package.json`, and optionally produces a single executable via Node SEA + postject. Consequence: two build modes share one config surface (`builder/builder.config.ts`, every option defaulted). Rejected: adopting Nitro/tsup (heavier, less control over SEA injection).

## Testing (gap record)

**No test suite** (2026-10-15). `package.json` `test` is a placeholder. Validation currently is `tsc -b --noEmit` + `oxfmt`/`oxlint` + manual runtime probes. The composition root (`AppRuntime`), `runEffect` mapping, and the migrator commands are the first candidates when tests arrive — they are exercised only by probes today. Record: `index.md` recap; trigger to act: first test-framework decision.
