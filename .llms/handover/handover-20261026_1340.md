## What changed and why it matters

- **Phase 3 was left uncommitted with three defects** when this session picked the plan back up:
  a duplicate `const ssrRouter` declaration in `serve.ts` (syntax error), `Layer.mergeAll` called
  through `.pipe()` as if it were a dual function (it is not — `node_modules/effect/dist/Layer.d.ts:1434`
  is a plain variadic `mergeAll(...layers)`, so `self.pipe(Layer.mergeAll(x))` tried to call the
  result of `Layer.mergeAll(x)` as a function), and `kernel/runtime.ts` exporting its runtime as
  `export default` instead of the repo's named-export convention (`export default` is used only by
  Solid route/component files — verified by grep). All three are fixed; `httpStack` in
  `kernel/http/stack.ts` is now generic (`<Layers extends ReadonlyArray<Layer.Layer<never, any, any>>>`)
  instead of annotated `Layer.Layer<any, any, any>`, which was also the root cause of two
  `exactOptionalPropertyTypes` type errors `vpr check` caught at the call sites.
- **The module contract is now three exports per module `module.ts`**: `layer` (self-wired),
  the `HttpApiGroup`, and the handlers factory — `modules/identity/module.ts` is the only file the
  kernel imports from that package. `kernel/layers.ts` merges module layers directly; there is no
  file to edit per new module beyond the module's own `module.ts`.
- **`kernel/runtime.ts` is the one owner of the `ManagedRuntime`** (`applicationRuntime`,
  `applicationContext`, `disposeUserRuntime`/`disposeUserRuntimeEffect`); `user_ssr.ts` only
  bridges to it through `AsyncLocalStorage`.
- **`kernel/http/stack.ts` is the one middleware order** both `serve.ts` and the dev `apiHandler`
  consume, with their own deltas (SSR router + dispose finalizer vs. `Layer.succeedContext`).
