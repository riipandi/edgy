## What changed and why it matters

- **`kernel/registry.ts` is the single module-registration file.** It builds `api`
  (`HttpApi.make(...).add(...)`), `moduleServiceLayer` (consumed by `kernel/layers.ts`), and
  `moduleHandlerLayer` (consumed by `kernel/http/api.ts`'s `apiRoutes`). Neither kernel file
  imports a feature module directly anymore. A declarative registry (modules export a descriptor
  an iterator reads) was rejected twice now — this plan's D1 and the prior plan's D1 — because
  `HttpApi.add<const A extends NonEmptyReadonlyArray<...>>(...groups: A)` needs a tuple-typed
  argument list; a runtime array of module groups does not type-check without a cast. Revisit only
  once three or more feature modules exist and the diff in `registry.ts` per module is proven
  repetitive.
- **Every `/api/*` response except `/api/health` is the envelope.** `kernel/http/envelope.ts`'s
  `SuccessEnvelope`/`ErrorEnvelope` wrap each endpoint's declared schema — chosen schema-level
  over a transport-rewrite middleware specifically so `/api/openapi.json` stays accurate; the
  final probe confirmed the generated document does contain `metadata`/`status_code`/`retryable`,
  not bare domain schemas. Six generic, reusable error classes (`kernel/http/errors.ts`) replace
  Effect's `HttpApiError.*` built-ins and every per-domain error class a module would otherwise
  need; a module supplies its own `code`/`details`. `kernel/http/respond.ts`'s
  `respondSuccess`/`respondError` assemble `request_id`/`trace_id`/`rate_limit`/`cache` from
  ambient state so a handler never builds that by hand; `errorBody` is the plain-value sibling
  `error-response.ts` and `apiFallback` use for the same shape without failing an Effect.
- **`listUsers` has real keyset pagination**, not a stub: `limit` (1-100, default 20), an opaque
  base64url `cursor` over `{sortValue, id}`, `sort_by`/`sort_order`. One extra row is fetched past
  `limit` to detect `has_more` without a second query. `DELETE /api/users/:id` moved from `204` to
  `200` with an empty envelope — a true `204` cannot carry the envelope's JSON body, and this was
  judged a natural consequence of the owner's schema-level-envelope choice, not a separate decision
  needing its own sign-off.
- **Two defects found and fixed while finishing phase 6, both worth knowing before touching this
  code again:**
  1. `SuccessEnvelope`/`ErrorEnvelope`'s generic was originally bound to `Schema.Schema<A>`
     (decoded-type-only). That silently collapsed the whole composed `ApplicationLayer`'s
     requirements to `unknown` instead of `never` everywhere it is consumed — `main.ts`, `cli.ts`,
     `tests/kernel/http.test.ts` — with no error at the factory or the endpoint, only a cryptic
     "`unknown` is not assignable to `never`" several layers away. Found by bisecting the whole
     identity-module diff down to one minimal endpoint declaration (a `git worktree` against the
     pre-phase-6 commit confirmed the baseline was clean, then files were swapped in one at a time).
     Fixed by binding to `Schema.Top`. Recorded as a trap in `rules.md` for anyone writing a
     similar generic schema-wrapping helper later.
  2. `user_fn.ts` (the client-side `fetch` bridge Solid components call — a different file from
     the route/handler pair, easy to miss when scoping "the identity module") still expected the
     old bare-array/bare-object bodies. The unit suite mocks `fetch` by hand, so it kept passing
     against the stale shape; only `vpr e2e` caught it, as an "Uncaught Client Exception" on
     hydration rather than a clear shape-mismatch error. Fixed by unwrapping `{data}` there and
     checking `DELETE`'s new `200`. Recorded as a trap: a wire-contract change must enumerate
     every consumer, not just the endpoint's own files.
- **Health stays outside the envelope (tentative).** `/api/health` keeps its `{status, details}`
  shape; the owner has not objected, but this was a judgment call recorded with its rationale, not
  a verified requirement — revisit if it stops holding up.
