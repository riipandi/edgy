# Rules

Contracts, how-to-change recipes, traps. Read the section a change touches before touching it.

## HTTP contracts

- **Every API response is an envelope** (spec: `.llms/api-response.md`; types and builders in `src/kernel/http/envelope.ts`). Success: `{ status: 'success', data, metadata: { status_code, request_id, …pagination }, links? }`. Error: `{ status: 'error', message, error?, metadata: { status_code, request_id } }`. Field names are snake_case because they are the wire contract. `message` is set only by `defineMessageHandler` (a static string, no `data`; `GET /health` uses it), `rate_limit` is filled by the rate limiter when it is on, and `trace_id` is in the type but nothing fills it yet (tracing has no exporter). Only `GET /` (plain text `All is well`), `/metrics` (Prometheus text) and `/.well-known/*` (RFC-defined formats) answer outside the envelope.
- **An error renders itself.** Every application error implements `AppError` (`src/kernel/errors.ts`): `status`, `clientMessage` and an optional `detail`. `runEffect` only renders them: `NotFound` 404 `<resource> not found` with `error: { id }`, `ValidationError` 400 with the issue list, `Conflict` 409, `RequestTimeout` 504, `DatabaseError` 500 `Database error`; a defect is 500 `Internal server error`, an interrupted fiber (client hung up) 499. `clientMessage` and `detail` reach the client, so they never carry internals. A failure with `status >= 500`, and any defect, is logged with its cause; expected failures (< 500) and interruptions are not (the observer still logs the request line at the level of its status). A new error is a class with those three members in `errors.ts` (or in its module); the kernel needs no edit. The cost: nothing forces every error to exist in a closed union any more, so the type check is `E extends AppError` on the handler.
- **Errors raised by h3 use the same error envelope.** `createApp` sets `onError: renderHTTPError` (`src/kernel/http/errors.ts`); it copies `event.res.errHeaders` into the `Response` it builds, because h3 does not merge them into a response returned from the hook. Unhandled exceptions are rendered as `Internal server error`. Unknown paths are answered by the `notFoundRoutes` catch-all (`src/routes/route.ts`), which **throws** an `HTTPError`: h3's `onResponse` middleware (the observer uses it) converts h3's internal not-found marker with a default config, bypassing `onError`. Keep that catch-all registered last.
- **Handlers accept `Effect<A, E extends AppError, HttpEnv>`.** `AppError` is an interface, not a union: a module adds its own errors without touching `kernel/`.
- **One runtime, no singleton.** `serveHttp` captures the command's service context into an `HttpRuntime` (`src/kernel/http/runtime.ts`) and `createApp` attaches it to every request through the `provideRuntime` plugin; `runEffect` and the observer read it with `runtimeOf(event)`. Never build a second `ManagedRuntime` on Node — it would open a second database connection and logger. (The Worker entry builds exactly one per isolate, and tests build one per test app.) `HttpEnv` is not a hand-kept list: it is the union of `HttpServices`, an empty interface in `runtime.ts` that each service augments next to its own definition (`declare module '../../kernel/http/runtime.ts' { interface HttpServices { user: UserService } }`), so the kernel never names a domain service. A service a handler uses must declare itself there.
- **Endpoints are declared with `defineHandler`** (`src/kernel/http/handler.ts`): `{ params?, body?, query?, response, status?, run }`. The helper reads the body, decodes router params, body and query, runs the program, encodes the value through `response` into the envelope's `data`; `run` receives exactly the inputs the spec declared (an undeclared one is `undefined`). Handlers do not call `runEffect`, `readBody`, `getQuery` or `decode` themselves.
- **Acknowledgements use `defineMessageHandler`** (`{ message, run }`): the envelope carries `message` and no `data`; `run` only has to succeed.
- **Collections use `definePagedHandler` and the pagination kit.** `run` returns a `Page<A>` (`src/kernel/pagination.ts`); the spec gives `items` (the schema of one element) instead of `response`. The query comes from `paginationQuery(sortable)` (`src/kernel/http/pagination.ts`): `page`, `limit`, `sort_by`, `sort_order`, where `sort_by` is an allow-list typed as a union, so a column name from the client never reaches a query unchecked. `toPageRequest(query, { sortBy })` applies defaults (`limit` 20, cap 100, `page` 1) and yields the `PageRequest` a repository takes (`offset` precomputed). `-1` for `page` or `limit` means every record in one page (`limit: null` in the metadata, only a `self` link); it is the only way past the cap, so reconsider it before exposing a large table. Repositories return `makePage(items, request, total)` and add `id` as the last `orderBy` so ties never straddle a page boundary. Metadata (`page`, `limit`, `total_pages`, `total_items`, 1-based inclusive `first_item_index`/`last_item_index`, `null` past the end) and relative `self`/`first`/`prev`/`next`/`last` links that keep the other query parameters are derived in one place (`paginationMeta`, `paginationLinks`). The total rides along as a scalar subquery in the same statement (one snapshot, one round trip); only an empty page past the first needs a separate count.
- **Request lifecycle limits.** `runEffect` passes `event.req.signal` to the runtime, so a client that disconnects interrupts the fiber; it wraps the program in `Effect.timeoutOrElse` with `REQUEST_TIMEOUT` (→ `RequestTimeout`, 504); `bodyLimit(BODY_LIMIT)` rejects oversized bodies with 413 as they are read. Field bounds live in the schemas (`email` ≤ 254, `name` ≤ 200).
- **Health**: `GET /` is a static plain-text liveness check (`All is well`) that never touches the database. `GET /health` stays at the root, outside `/api`, is readiness, and answers 200 only if `DatabaseService.ping` succeeds (otherwise 500 `Database error`). Once shutdown begins it answers `503` (`unlessDraining`, `HttpRuntime.beginDrain`); that 503 is logged as a warning, not an error. `GET /metrics` exists only with `METRICS_ENABLED`, is plain Prometheus text from `PrometheusMetrics.format`, and has no auth.
- **Resource endpoints live under `/api`.** `apiRoutes` (`src/routes/route.ts`) is a route group that registers each module's routes (`userRoutes` declares `/users`, so the public path is `/api/users`); groups nest, and the nested routes still merge into one trie. Probes, `/metrics` and `/.well-known` stay at the origin root. Middleware shared by the whole API sits on `apiRoutes` (rate limiting today, auth later).
- **Validation runs inside the Effect program** (`decode` in `src/kernel/http/decode.ts`): a body or router-params failure is a `ValidationError` (400 with issues). Malformed JSON never reaches the program — h3's `readBody` rejects it with its own 400.
- **Schemas are per resource and derived** (`src/modules/<resource>/<resource>_schema.ts`): one entity `Struct` (`UserSchema`, with its inferred type `User`) is the source; request schemas (`UserCreateRequestSchema`, `UserIdParamsSchema`, `UserListQuerySchema`), response schemas (`UserGetResponseSchema`, `UserListItemSchema`, `UserCreateResponseSchema`; a collection declares its item, the page wraps it) and the Kysely table type (`UsersTable`, `Omit<User,'id'>` plus `Generated<number>`, merged into `Database` in `src/database/schema.ts`) come from it. Domain code uses the inferred types (`User`, `UserCreateRequest`); no hand-written row or input interfaces.
- **Response data is encoded through its schema.** `defineHandler` requires `response` (`definePagedHandler`, `items`); only declared fields reach the client, so a column added to the table does not leak through `selectAll()`. An encode failure is a defect (500). Database rows are not decoded on read — the migration owns their shape; add a decode in the repository only for a column that needs a transformation.
- **Create answers `201`** (`status: 201` in the handler spec).
- **Request ID**: minted by `requestId` middleware as TypeID `req_…` (TypeID v7), inbound `x-request-id` echoed when <= 128 chars. Written to both `res.headers` and `res.errHeaders` because h3 merges only the latter into error responses (`src/middleware/request_id.ts`). Never drop the `errHeaders` write.
- **Middleware order is a contract** (`src/app.ts`): `provideRuntime` → `cors` → `requestId` → `securityHeaders` → `httpObserver` → `bodyLimit`, registered before route groups mount, so the runtime exists for everyone, preflight is answered early, the observer can read the id, every later response carries the security headers, and a rejected body is still logged and carries the id. Reordering breaks the observer and the runtime lookup.
- **Route groups** (`defineRouteGroup`, `src/kernel/http/router.ts`; the route table itself is `src/routes/route.ts`): a group owns an isolated `H3` instance mounted at `prefix`; its middleware runs only for its routes. Group routes are written relative to the prefix. Mounted groups merge into the parent rou3 trie — no nested fetch hop. App-level config/hooks do not flow into a mounted app; shared behaviour goes in global middleware.

## Security contracts

- **Security headers are fixed** (`src/middleware/security_headers.ts`): `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and a `default-src 'none'` CSP. They go to both `event.res.headers` and `event.res.errHeaders` (same reason as the request id). No `Strict-Transport-Security`: TLS ends at the proxy or the platform.
- **A body must be JSON.** A handler that declares `body` rejects any other `Content-Type` with `415` before reading it (`requireJson` in `src/kernel/http/handler.ts`).
- **Rate limiting is per instance** (`src/middleware/rate_limit.ts`): a fixed window per client address, in memory, on `apiRoutes` only (probes and `/.well-known` stay reachable). `RATE_LIMIT_MAX=0` turns it off, which is the default. It sets `x-ratelimit-*` headers and `metadata.rate_limit`, answers `429` with `retry-after`, and bounds its own memory (50 000 clients). The client address is the socket's, or `CF-Connecting-IP` / `X-Forwarded-For` only with `TRUST_PROXY`; without it, behind a proxy every client shares one bucket, and on Workers (no socket address) too — set it there.
- **There is no authentication.** No product rule exists for who may call what, so none was invented; `apiRoutes` is where it goes.

## Where HTTP code lives

- **`src/kernel/http/`** holds generic mechanisms: code that knows h3 and Effect but nothing about a resource, and that does not grow with the endpoint count (`defineHandler`, `definePagedHandler`, `defineRouteGroup`, `runEffect`, `decode`, the envelope and pagination kit, the runtime bridge, the h3 error renderer). It must not import from `modules/` or `routes/`, and it names no domain service (`HttpEnv` is assembled from declarations the services make).
- **`src/middleware/`** holds plugins: the global ones `createApp` registers once in a fixed order (`cors`, `requestId`, `securityHeaders`, `bodyLimit`), and group-level ones (`rateLimit`, `cacheControl`).
- **`src/modules/<resource>/`** is one vertical slice per resource: `*_schema.ts`, `*_repo.ts`, `*_service.ts`, `*_handler.ts`, `*_routes.ts`, and tests beside them. A module imports `kernel/` and `database/`, never another module's internals. `src/routes/route.ts` is the route table that mounts every module; `src/services.ts` wires every module's layers.

## Naming conventions

- **No `index.ts` barrels.** A directory's entry file is named for what it holds (`config/service.ts`), and imports name the file they need. The one exception is `src/database/migrations/index.ts`, the static migration registry.
- **A schema value ends in `Schema`; the type inferred from it does not.** `UserSchema` is the value, `User` is `typeof UserSchema.Type`. Value and type never share a name, so an import tells you which one you hold. Applies to entity, request, response and params schemas alike: `UserCreateRequestSchema`, `UserGetResponseSchema`, `UserIdParamsSchema`.
- **Pattern for wire contracts**: `<Resource><Action><Request|Response>Schema`, `<Resource>IdParamsSchema` for router params. `Request`/`Response` in a name always means HTTP; the user-lookup cache key is `UserLookup` for that reason.
- **Export a type only when code consumes it.** Do not add `XEncoded`/`XResponse` types speculatively. When a schema transforms (a `Date` that goes out as a string), export `typeof XSchema.Encoded` as `X…Encoded` next to it — `Type` is the domain shape, `Encoded` is the wire shape.
- **Derive, do not repeat**: request and response schemas reuse the entity's fields (`UserSchema.fields.email`) or derive with `mapFields`; the Kysely table type is `Omit<Entity, 'id'>` plus `Generated<…>`.
- **Exceptions, on purpose**: the error envelopes (`ErrorResponse`, `ValidationErrorResponse`) are plain interfaces because the responder builds them and nothing decodes or encodes them; configuration declarations (`src/kernel/config/`, built from the `field.ts` helpers) are not `Schema` values and keep lower-case names (`serverConfig`).
- **File suffixes**: `*_schema.ts`, `*_repo.ts`, `*_service.ts`, `*_handler.ts`, `*_routes.ts`, one per resource, inside `src/modules/<resource>/`; the class inside keeps the `UserRepository`/`UserService` form because it is a service tag, not a schema.

## Observability contracts

- **The logger never blocks a request on Node** (`LoggerLayer` in `src/observer/logger.ts`): lines are formatted on the calling fiber and pushed into an in-memory buffer; a detached fiber writes the buffer to stdout once per `LOG_FLUSH_INTERVAL` in a single `write`. The scope finalizer drains the rest, so graceful shutdown (`SIGINT`/`SIGTERM` through `NodeRuntime.runMain`) loses nothing; a hard crash loses at most one window. On Workers `ConsoleLoggerLayer` writes each line straight to `console.log` (no buffer, no stdout, no colours): a Worker has no shutdown hook to flush on. Do not log with `console.*` from services — use `Effect.log*`. CLI user output (`print` in `src/command/helper.ts`) is not a log and stays direct.
- **Log config** is `LOG_LEVEL`, `LOG_TRANSPORT` (`console`, `file` or both, a comma-separated list), `LOG_FILE`, `LOG_ROTATION`, `LOG_FILE_MAX_FILES`, `LOG_FORMAT` (`pretty` | `json`, console only) and `LOG_FLUSH_INTERVAL`, parsed in `src/kernel/config/logging.ts` (`config.logging.{level,transport,file,rotation,fileMaxFiles,format,flushInterval}`). `LOG_TRANSPORT` is parsed by `choiceList` (`field.ts`): unknown or empty entries fail at startup. Each selected sink receives every line.
- **The file sink rotates by time and is our own code** (`src/observer/log_file.ts`; Effect v4 has no rotation, only `Logger.toFile` and the `FileSystem` primitives). `LOG_FILE` is a base path: the file written is `<stem>_<stamp><ext>`, with `rotationStamp` giving `YYYYMMDD_hh` (hourly), `YYYYMMDD` (daily), `YYYYMMDD` of the Monday (weekly) or `YYYYMM` (monthly), all UTC, `_` as separator. `LOG_ROTATION` picks the period (default daily); `LOG_FILE_MAX_FILES` (default 14, `0` = keep all) prunes older files when a new one opens, and only names matching `<stem>_<stamp><ext>` are ever deleted. Entries carry their own timestamp (`LogEntry.at`), so a batch that straddles a boundary is split across the two files; a restart in the same period appends. One handle is open at a time, closed by a scope finalizer registered *before* `Logger.batched`, so the batcher's final flush runs first. JSON lines regardless of `LOG_FORMAT`; a failed write goes to stderr and drops that batch, never throws into the request. The sink needs `FileSystem` and `Path`, hence `CoreLayer` feeds `NodeServices` into `LoggerLayer`. Not compressed. Workers ignore `LOG_TRANSPORT` (`ConsoleLoggerLayer`).
- **Kysely logging goes through the Effect logger** (`makeQueryLogger`, `src/database/service.ts`, passed as Kysely's `log`). SQL and duration print at `Trace` only (skipped by a boolean check when `Trace` is off); a failed statement logs at `Warn` with the SQL and error text (a unique violation produces one, next to the 409). Bound parameters are never logged: they carry user data. The callback runs outside any fiber, so it takes the `requestId` from `currentRequestId()` (`src/kernel/http/request_context.ts`), an `AsyncLocalStorage` that the `requestId` middleware fills with `run` — never `enterWith`, which workerd does not implement.
- **The pretty sink prints each fact once.** `renderPretty` (`src/observer/logger.ts`) leaves out an annotation whose value is already a whole word of the message (optionally with a unit, `0.49` in `0.49ms`), so the request line is `GET /api/users 200 0.49ms requestId=…`; the JSON sink always keeps every annotation. Message and annotations may therefore overlap freely.
- **Request logs and metrics come from one plugin** (`src/observer/http_observer.ts`), so the counter `http_requests_total` and the timer `http_request_duration_ms` (both labelled `method`, `status`) cover every response, including 404s and h3-level errors. New instruments live in `src/observer/metrics.ts`. The registry is exported at `GET /metrics` when `METRICS_ENABLED` is set; there is no OTLP exporter.

## Shutdown contract

- `SIGINT`/`SIGTERM` reach `NodeRuntime.runMain`, which interrupts the `serve` fiber. The finalizer first calls `beginDrain` (so `/health` turns 503) and waits `SHUTDOWN_DRAIN_DELAY` (default 0), then stops listening. srvx's own signal handler is disabled (`gracefulShutdown: false` in `src/server.ts`) so the scope owns the order: stop accepting, wait until no request is in flight (bounded by `SHUTDOWN_TIMEOUT`), close the remaining sockets with `close(true)`, release the database, flush the log buffer last. Do not re-enable srvx's handler — two handlers race the finalizers and can drop buffered log lines.
- **Drain on requests, never on `server.close()`.** `close()` resolves only when every *connection* has ended, and a socket that never completed a request (a browser's speculative preconnect, a half-sent header) is neither idle nor in flight, so awaiting it stalls for the whole timeout. `provideRuntime` counts requests (`src/kernel/http/inflight.ts`); the finalizer awaits `inFlight.drained`, then force-closes. The warning `Shutdown timed out with N request(s) still in flight` therefore means real work was cut off, not an idle socket.
- **The shutdown is announced by our own logs**: `Shutting down` (with the in-flight count when non-zero) when the finalizer starts, `Server stopped` when the last socket is closed. srvx's own messages are off (`silent: true`, `gracefulShutdown: false`), so removing these two lines makes a stop invisible.
- **`silent: true` hides srvx's listen failures**, so `serveHttp` awaits `server.ready()`; a busy port exits with status 1 and the error instead of idling.
- **How it was verified** (needs a socket, so not in the sandbox): spawn `node src/main.ts serve`, hold an idle socket / a half-sent header / a half-sent body open, send `SIGTERM`, time the exit. Idle and half-header sockets exit in ~10 ms; a body that finishes during the drain is answered (201) and the process exits when it ends; a body that never finishes waits `SHUTDOWN_TIMEOUT` and logs the warning.

## CLI contracts

- **Commands are flat, colon-named**: `serve`, `config:generate`, `migrate:up`, `migrate:down`, `migrate:status`, `migrate:reset`, `migrate:seed` (`src/command/`, wired in `cli.ts`). One file per command; `helper.ts` holds the shared CLI output helpers (`print`, `printWarning` — plain console output, no timestamp/level prefix) and the destructive-op confirmation (`confirmDestructive`).
- **Destructive commands** (`migrate:down`, `migrate:reset`) prompt via `Prompt.Confirm`; `--force` skips the prompt, and a non-TTY session without `--force` refuses to run (`src/command/helper.ts`). Keep this pairing on any new destructive command.
- **`config:generate`** writes `.env.example` from `appConfig.specs`; A new file is created freely; replacing an existing one that differs needs `--overwrite` plus `confirmDestructive` (`--force` skips the prompt and is rejected without `--overwrite`). `--check` fails when the file is stale, `--stdout` prints. It refuses any real dotenv name (`.env`, `.env.local`, …) — dotenv files are never rewritten.
- **`--dry-run`** must not touch the database beyond reads (`getMigrationInfos`).
- **`serve --auto-migrate`** runs `migrateToLatest` before the server starts and never seeds (`src/command/serve.ts`). The command provides `AppLayer`; migrate commands provide `DatabaseLayer` (`src/database/layer.ts`, the driver chosen by `DATABASE_DRIVER`). `Effect.provide` with a layer is reserved for `main.ts` (lint rule `effecttsgo/strict-effect-provide`).
- `migrate:reset --seed` requires `--up`; `migrate:down --count` must be >= 1 — both enforced with `CliError.UserError` in the handler.
- `--to` on `migrate:up` takes a **migration name** (not a numeric version).

## Database contracts

- **Migrations are a static registry** (`src/database/migrations/index.ts`), not a directory scan: keys are `NNNNN_name` (zero-padded prefix, sorts in execution order), each file exports `up` (+ optional `down`). Registry keys must match the file's export binding; a new migration adds the file **and** registers it in `index.ts` — an unregistered file silently never runs.
- **Kysely owns the bookkeeping**: tables `kysely_migration` / `kysely_migration_lock`. Never hand-edit them; `migrate:status` reads state via `Migrator.getMigrations()`.
- **`migrateDown(steps)`** resolves the target name from the executed list and delegates to `migrateTo` (Kysely's `migrateDown` is one-step only) — `src/database/migrator.ts`. The DB must be reachable to compute the target.
- **Seeders are idempotent** by contract (`src/database/seeder.ts` registry; e.g. `onConflict doNothing`). A seeder that is not idempotent breaks every re-run (`migrate:reset --seed`, repeated `migrate:seed`).
- **Schema ownership**: `src/database/schema.ts` is the Kysely `Database` type (tables/columns used in queries); a migration changing the schema updates this type in the same change, or `typecheck` drifts from reality.
- **Two drivers, one contract.** `DatabaseService` (`src/database/service.ts`) is the only thing repositories see: `db`, `query`, `transaction`, `ping`. `DATABASE_DRIVER=sqlite` builds it over `node:sqlite` (`sqlite.ts`, `SqliteDatabaseLayer`); `d1` builds it over a Cloudflare D1 binding (`d1.ts`, `D1DatabaseLayer`, needs the `D1Binding` service). Node picks one in `database/layer.ts` (`DatabaseLayer`); the Worker wires D1 itself in `src/worker.ts`. `makeDatabaseService` is shared, so query/transaction/ping behave the same.
- **The builder has two runtimes** (`pnpm build:node` / `pnpm build:worker`, both `builder/cli.ts build --target=…`, default `node` when the flag is absent; `runtime` in `builder/config.ts`). `workers` applies `WORKERS_PRESET` over the user's config — entry `src/worker.ts`, output `dist/worker/index.mjs`, one file (no splitting), `workerd`/`worker`/`browser` conditions, no shebang, no `node_modules` tracing, no `package.json` — while `minify`/`obfuscate`/`sourcemap` still apply. An unknown `--target` fails; `compile` with `workers` fails. `pnpm deploy` and `pnpm preview` both build with `--minify` and run `wrangler ... dist/worker/index.mjs --no-bundle`, so what `preview` runs is exactly what `deploy` ships (minified); `pnpm watch:worker` lets wrangler bundle the source, unminified, for the edit loop.
- **Never import a Node-only module from the Worker's import graph.** `src/worker.ts` reaches `app.ts`, `services.ts`, `database/d1.ts`, `database/service.ts`, `observer/` and `kernel/`; none may import `node:sqlite`, `layers.ts`, `database/layer.ts`, `database/sqlite.ts`, `server.ts` or `@effect/platform-node`. A violation breaks the Worker bundle (`pnpm preview` and `pnpm watch:worker` fail to start).
- **SQLite connection lifecycle** lives in `SqliteDatabaseLayer`: opens `node:sqlite` once per scope, creates the parent directory, destroys on scope close. Nothing else may open a connection. On open it sets a 5 s busy timeout and `journal_mode = WAL` (not for `:memory:`), so `migrate:*` and the server can share one file; WAL leaves `-wal`/`-shm` files next to the database.
- **D1 specifics.** The dialect (`dialect/d1-*.ts`, adapted from `kysely-d1`, MIT) declares its own `D1Database` type instead of `@cloudflare/workers-types`. D1 has no interactive transactions, so `transaction` fails with `DatabaseError` there. Kysely's SQLite introspector reads columns through `pragma_table_info`, which D1 rejects (`SQLITE_AUTH`) and which breaks the migrator; `D1Introspector` lists tables from `sqlite_master` only, with empty `columns` — anything needing column metadata must not run on D1. `DATABASE_AUTO_MIGRATE` applies migrations at Worker start; isolates can race, so production applies them once, beforehand.
- **D1 on Node is local only.** `D1BindingNodeLayer` (in `src/database/d1.ts`, next to the portable layer) gets the binding from wrangler's `getPlatformProxy`, which reads the same `wrangler.jsonc` and `.wrangler/` state as `wrangler dev`: `DATABASE_DRIVER=d1 pnpm app migrate:up` prepares what `pnpm watch:worker` and `pnpm preview` serve. `wrangler` is imported through a variable (`WRANGLER`) on purpose: a literal import is followed by the bundler and adds ~20 MB (wrangler, miniflare, sharp) to `pnpm build`.
- **Transactions**: `DatabaseService.transaction(run)` commits when the promise resolves and rolls back on rejection; use the `trx` handle inside, never the outer `db`. It is promise-level, not an Effect scope, so repositories that take part accept a `Kysely` or `Transaction` argument. Not available on D1.
- **The connection caches prepared statements** (`NodeSQLiteConnection`, 128 entries, least recently used evicted): Kysely emits the same SQL text for the same query shape, so `prepare` runs once per shape, not per call. Measured at about 4 µs saved per query (roughly 20 % of a Kysely round trip). The connection mutex is a FIFO queue with direct hand-off; it only ever queues when a transaction holds the connection across awaits.
- **The driver is synchronous** (`node:sqlite`): every query blocks the event loop for its duration. Fine for this workload; a long query or migration stalls requests, which is the known ceiling of the single-process design.
- **Uniqueness violations are a domain error.** `isUniqueViolation` (`src/database/service.ts`) recognises SQLite codes 2067 and 1555 on the `DatabaseError` cause (`node:sqlite`) and the text `UNIQUE constraint failed` (D1, which reports no code); the repository turns them into `Conflict`. Other constraint failures stay `DatabaseError` until a route needs them mapped.
- **Queries go through `DatabaseService.query`**, which maps any rejection to `DatabaseError`. Repositories, the migrator and seeders do not call `Effect.tryPromise` themselves.

## How to change it

- **New module / endpoint**: `src/modules/<resource>/` with `<resource>_schema.ts` (entity, request and response schemas, and the table type merged into `Database`; a new table also needs a migration + registry entry), `_repo.ts` and `_service.ts` (each a `Context.Service` with `static layer`; the service declares itself in `HttpServices`), `_handler.ts` (one `defineHandler` — or `definePagedHandler` for a collection — per endpoint; declare `params`/`body`/`query`/`response`), `_routes.ts` (a `defineRouteGroup`) → add the layers to `src/services.ts` and register the routes inside `apiRoutes` in `src/routes/route.ts` → a test beside the code → `docs/api-endpoint.md` row in the same commit.
- **New CLI command**: `src/command/<name>.ts` (`Command.make` + flags + handler) → register in `command/cli.ts` `withSubcommands` → `docs/commandline.md` entry in the same commit. Destructive? Add `--force` + `confirmDestructive` (`src/command/helper.ts`).
- **New config key**: add a field (`text`, `port`, `int`, `flag`, `duration`, `choice`, `logLevel` from `src/kernel/config/field.ts`) to the section file in `src/kernel/config/` that owns the concern, with its default and description; read it as `(yield* ConfigService).<section>.<key>`. The same declaration feeds `.env.example`: run `pnpm app config:generate` and commit the result (a test fails when the file is stale) → `docs/configuration.md` row in the same commit. **New concern**: one new file exporting `<name>Config` (a `group` of fields with a `title`) and its inferred type, plus one line in `appConfig` in `config/service.ts`; cross-field checks go in the group's `transform` (CORS credentials with a wildcard origin fails at startup in `cors.ts`). A secret uses `Config.Redacted` and is listed once, in its section.
- **New migration**: `src/database/migrations/NNNNN_name.ts` exporting `up`/`down` → register in `migrations/index.ts` → run `pnpm app migrate:up`.

## Traps

- **Tests are Vitest** (`pnpm test`, files `src/**/*.test.ts` beside the code, shared helper in `tests/`). `makeTestApp` (`tests/app.ts`) builds the real app over an in-memory database and is called with `app.fetch`, so no port opens (a sandbox that forbids binding is fine). Pass environment overrides the way an operator would (`makeTestApp({ RATE_LIMIT_MAX: '2' })`). A green suite does not exercise the built bundle or workerd: before claiming a change works also run `pnpm build:node` + `node dist/server/index.mjs serve` and, if the Worker's import graph or the D1 path changed, `pnpm preview`. A sandbox that forbids port binding rejects `serve` and `wrangler dev` with `EPERM`.
- **Edit races**: never batch multiple `edit_file` calls to the same file in one parallel block — one edit is silently lost. Sequential per file, verify after.
- **`exactOptionalPropertyTypes` is on**: optional properties in response/error types must be explicitly `| undefined`-compatible; Effect `Option` values from `Flag.optional` need `Option.isSome` before `.value`.
- **Effect v4 vs v3 docs**: this repo is Effect **v4** (`effect@4.0.5`) — v3-era APIs (`Effect.zipRight` as a standalone combinator name, old `Command`/`Prompt` shapes) do not match; the pinned `node_modules` types are the truth.
- **workerd is not Node.** `AsyncLocalStorage.enterWith` is not implemented (use `run`), `process.stdout` is not the log sink, there is no socket address, and `node:sqlite` does not exist. Anything shared with the Worker must be checked with `pnpm preview`.
- **`node --watch` + CLI commands**: `pnpm dev` / `pnpm watch:node` hard-code `serve`; other commands are run via `pnpm app <command>`.

## Plan documents

A plan (`.llms/plans/plan-YYYYMMDD_HHMM.md`) is a contract with fixed shape — frontmatter (`status`, `updated`, `phases` with per-phase `status`/`note`), Objective, Current state (verified file:line facts), Decisions (dated, rejected alternatives named), execution rules, Phases (each with an objectively checkable validation line and a suggested commit message), test matrix, out-of-scope. It executes only on the owner's explicit instruction ("continue with phase N"); one atomic commit per phase; after the last phase, stop and recommend the closing commit message — never commit it unasked. Full spec: the `agent-docs` skill.
