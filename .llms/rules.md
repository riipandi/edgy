# Rules

Contracts, how-to-change recipes, traps. Read the section a change touches before touching it.

## HTTP contracts

- **Every API response is an envelope** (spec: `.llms/api-response.md`; types and builders in `src/kernel/http/envelope.ts`). Success: `{ status: 'success', data, metadata: { status_code, request_id, …pagination }, links? }`. Error: `{ status: 'error', message, error: { code, retryable, details?, debug? }, metadata: { status_code, request_id, … } }`. `metadata` also carries `trace_id` (a `trc_` id, when the trace was recorded), `cache` (`hit`/`miss`/`bypass`) and `rate_limit`, on success and error alike. Field names are snake_case because they are the wire contract. `message` is set only by `defineMessageHandler` (a static string, no `data`; `GET /health` uses it), `rate_limit` is filled by the rate limiter when it is on. Only `GET /` (plain text `All is well`), `/metrics` (Prometheus text) and `/.well-known/*` (RFC-defined formats) answer outside the envelope.
- **An error renders itself.** Every application error implements `AppError` (`src/kernel/errors.ts`): `status`, `clientMessage` and an optional `detail`. `runEffect` only renders them: `NotFound` 404 `<resource> not found` with `error: { id }`, `ValidationError` 400 with the issue list, `Conflict` 409, `RequestTimeout` 504, `DatabaseError` 500 `Database error`; a defect is 500 `Internal server error`, an interrupted fiber (client hung up) 499. `clientMessage` and `detail` reach the client, so they never carry internals. A failure with `status >= 500`, and any defect, reaches the error reporters (`src/observer/error_reporter.ts`) once, with its cause; expected failures (< 500) carry `ErrorReporter.ignore` and interruptions are skipped by Effect (the observer still logs the request line at the level of its status). `runEffect` wraps the program in `Effect.withErrorReporting`; the default reporter logs `Request failed` at `Error` with the request id on the failing fiber's own logger, and extra reporters (Sentry, a pager) are added to `ErrorReporter.layer([...])` there. A new error is a class with those three members in `errors.ts` (or in its module); the kernel needs no edit. The cost: nothing forces every error to exist in a closed union any more, so the type check is `E extends AppError` on the handler.
- **An error is JSON under `/api` and an HTML page elsewhere.** `createApp` sets `onError: makeErrorHandler(() => import('../app/pages/error.marko'))` (`src/kernel/http/error_page.ts`): `isApiPath` (`router.ts`, `API_PREFIX`; `/api` and `/api/…`, not `/apiary`) decides. Under `/api` it is `renderHTTPError` (`errors.ts`), the error envelope; everywhere else, `/health` and `/metrics` included, it renders `app/pages/error.marko` with `{ status, message, requestId?, retryAfter? }` (`publicMessage` is shared, so an unhandled exception is still `Internal server error`). Both copy `event.res.errHeaders` into the `Response` they build, because h3 does not merge them into a response returned from the hook; the page also replaces the fixed CSP with its own nonce'd one. If the error page cannot be rendered the envelope answers: a broken error page must not hide the error. Unhandled exceptions are rendered as `Internal server error`. Unknown paths are answered by the `notFoundRoutes` catch-all (`src/routes/route.ts`), which **throws** an `HTTPError` (`404`, or `405` with `Allow` when `allowedMethods` finds the path under other methods: `src/kernel/http/allowed_methods.ts` asks rou3's `findAllRoutes` over h3's own router, `app['~rou3']`, ignoring the `/**` catch-all itself, and adds `HEAD` where there is `GET`; `rou3` is a direct dependency pinned to h3's version, h3 has no public lookup, and `allowed_methods.test.ts` fails if the property goes; `Allow` is set on `event.res.errHeaders`, since h3 builds an error response from those only; Effect's `HttpRouter` has no `405` to copy): h3's `onResponse` middleware (the observer uses it) converts h3's internal not-found marker with a default config, bypassing `onError`. Keep that catch-all registered last.
- **Handlers accept `Effect<A, E extends AppError, HttpEnv>`.** `AppError` is an interface, not a union: a module adds its own errors without touching `kernel/`.
- **One runtime, no singleton.** `serveHttp` captures the command's service context into an `HttpRuntime` (`src/kernel/http/runtime.ts`) and `createApp` attaches it to every request through the `provideRuntime` plugin; `runEffect` and the observer read it with `runtimeOf(event)`. Never build a second `ManagedRuntime` on Node — it would open a second database connection and logger. (The Worker entry builds exactly one per isolate, and tests build one per test app.) `HttpEnv` is not a hand-kept list: it is the union of `HttpServices`, an empty interface in `runtime.ts` that each service augments next to its own definition (`declare module '../../kernel/http/runtime.ts' { interface HttpServices { user: UserService } }`), so the kernel never names a domain service. A service a handler uses must declare itself there.
- **Endpoints are declared with `defineHandler`** (`src/kernel/http/handler.ts`): `{ params?, body?, query?, response, status?, run }`. The helper reads the body, decodes router params, body and query, runs the program, encodes the value through `response` into the envelope's `data`; `run` receives exactly the inputs the spec declared (an undeclared one is `undefined`). Handlers do not call `runEffect`, `readBody`, `getQuery` or `decode` themselves.
- **Acknowledgements use `defineMessageHandler`** (`{ message, run }`): the envelope carries `message` and no `data`; `run` only has to succeed.
- **Collections use `definePagedHandler` and the pagination kit, and paginate by cursor.** `run` returns a `Page<A>` (`src/kernel/pagination.ts`: `items`, `limit`, `next`); the spec gives `items` (the schema of one element) instead of `response`. The query comes from `paginationQuery(sortable, defaults)` (`src/kernel/http/pagination.ts`): `limit` (1 to 100), `cursor`, `sort_by`, `sort_order`, where `sort_by` is an allow-list typed as a union, so a column name from the client never reaches a query unchecked. There is no `page`, no total and no "every record" mode: a count per request and an offset scan do not scale, and a synchronous driver cannot interrupt either. A cursor is base64url JSON `{ s: sort column, o: order, v: last sort value, i: last id }` (`encodeCursor` / `decodeCursor`; opaque to clients, not secret, only ever bound as parameters, at most 512 characters) and belongs to the sort it was issued for: the schema refuses it with another `sort_by` / `sort_order` (defaults included) or when it does not decode, as `400 VALIDATION_FAILED`. `toPageRequest(query, defaults)` yields the `PageRequest` (`limit`, `after`, `sortBy`, `sortOrder`) a repository takes. A repository fetches `limit + 1` rows, starting after the anchor with a row-value comparison `(sort column, id) > (value, id)` (`<` for `desc`; `id` alone when sorting by `id`), orders by the sort column then `id` **in the same direction** (so the order is total and one comparison covers both), and returns `makePage(rows, request)`, which drops the look-ahead row and encodes the cursor of the last row kept. `user_query_plan.test.ts` fails if a keyset query stops using its index. Metadata (`limit`, `has_more`, `next_cursor`) and relative `self` / `first` / `next` links that keep the other query parameters are derived in one place (`paginationMeta`, `paginationLinks`). The sortable columns must be non-null, since a null cannot be compared this way.
- **Request lifecycle limits.** `runEffect` passes `event.req.signal` to the runtime, so a client that disconnects interrupts the fiber; it wraps the program in `Effect.timeoutOrElse` with `REQUEST_TIMEOUT` (→ `RequestTimeout`, 504); `bodyLimit(BODY_LIMIT)` rejects oversized bodies with 413 as they are read; `loadShedding` (`src/middleware/load_shedding.ts`) answers `503` + `Retry-After: 1` when more than `MAX_IN_FLIGHT` (default 1024, `0` off) requests are in flight, using the count `provideRuntime` keeps (`InFlight.active()`, this request included). `/health` and `/metrics` are exempt, refusals are logged (warning), counted in `http_requests_shed_total`, and carry the request id and CORS headers because the guard is registered after them. Field bounds live in the schemas (`email` ≤ 254, `name` ≤ 200).
- **Health**: `GET /` is the front page (`modules/home`, a Marko page that reads nothing and never touches the database), not a probe. `GET /health` stays at the root, outside `/api`, is readiness, and answers 200 only if `DatabaseService.ping` succeeds (otherwise 500 `Database error`). Once shutdown begins it answers `503` (`unlessDraining`, `HttpRuntime.beginDrain`; an HTML error page, since it is outside `/api`: a probe reads the status); that 503 is logged as a warning, not an error. `GET /metrics` exists only with `METRICS_ENABLED`, is plain Prometheus text from `PrometheusMetrics.format`, and has no auth.
- **Resource endpoints live under `/api`.** `apiRoutes` (`src/routes/route.ts`) is a route group that registers each module's routes (`userRoutes` declares `/users`, so the public path is `/api/users`); groups nest, and the nested routes still merge into one trie. Probes, `/metrics` and `/.well-known` stay at the origin root. Middleware shared by the whole API sits on `apiRoutes` (rate limiting today, auth later).
- **Validation runs inside the Effect program** (`decode` in `src/kernel/http/decode.ts`): a body or router-params failure is a `ValidationError` (400 with issues). Malformed JSON never reaches the program — h3's `readBody` rejects it with its own 400.
- **Schemas are per resource and derived** (`src/modules/<resource>/<resource>_schema.ts`): one entity `Struct` (`UserSchema`, with its inferred type `User`) is the source; request schemas (`UserCreateRequestSchema`, `UserIdParamsSchema`, `UserListQuerySchema`), response schemas (`UserGetResponseSchema`, `UserListItemSchema`, `UserCreateResponseSchema`; a collection declares its item, the page wraps it) and the Kysely table type (`UsersTable`, the entity itself because the repository mints the `user_` id, merged into `Database` in `src/database/schema.ts`) come from it. Domain code uses the inferred types (`User`, `UserCreateRequest`); no hand-written row or input interfaces.
- **Response data is encoded through its schema.** `defineHandler` requires `response` (`definePagedHandler`, `items`); only declared fields reach the client, so a column added to the table does not leak through `selectAll()`. An encode failure is a defect (500). Database rows are not decoded on read — the migration owns their shape; add a decode in the repository only for a column that needs a transformation.
- **A cache must not keep failures.** `Cache` (and `RequestResolver.asCache`) stores a failed lookup like a successful one, for the full TTL. `UserService` passes `timeToLive: (exit) => Exit.isSuccess(exit) ? 30s : zero`, so a transient `DatabaseError` is retried by the next call instead of replayed; any new cache must do the same.
- **Create answers `201`** (`status: 201` in the handler spec).
- **Request ID**: minted by `requestId` middleware as TypeID `req_…` (TypeID v7), inbound `x-request-id` echoed when <= 128 chars. Written to both `res.headers` and `res.errHeaders` because h3 merges only the latter into error responses (`src/middleware/request_id.ts`). Never drop the `errHeaders` write.
- **Middleware order is a contract** (`src/app.ts`): `provideRuntime` → `cors` → `requestId` → `securityHeaders` → `httpObserver` → `loadShedding` → `bodyLimit`, registered before route groups mount, so the runtime exists for everyone, preflight is answered early, the observer can read the id, every later response carries the security headers, and a rejected body is still logged and carries the id. Reordering breaks the observer and the runtime lookup.
- **Route groups** (`defineRouteGroup`, `src/kernel/http/router.ts`; the route table itself is `src/routes/route.ts`): a group owns an isolated `H3` instance mounted at `prefix`; its middleware runs only for its routes. Group routes are written relative to the prefix. Mounted groups merge into the parent rou3 trie — no nested fetch hop. App-level config/hooks do not flow into a mounted app; shared behaviour goes in global middleware.

## Security contracts

- **Security headers are fixed** (`src/middleware/security_headers.ts`): `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and a `default-src 'none'` CSP; an HTML page replaces only the CSP (see "Frontend contracts"). They go to both `event.res.headers` and `event.res.errHeaders` (same reason as the request id). No `Strict-Transport-Security`: TLS ends at the proxy or the platform.
- **A body must be JSON.** A handler that declares `body` rejects any other `Content-Type` with `415` before reading it (`requireJson` in `src/kernel/http/handler.ts`).
- **Rate limiting counts through a `RateCheck`** (`src/middleware/rate_limit.ts`): a fixed window per client address, shared by `apiRoutes` and the HTML pages (`/`, `/users`: route-level `rateLimitMiddleware`, since a group at the root would wrap every later route); probes, `/metrics`, assets and `/.well-known` stay reachable. `RATE_LIMIT_ENABLED` (default `true`) decides whether the plugin is registered at all; `RATE_LIMIT_MAX` must be at least 1 when it is on (checked at startup); with `cloudflare` it is only reported as `limit` and must mirror the binding's limit in `wrangler.jsonc`. A `RateDecision` always carries `limit` and `resetAt`, and `remaining` unless the store only answers yes or no (the Workers binding; `ApiRateLimit.remaining` is then absent and so is `x-ratelimit-remaining`). It sets `x-ratelimit-limit/remaining/reset` on every response of the group, errors included, puts `rate_limit` in the success **and** the error envelope's `metadata`, answers `429` with `retry-after`, and the client address comes from `clientAddress` (`src/middleware/client_ip.ts`, a pure function of the socket address, the headers and `ClientIpTrust`): the `TRUSTED_PLATFORM` header if set and valid (with a socket, only from a `TRUST_PROXY` peer; with none, as on Workers, as sent; a missing, malformed or unbelieved one falls back to the socket, never to `X-Forwarded-For`; `clientLocation` follows the same rule through `platformAddress`); otherwise the socket's address unless it belongs to a `TRUST_PROXY` proxy (`TrustedProxies`: none, all, or `IpRange`s from `kernel/ip.ts`, which handles IPv4, IPv6 and IPv4-mapped sockets without `node:net`, so the Workers bundle stays clean), then `X-Forwarded-For` from the right skipping trusted proxies (a malformed entry stops the search and the socket's address is used), then `X-Real-IP`; no address at all is `unknown`, one shared bucket. In-process tests set the peer with `makeTestApp().request(path, { ip })`. Workers have no socket: set `TRUSTED_PLATFORM`. **`PROXY_PROTOCOL`** (a `TrustedProxies`, parsed like `TRUST_PROXY`) is read from the TCP connection, not a header: `acceptProxyProtocol` (`kernel/http/proxy_protocol.ts`, Node only, called by `serveHttp` right after `serve(…, { manual: true })` and before `serve()` starts listening) takes the HTTP server's `connection` listeners off, reads a PROXY v1 or v2 header from a peer in the list (buffering until complete, 5 s, v1 ≤ 107 bytes, v2 payload ≤ 536), redefines the socket's `remoteAddress` / `remotePort` (which is where srvx and h3 read the client, so the limiter, `TRUST_PROXY` and logs all follow), pushes the bytes after the header back with `unshift`, and only then calls the original listeners. A listed peer that sends no valid header is destroyed (serving it would make every client the balancer); a peer outside the list is passed through untouched and its header, if any, is just a bad HTTP request. `kernel/http/proxy_protocol.test.ts` drives it through a real `http.createServer` without a port. **`CLOUDFLARE_LOCATION_HEADERS`** puts `country` / `city` (`CF-IPCountry`, `CF-IPCity`; `clientLocation` sanitises: two letters or digits, `XX` dropped, city printable ≤ 64) on the request log through the `locationHeaders` plugin (`event.context.location`), registered only when on, and believed only when `TRUSTED_PLATFORM` is set and that header holds a valid address on this request. `RATE_LIMIT_STORE=memory` (default) is `makeMemoryRateCheck`: in-process, synchronous, bounded to 50 000 clients, so the effective limit is `max` times the instance count. `redis` is `makeSharedRateCheck` (`rate_limit_shared.ts`): Effect's `RateLimiter` (`fixed-window`, `onExceeded: 'fail'`) over a Redis/Valkey store, so `max` is global. It **fails open and fast**: each store call has a 250 ms timeout, and after any failure the store is bypassed for 10 s (one warning), so a dead Redis costs one slow request, not every request (measured: 285 ms, then 1–3 ms; counting resumes when Redis answers). Only a real "limit exceeded" refuses. Node only: `src/layers.ts` builds the store (`NodeRedis` is imported lazily, only when the limiter is on with `redis`), `server.ts` passes the check to `createApp`. `RATE_LIMIT_STORE=cloudflare` is `makeBindingRateCheck` (`rate_limit_binding.ts`) over Cloudflare's Rate Limiting binding (`ratelimits` in `wrangler.jsonc`, named by `RATE_LIMIT_BINDING`): per location, eventually consistent, allowance and period (10 or 60 s) fixed in Wrangler, so `RATE_LIMIT_MAX` is only reported and `RATE_LIMIT_WINDOW` only feeds `retry-after`; same fail-open guards (250 ms, 10 s cooldown). Workers only: `worker.ts` resolves the binding and dies at isolate build if it is missing; a store the platform lacks (`redis` on Workers, `cloudflare` on Node) stops startup. KV is not a rate-limit store (no atomic increment, eventual consistency, one write per second per key). Tests use the memory check, or inject a `RateCheck` through `makeTestApp`.
- **A user has a required, non-blank `name`** (`NameSchema` in `user_schema.ts`: at most 200 characters and a non-whitespace one); `users.name` is `NOT NULL` in the initial migration, `UserSchema` and `UserCreateRequestSchema` both require it, and a missing or blank one is a `400` naming `name`. `tests/ids.ts`' `userRow` defaults it.
- **There is no authentication.** No product rule exists for who may call what, so none was invented; `apiRoutes` is where it goes.

## Frontend contracts

- **Layout.** `app/pages/*.marko` (one per page), `app/tags/*.marko` (components; Marko discovers `tags/` directories, so `user-list.marko` is `<user-list>` with no import), `app/styles/*.css.ts` (vanilla-extract: `theme.css.ts` holds `createTheme` tokens and the theme class, applied to `<html>` in `tags/app-shell.marko`; other files import `vars` from it). `app/marko.d.ts` declares `*.marko` for `tsc`; `pnpm typecheck` also runs `mtc`, the only thing that type-checks a template (`export interface Input`). `tsconfig.json` includes `**/*.marko` for it. Oxlint and oxfmt do not see `.marko`.
- **A page is `definePageHandler({ load, template })`** (`src/kernel/http/page.ts`; `HtmlTemplate` in `html_response.ts`) in the module that owns the data (`user_pages.ts`: `usersPageHandler` and the `userPages` route group, mounted at the origin root by `pageRoutes` in `routes/route.ts`; the page address is the group's prefix). `load` is an Effect over `HttpEnv`, so a page uses the services the API uses (same cache, same `UserService`). It runs through `runProgram` (`responder.ts`: timeout, cancellation, span, error reporting, `?nocache=true`, `x-cache`) — the part of `runEffect` that does not depend on the envelope. `template` must be `() => import('…/app/pages/x.marko')`, never a static import: a static one makes every module that mentions the page unloadable outside Vite (`pnpm app migrate:up` runs plain Node), and in `pnpm dev` the fresh `import()` is what picks up an edited template. The result streams (`render(...).toReadable()`); `$global.signal` is the request's `AbortSignal` and `$global.cspNonce` the per-response nonce.
- **A page failure is thrown, not rendered by the page**: `definePageHandler` throws `HTTPError({ status, message: clientMessage })` for a refusal or failure (a client that hung up gets a bare `499`), and the app's error hook renders it (an error page outside `/api`). `refusal` / `failure` in `responder.ts` are the envelope's alone.
- **HTML responses have their own CSP** (`contentSecurityPolicy` in `html_response.ts`, used by pages and error pages through `htmlResponse`, which streams the template, sets `content-type`, `cache-control: private, no-cache` and the nonce'd CSP on the headers it is given — `event.res.headers` for a page, because h3 merges those over a returned `Response`; a copy of `errHeaders` for an error page): `default-src 'none'; script-src 'self' 'nonce-…'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. The nonce reaches Marko's inline resume script and the `<script>`/`<link>` tags it emits through `$global.cspNonce`. Under `pnpm dev` (`event.context.development`, set by `developmentMode`) `style-src` gains `'unsafe-inline'` and `connect-src` gains `ws: wss:`, nowhere else. Both platforms must set it: Node's `startDevApp` passes `development: true`, and `src/worker.ts` passes `import.meta.env.DEV` (Vite replaces it with `false` in a build, so a deployed Worker never has it). Forgetting it on the Worker makes the browser block the `<style>` tags Vite injects for `.css.ts` in `pnpm dev --mode worker` (pages render unstyled while the CSS requests answer 200/304); `src/vite-env.d.ts` types the one `import.meta.env` field in use. A page answers `cache-control: private, no-cache` because the nonce is per response. Never add `'unsafe-inline'` to `script-src`; a template that needs an inline script uses the nonce.
- **Browser assets are `/assets/**`.** Vite names them `assets/<name>-<hash>`; `assetRoutes` (`src/kernel/http/assets.ts`, `serveStatic` with `cache-control: public, max-age=31536000, immutable`, no index) serves them from an `AssetSource` (`meta`/`contents` over an opaque id; never decode it again, h3 has already normalised it). `src/kernel/http/node_assets.ts` (Node only, imported by `server.ts` alone, because `node:sea` does not exist on Workers) has `directoryAssets(root, scope)` (confined to `root` and to ids under `scope`, since the Node root also holds `index.mjs`: a strict name pattern, no `..`, a `startsWith(root + sep)` check) and `embeddedAssets()` (SEA blobs keyed `assets/<name>`, `undefined` when not a SEA). `serveHttp` picks: dev server installed → none (Vite serves the source); else `embeddedAssets() ?? directoryAssets('<entry dir>', '/assets/')`. The client build writes into the server's directory without emptying it (the server builds first and empties it); SSR chunks go to `chunks/` (`assetsDir`), so they never collide with `assets/`. On Workers `/assets/**` is served by Cloudflare's assets binding (the plugin adds `assets` to the generated `wrangler.json`; do not declare it in `wrangler.jsonc`) before the Worker runs, so `createApp` gets no `assets` there.
- **`pnpm dev` is `vite`, and the application runs inside it.** `devServerPlugin` (`builder/dev.ts`, `apply: 'serve'`, part of the node platform; where Vite listens is `vite.config.ts`'s, not the plugin's) (`HOST`, default `127.0.0.1`; `PORT`, default 3000; `strictPort`), puts `.env` / `.env.local` in `process.env` where a variable is not already set (what `node --env-file` did; the keys it set are replaced when a file is edited), and in `configureServer` creates a module runner on the SSR environment (`createServerModuleRunner`) and returns a `post` hook that mounts the application after Vite's own middleware, so Vite answers modules, assets and the hot-reload socket and everything else is ours: one process, one port, no proxy. The application is `startDevApp` in `src/dev.ts` (loaded through the runner, which is how it imports `.marko` and `.css.ts`): `ManagedRuntime` over `CoreLayer` + `AppLayer`, migrations at every start (an unset `DATABASE_AUTO_MIGRATE` means on in dev; only an explicit `false` opts out), then `makeNodeApp({ development: true })` (`src/application.ts`, shared with `serveHttp`, so dev and production build the application the same way and differ only in who listens and who serves the assets) and `toNodeHandler(app)` from `h3/node`. `development: true` registers `developmentMode` (`event.context.development`), which `htmlResponse` reads to widen the HTML policy for Vite (`style-src 'unsafe-inline'`, `connect-src ws: wss:`). The plugin's watcher listens for `src/` (tests excluded) and `.env` / `.env.local`: it stops the application (`http.beginDrain()`, up to 2 s for requests in flight, then `runtime.dispose()`: database, logs, telemetry), clears the runner's cache (or the old code would run again), starts a new one and sends `full-reload`. A failed start is kept and shown for every request until the next change. Not in dev: the PROXY protocol reader and the `/assets` route (Vite serves the assets from source), and `serve`'s flags. Starting `serve` natively (`node src/main.ts serve`) is unsupported: it fails at the first page request, when `import('….marko')` runs under plain Node. `tests/dev_server.test.ts` drives the real plugin (a Vite server in middleware mode, no port) through Node's real HTTP parser: pages, API, errors, Vite's own `/@vite/client`, the widened policy, and a restart that drops in-memory data while a test file or a page does not.
- **Vitest loads pages through the same plugins** (`vitest.config.ts`: `marko()` is not linked under test, so no browser entries are named in the HTML; `vanillaExtractPlugin()`). `makeTestApp(env, { assets })` mounts an `AssetSource`. Page tests assert on the HTML (`Showing <!>2` — Marko's text-node markers), the CSP nonce and the shared headers.
- **The executable embeds the pages.** `builder/compile.ts` builds the application again with the SSR environment overridden to one CJS file (`format: 'cjs'`, `codeSplitting: false`, `transform.define['import.meta'] = '({})'`, no banner) and the client output in a temp directory, then passes every browser file to `node --experimental-sea-config` as `assets/<name>`. The one `import.meta.url` in the server (`server.ts`) is evaluated only when `embeddedAssets()` is `undefined`.

## Where HTTP code lives

- **`src/kernel/http/`** holds generic mechanisms: code that knows h3 and Effect but nothing about a resource, and that does not grow with the endpoint count (`defineHandler`, `definePagedHandler`, `defineRouteGroup`, `runEffect`, `decode`, the envelope and pagination kit, the runtime bridge, the h3 error renderer). It must not import from `modules/` or `routes/`, and it names no domain service (`HttpEnv` is assembled from declarations the services make).
- **Reads that can be cached go through `makeReadThrough`** (`src/kernel/cache/read_through.ts`), never an ad-hoc `Cache`. It wraps Effect's `PersistedCache` and is shaped by `config.cache`: `CACHE_ENABLED=false` is a plain lookup; `memory` is the in-process half only (`LocalCachePersistence` stores nothing, and the persisted TTL is zero so nothing is serialised); `redis` / `cloudflare` keep the entry in the shared store for `CACHE_TTL` and a process-local copy for `CACHE_LOCAL_TTL`. The key is a `Persistable.Class` (`UserLookup`, in the service file) whose success schema includes `null` for "known missing" (a negative cache), and only a success is kept: both TTL functions return zero for a failure, so a transient database error is never replayed (the bug the first version had). A write must `invalidate` the keys it touches. Store failures are never the request's: `makeReadThrough` falls back to the lookup on a `PersistenceError` or `SchemaError` (an entry that no longer decodes after a deploy), and shared backings are wrapped by `guardBacking` (`guard.ts`: 250 ms timeout, 10 s cooldown, a read becomes a miss and a write a no-op, one warning), the same policy as the rate limiter. The request log's `cache` annotation (`hit`/`miss`/`bypass`) comes from a per-request `CacheTally` that `runEffect` provides as `CacheTrace`: the lookup runs only when neither the process nor the store had the entry, so running it is a miss and finishing a read without it a hit (`summarizeTally`: bypass, else miss if any read missed, else hit; absent when nothing was read through a cache), and the same word goes out in `metadata.cache` (success and error envelopes, `cacheMeta` in `envelope.ts`) and as the `x-cache` header (`HIT`/`MISS`/`BYPASS`, on `res.headers` and `res.errHeaders`, exposed through CORS). `?nocache=true` on a `GET` sets the `CacheBypass` reference in `runEffect`; a bypassed read goes to the source and neither reads nor writes the cache. The roots provide `Persistence`: Node `CachePersistenceLayer` in `layers.ts` (Redis shares one `RedisLayer` with the rate limiter, so one connection), Workers `cachePersistence` in `worker.ts` (`layerBackingEdgeCache` over `caches.default`; per location, no global purge or clear, nothing stored on `*.workers.dev`, writes awaited because there is no `ctx` here), tests `makeTestApp({ cacheBacking })` with `tests/cache.ts`' fake store. A store the platform lacks stops startup (`redis` on Workers, `cloudflare` on Node). KV is not a cache store here: 60 s minimum TTL, up to 60 s of staleness across locations, a write per second per key, and a cold read no quicker than D1.
- **Every error response explains itself, and says no more than the log level allows.** The error envelope's `error` is always `{ code, retryable, details?, debug? }` (`ApiErrorBody`, built in `src/kernel/http/error_body.ts`). An `AppError` owns its `code` (stable, `UPPER_SNAKE`), `retryable` and `detail` (`DatabaseError.retryable` is the same transient check the read retry uses); an error h3 raised or a middleware threw has no `AppError`, so `statusBody` derives the code from the status and repeats `Retry-After` as `details.retry_after`; a defect is `INTERNAL_ERROR`. `debug` (`{ type, message }`, server errors only) exists only when `HttpRuntime.diagnostics` is true, which is `LogLevel.isEnabled('Debug')`: the response is as chatty as the log, so production never leaks it. Whatever reaches a client or a log passes `src/kernel/redact.ts` first (`redactText` for credentials in URLs, bearer/basic tokens, JWTs and the value of any `password`/`token`/`secret`/`api_key`/`authorization`/`cookie`-like name; `redactValue` for objects, by key; `describeFailure` for a thrown value). Applied to `error.details`, `error.debug`, the error reporter's log line and Kysely's `Query failed` line; a validation message for a field with a secret-like name is replaced, because a schema message can quote the rejected value. `metadata.trace_id` and the `x-trace-id` header are set on errors too (`runEffect` notes the trace on success and failure; both only when telemetry is on and the trace was recorded), the request log carries `errorCode`, and a new `AppError` must declare `code` and `retryable`. Emails and other personal data are not redacted by shape: keep them out of error messages.
- **Untrusted input is bounded before it is used.** An inbound `x-request-id` is kept only if it matches `[A-Za-z0-9._:-]{1,128}` (it is echoed in a header and printed in every log line; the pretty sink writes it raw), otherwise a fresh id is minted. A JSON body is read within `REQUEST_TIMEOUT` (`readBodyWithin` in `handler.ts`, `408`), because the body is read before the program and its timeout starts. The read is the handler's own stream reader (`readBodyWithin`, not h3's `readBody`, which cannot be cancelled): on the deadline it cancels the read and answers `408` with `Connection: close`, so the half-sent request releases its socket instead of waiting for the server's own timeouts. The same reader parses the JSON (`400 Invalid JSON body`). `redactText` truncates its input to 16 KB and scans linearly (a keyword search, then a bounded sticky match at each hit, never a pattern tried from every offset); keep any new pattern in that style. Metric labels that come from the client are folded to a fixed set (`metricMethod`); never label a metric with a path or a header. Every OTLP export has a 5 s deadline and every log sink write a 5 s budget, and shutdown's last telemetry flush 1 s.
- **Identifiers are TypeIDs, each declared next to what it identifies** with `defineId(prefix)` (`src/kernel/objectids.ts`), which returns `{ prefix, make, schema }` and throws at import on a malformed or already-used prefix: `UserId` (`user`) in `user_schema.ts`, `RequestId` (`req`) in `request_id.ts`, `TraceId` (`trc`) in `observer/trace_id.ts`, `InstanceId` (`inst`) in `telemetry.ts`. A new kind declares its own; there is no shared list. `make()` mints a UUIDv7-based id (ids sort by creation time) and `schema` is a pattern check (wrong prefix or malformed suffix is a `400` before any query). Row ids are minted by the repository, not the database: `users.id` is `text`, the same column on SQLite and D1. The trace id is the one exception to `make`: `metadata.trace_id` is the OpenTelemetry id re-encoded as `trc_…` (`traceTypeId`; `traceHexOf` reverses it) because a trace id is random and `typeid-js` accepts only UUIDv7. The span carries the `trc_` form as the `trace.typeid` attribute and request log lines as `traceId`, so a pasted id is searchable; the backend's own index stays the hex id.
- **Response headers are part of the contract.** `/api` answers `cache-control: no-store` (`cacheControl({ errors: true })` also covers error responses; a public group leaves errors uncached-by-default), every response carries `server-timing: total;dur=<ms>` (set by the observer on both the response and error paths), collections repeat their links as an RFC 8288 `link` header (`linkHeader` in `envelope.ts`), and CORS exposes `x-request-id`, `x-ratelimit-*`, `retry-after` and `link` (`EXPOSED_HEADERS` in `cors.ts`; a header a script must read has to be listed there). h3 builds an error response from `res.errHeaders` only, so a header that must survive errors is set on both.
- **`src/middleware/`** holds plugins: the global ones `createApp` registers once in a fixed order (`cors`, `requestId`, `securityHeaders`, `bodyLimit`), and group-level ones (`rateLimit`, `cacheControl`).
- **`src/modules/<resource>/`** is one vertical slice per resource: `*_schema.ts`, `*_repo.ts`, `*_service.ts`, `*_handler.ts`, `*_routes.ts`, and tests beside them. A module imports `kernel/` and `database/`, never another module's internals. `src/routes/route.ts` is the route table that mounts every module; `src/services.ts` wires every module's layers.

## Naming conventions

- **No `index.ts` barrels.** A directory's entry file is named for what it holds (`config/service.ts`), and imports name the file they need. The one exception is `src/database/migrations/index.ts`, the static migration registry.
- **A schema value ends in `Schema`; the type inferred from it does not.** `UserSchema` is the value, `User` is `typeof UserSchema.Type`. Value and type never share a name, so an import tells you which one you hold. Applies to entity, request, response and params schemas alike: `UserCreateRequestSchema`, `UserGetResponseSchema`, `UserIdParamsSchema`.
- **Pattern for wire contracts**: `<Resource><Action><Request|Response>Schema`, `<Resource>IdParamsSchema` for router params. `Request`/`Response` in a name always means HTTP; the user-lookup cache key is `UserLookup` for that reason.
- **Export a type only when code consumes it.** Do not add `XEncoded`/`XResponse` types speculatively. When a schema transforms (a `Date` that goes out as a string), export `typeof XSchema.Encoded` as `X…Encoded` next to it — `Type` is the domain shape, `Encoded` is the wire shape.
- **Derive, do not repeat**: request and response schemas reuse the entity's fields (`UserSchema.fields.email`); the Kysely table type is the entity, or `Omit<Entity, …>` plus `Generated<…>` for columns the database fills.
- **Exceptions, on purpose**: the envelopes (`ApiSuccess`, `ApiError`, `ApiErrorBody`) are plain interfaces because the responder builds them and nothing decodes or encodes them; configuration declarations (`src/kernel/config/`, built from the `field.ts` helpers) are not `Schema` values and keep lower-case names (`serverConfig`).
- **File suffixes**: `*_schema.ts`, `*_repo.ts`, `*_service.ts`, `*_handler.ts`, `*_routes.ts`, one per resource, inside `src/modules/<resource>/`; the class inside keeps the `UserRepository`/`UserService` form because it is a service tag, not a schema.

## Code comments

A comment carries what the code cannot say, and nothing else. Keep it short.

- **Write one for** a non-obvious reason (why this and not the obvious alternative), a contract or invariant a caller must respect, a trap (an order that matters, a platform quirk, a failure that looks harmless), or a unit.
- **Do not write one that** restates the next line or the name, narrates a change ("now", "no longer", "used to", "previously", "we decided"), explains how the code got here, or opens with filler ("Note that", "Basically", "This function...", "In order to"). A good name replaces a comment.
- **Never mention** a decision, plan, issue, audit, ticket, roadmap, session, the owner, or the user, and never point to a file or path ("see foo.ts", "handled in `route.ts`"). A comment that needs a pointer to make sense is stating a contract the code should hold itself. When the counterpart matters, name the concept or symbol, not the location. Reasons and history belong in `.llms/architecture.md`, open findings in `.llms/issues/`.
- **Shape.** One summary line for an exported symbol; add lines only for a contract or a trap. No `@param` or `@returns` that repeat the signature. No section banners, no commented-out code, no TODO without something to act on. English, plain sentences, one idea per line, under about 100 characters.
- **Keep directive comments** (`oxlint-disable-next-line`, `@ts-expect-error`, `@vite-ignore`, `/// <reference />`, shebangs) on the line they apply to, with a reason when the directive is not obvious.
- **Update or delete** a comment in the same change that makes it wrong. A stale comment is a defect.

## Observability contracts

- **The logger never blocks a request on Node** (`LoggerLayer` in `src/observer/logger.ts`): lines are formatted on the calling fiber and pushed into an in-memory buffer; a detached fiber writes the buffer to stdout once per `LOG_FLUSH_INTERVAL` in a single `write`. The scope finalizer drains the rest, so graceful shutdown (`SIGINT`/`SIGTERM` through `NodeRuntime.runMain`) loses nothing; a hard crash loses at most one window. On Workers `ConsoleLoggerLayer` writes each line straight to `console.log` (no buffer, no stdout, no colours): a Worker has no shutdown hook to flush on. Do not log with `console.*` from services — use `Effect.log*`. CLI user output (`print` in `src/command/helper.ts`) is not a log and stays direct.
- **Log config** is `LOG_LEVEL`, `LOG_TRANSPORT` (`console`, `file` or both, a comma-separated list), `LOG_FILE`, `LOG_ROTATION`, `LOG_FILE_MAX_FILES`, `LOG_FORMAT` (`pretty` | `json`, console only) and `LOG_FLUSH_INTERVAL`, parsed in `src/kernel/config/logging.ts` (`config.logging.{level,transport,file,rotation,fileMaxFiles,format,flushInterval}`). `LOG_TRANSPORT` is parsed by `choiceList` (`field.ts`): unknown or empty entries fail at startup. Each selected sink receives every line.
- **The file sink rotates by time and is our own code** (`src/observer/log_file.ts`; Effect v4 has no rotation, only `Logger.toFile` and the `FileSystem` primitives). `LOG_FILE` is a base path: the file written is `<stem>_<stamp><ext>`, with `rotationStamp` giving `YYYYMMDD_hh` (hourly), `YYYYMMDD` (daily), `YYYYMMDD` of the Monday (weekly) or `YYYYMM` (monthly), all UTC, `_` as separator. `LOG_ROTATION` picks the period (default daily); `LOG_FILE_MAX_FILES` (default 14, `0` = keep all) prunes older files when a new one opens, and only names matching `<stem>_<stamp><ext>` are ever deleted. Entries carry their own timestamp (`LogEntry.at`), so a batch that straddles a boundary is split across the two files; a restart in the same period appends. One handle is open at a time, closed by a scope finalizer registered *before* `Logger.batched`, so the batcher's final flush runs first. JSON lines regardless of `LOG_FORMAT`, in the key order of `jsonLogger` (`src/observer/log_json.ts`: `timestamp`, `level`, `message`, `annotations`, `cause` when present, `spans`, `fiberId`; Effect's own `Logger.formatJson` starts with `message`), which `LOG_FORMAT=json` shares; a failed write goes to stderr and drops that batch, never throws into the request. The sink needs `FileSystem` and `Path`, hence `CoreLayer` feeds `NodeServices` into `LoggerLayer`. Not compressed. Workers ignore `LOG_TRANSPORT` (`ConsoleLoggerLayer`).
- **Kysely logging goes through the Effect logger** (`makeQueryLogger`, `src/database/service.ts`, passed as Kysely's `log`). SQL and duration print at `Trace` only (skipped by a boolean check when `Trace` is off); a failed statement logs at `Warn` with the SQL and error text (a unique violation produces one, next to the 409). Bound parameters are never logged: they carry user data. The callback runs outside any fiber, so it takes the `requestId` from `currentRequestId()` (`src/kernel/http/request_context.ts`), an `AsyncLocalStorage` that the `requestId` middleware fills with `run` — never `enterWith`, which workerd does not implement.
- **The pretty sink prints each fact once.** `renderPretty` (`src/observer/logger.ts`) leaves out an annotation whose value is already a whole word of the message (optionally with a unit, `0.49` in `0.49ms`), so the request line is `GET /api/users 200 0.49ms requestId=…`; the JSON sink always keeps every annotation. Message and annotations may therefore overlap freely.
- **Request logs and metrics come from one plugin** (`src/observer/http_observer.ts`), so the counter `http_requests_total` and the timer `http_request_duration_ms` (both labelled `method`, `status`) cover every response, including 404s and h3-level errors. New instruments live in `src/observer/metrics.ts`. The registry is exported at `GET /metrics` when `METRICS_ENABLED` is set; there is no OTLP exporter.

- **Telemetry is OTLP over HTTP/JSON, on by default and aimed at the Compose collector** (`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`, header `authorization=edgy-dev-ingestion-key`; `OTEL_SDK_DISABLED=true` turns it off, and `telemetryEnabled` in `config/observability.ts` is the one definition of "on" — exporters, request tracing and `trace_id` all use it; an empty endpoint cannot disable it, because Effect's env provider treats an empty string as unset). `wrangler.jsonc` sets `OTEL_SDK_DISABLED` for deployed Workers, and `tests/app.ts` sets it for every test app (`src/observer/telemetry.ts`; no gRPC, no protobuf). `TelemetryLayer` installs Effect's `OtlpTracer` and `OtlpMetrics` and the `Flusher` they share; `TelemetryRuntimeLayer` adds the `fetch`-based `HttpClient` and JSON serialization and is the unit every composition root (Node `CoreLayer`, `worker.ts`, `tests/app.ts`) builds once and gives both to the app and to the logger, so the OTLP log sink (`LOG_TRANSPORT` containing `otlp`, `makeOtlpLogSink`) and the tracer share one `Flusher`. Headers come from the secret `OTEL_EXPORTER_OTLP_HEADERS` (`parseOtlpHeaders`), the resource carries `service.name`, `service.version` (package.json) and a per-process `service.instance.id`. Export never touches a request: buffered, sent every `OTEL_EXPORT_INTERVAL` (default 5 s) or when a batch fills; an exporter whose collector fails switches itself off for 60 s and drops its buffer; on Node each exporter flushes at shutdown (scope finalizer, after the server stops); on Workers `worker.ts` calls `Flusher.flush` from `waitUntil`, at most once per interval, so the last requests before idle go out with the next one.
- **Tracing rules** (`runEffect`). One server span per request, named `METHOD route-pattern` (the matched route, trailing slash trimmed; never the raw path, to keep names low-cardinality), attributes `http.request.method`, `url.path`, `http.route`, `request.id`, `http.response.status_code`. A W3C `traceparent` continues the caller's trace and its sampled flag wins; otherwise the span is a root, recorded for `OTEL_TRACES_SAMPLE_RATIO` of requests (`sampled` option; no synthetic parent). A client error (status < 500) is an *answer*: `runEffect` carries it as a value (`Outcome.refused`) so the span ends `Ok`, as OpenTelemetry asks of server spans; only 5xx and defects fail it. `metadata.trace_id` is returned only when traces are exported and this trace was sampled. `event.context.trace` keeps the span so the observer's request log line (written after the fiber ended) is logged with that span as parent and joins the trace. Spans use `captureStackTrace: false`.
- **Noise requests are quieted by a hard-coded list** (`src/observer/quiet_paths.ts`, tested entry by entry in `quiet_paths.test.ts`; deliberately not configuration: it changes when browsers and bots do, not per deployment). Groups: `browser` (`/favicon.ico`, `apple-touch-icon*`, `/.well-known/appspecific/*`, i.e. Chrome DevTools), `crawler` (`/robots.txt`, `/sitemap.xml`, `/ads.txt`, `/security.txt`), `probe` (`/health`, `/metrics`), `scanner` (`/wp-*`, `*.php`, `/.env*`, `/.git/`, `/phpmyadmin`, `/cgi-bin/`, `/actuator`, … only while the answer is 404). A quiet request's log line is written at **Debug** (gone at Info, back with `LOG_LEVEL=Debug`, annotated `quiet=<group>`), never dropped; a quiet request that fails (`/health` 503 while draining, any 5xx) is logged normally. Metrics still count every request; a **probe** is additionally left out of `http_request_duration_ms` (a stream of instant answers drags p50/p99 down) and its trace is not recorded (`sampled: false` unless the caller sent a sampled `traceparent`). To add a path, add it to the right group in `RULES`; a path must be listed in one group only (checked at import).
- **Metrics registry is process-wide.** `Metric` counters live in a global registry, so tests in one process share them: assert a difference, not an absolute value.

## Shutdown contract

- `SIGINT`/`SIGTERM` reach `NodeRuntime.runMain`, which interrupts the `serve` fiber. The finalizer first calls `beginDrain` (so `/health` turns 503) and waits `SHUTDOWN_DRAIN_DELAY` (default 0), then stops listening. srvx's own signal handler is disabled (`gracefulShutdown: false` in `src/server.ts`) so the scope owns the order: stop accepting, wait until no request is in flight (bounded by `SHUTDOWN_TIMEOUT`), close the remaining sockets with `close(true)`, release the database, flush the log buffer last. Do not re-enable srvx's handler — two handlers race the finalizers and can drop buffered log lines.
- **Drain on requests, never on `server.close()`.** `close()` resolves only when every *connection* has ended, and a socket that never completed a request (a browser's speculative preconnect, a half-sent header) is neither idle nor in flight, so awaiting it stalls for the whole timeout. `provideRuntime` counts requests (`src/kernel/http/inflight.ts`); the finalizer awaits `inFlight.drained`, then force-closes. The warning `Shutdown timed out with N request(s) still in flight` therefore means real work was cut off, not an idle socket.
- **The shutdown is announced by our own logs**: `Shutting down` (with the in-flight count when non-zero) when the finalizer starts, `Server stopped` when the last socket is closed. srvx's own messages are off (`silent: true`, `gracefulShutdown: false`), so removing these two lines makes a stop invisible.
- **`silent: true` hides srvx's listen failures**, so `serveHttp` awaits `server.ready()`; a busy port exits with status 1 and the error instead of idling.
- **How it was verified** (needs a socket, so not in the sandbox): spawn `node src/main.ts serve`, hold an idle socket / a half-sent header / a half-sent body open, send `SIGTERM`, time the exit. Idle and half-header sockets exit in ~10 ms; a body that finishes during the drain is answered (201) and the process exits when it ends; a body that never finishes waits `SHUTDOWN_TIMEOUT` and logs the warning.

## CLI contracts

- **Commands are flat, colon-named**: `serve`, `config:generate`, `openapi:generate`, `migrate:up`, `migrate:down`, `migrate:status`, `migrate:reset`, `migrate:seed` (`src/command/`, wired in `cli.ts`). One file per command; `helper.ts` holds the shared CLI output helpers (`print`, `printWarning` — plain console output, no timestamp/level prefix) and the destructive-op confirmation (`confirmDestructive`).
- **Destructive commands** (`migrate:down`, `migrate:reset`) prompt via `Prompt.Confirm`; `--force` skips the prompt, and a non-TTY session without `--force` refuses to run (`src/command/helper.ts`). Keep this pairing on any new destructive command.
- **`openapi:generate`** writes `docs/openapi.json`, the OpenAPI 3.1 description of `/api`, derived rather than written: a handler built by `defineHandler`, `definePagedHandler` or `defineMessageHandler` records what it declared (`documentHandler` in `handler_doc.ts`: kind, `summary`, `params`, `query`, `body`, `response`, `status`), `defineRouteGroup` can be read without an app (`routesOf` runs a group's `routes` callback against a recorder, nested groups included; `RouteTable` is the narrow set of methods a group may use), and `buildOpenApi` (`openapi.ts`) turns the schemas into JSON Schema (`Schema.toJsonSchemaDocument`, the encoded side, so a query is strings) wrapped in the response envelope, with one shared `ApiError` as every operation's `default`. `apiModules` (`routes/route.ts`) is the one list of modules under `/api`, used by the server and the document alike. A route whose handler declared nothing is an error, not a gap. Descriptions come from `.annotate` / `.annotateKey` on the schemas. `docs/openapi.json` is exempt from `oxfmt` (the generator writes the bytes), `openapi.test.ts` compares it with the generator, and CI runs `--check`; regenerate with `pnpm app openapi:generate --overwrite --force` after a route or schema change. Both generators share `generated.ts` (the flags, the check, the confirmed overwrite).
- **`config:generate`** writes `.env.example` from `appConfig.specs`; A new file is created freely; replacing an existing one that differs needs `--overwrite` plus `confirmDestructive` (`--force` skips the prompt and is rejected without `--overwrite`). `--check` fails when the file is stale, `--stdout` prints. It refuses any real dotenv name (`.env`, `.env.local`, …) — dotenv files are never rewritten.
- **`--dry-run`** must not touch the database beyond reads (`getMigrationInfos`).
- **`serve --auto-migrate`** runs `migrateToLatest` before the server starts and never seeds (`src/command/serve.ts`). The command provides `AppLayer`; migrate commands provide `DatabaseLayer` (`src/database/layer.ts`, the driver chosen by `DATABASE_DRIVER`). `Effect.provide` with a layer is reserved for `main.ts` (lint rule `effecttsgo/strict-effect-provide`).
- `migrate:reset --seed` requires `--up`; `migrate:down --count` must be >= 1 — both enforced with `CliError.UserError` in the handler.
- `--to` on `migrate:up` takes a **migration name** (not a numeric version).

## Database contracts

- **Migrations are a static registry** (`src/database/migrations/index.ts`), not a directory scan: keys are `NNNNN_name` (zero-padded prefix, sorts in execution order), each file exports `up` (+ optional `down`). Registry keys must match the file's export binding; a new migration adds the file **and** registers it in `index.ts` — an unregistered file silently never runs.
- **Kysely owns the bookkeeping**: tables `kysely_migration` / `kysely_migration_lock`. Never hand-edit them; `migrate:status` reads state via `Migrator.getMigrations()`.
- **SQLite migrations are atomic and locked** (`NodeSQLiteAdapter` in `dialect/sqlite-dialect.ts`): `supportsTransactionalDdl` is true, so the migrator wraps the batch and its bookkeeping in one transaction, and the driver opens every transaction with `BEGIN IMMEDIATE`, so a second process waits for the write lock (up to the busy timeout) and then finds nothing pending. Kysely takes its own lock on the connection before the transaction starts, so it is not held and the adapter does not override it; a plain `BEGIN` reads first and fails at once with `database is locked` when the other process committed in between (`migration_race.test.ts` runs two real processes). A raw statement returns rows when SQLite says it has result columns (`explain query plan` works). `users` has an index on `(name, id)`; a new sortable column needs its own `(column, id)` index, and `user_query_plan.test.ts` shows how to assert it.
- **`migrateDown(steps)`** resolves the target name from the executed list and delegates to `migrateTo` (Kysely's `migrateDown` is one-step only) — `src/database/migrator.ts`. The DB must be reachable to compute the target.
- **Seeders are idempotent** by contract (`src/database/seeder.ts` registry; e.g. `onConflict doNothing`). A seeder that is not idempotent breaks every re-run (`migrate:reset --seed`, repeated `migrate:seed`).
- **Schema ownership**: `src/database/schema.ts` is the Kysely `Database` type (tables/columns used in queries); a migration changing the schema updates this type in the same change, or `typecheck` drifts from reality.
- **Two drivers, one contract.** `DatabaseService` (`src/database/service.ts`) is the only thing repositories see: `db`, `query`, `read`, `ping`. `DATABASE_DRIVER=sqlite` builds it over `node:sqlite` (`sqlite.ts`, `SqliteDatabaseLayer`); `d1` builds it over a Cloudflare D1 binding (`d1.ts`, `D1DatabaseLayer`, needs the `D1Binding` service). Node picks one in `database/layer.ts` (`DatabaseLayer`); the Worker wires D1 itself in `src/worker.ts`. `makeDatabaseService` is shared, so query/read/ping behave the same.
- **One Vite plugin, two platforms; one script does the rest.** `vite.config.ts` is plain Vite configuration: `server` and `preview` (`host` / `port` from `HOST` / `PORT` through `loadEnv(mode)`, so the environment, `.env`, `.env.local` and the mode's files, in that order; default `127.0.0.1:3000`; `strictPort`) and `plugins: [edgy({ mode })]`. **Anything the user's config sets wins over the plugin**, which only fills in what is unset (`withDefaults`), so `server.*`, `preview.*`, `build.*`, `resolve`, `define`, more plugins and the command line (`--port`) all keep working as on any Vite project; the plugin owns no `server` setting. `edgy` (`builder/edgy.ts`) returns the plugins in a fixed order: `edgy:shared` first (`enforce: 'pre'`: `appType: 'custom'`, the output directories from `OUT_DIR` and `CLIENT_DIR`, and `MARKO_DEBUG=false` for a build, which has to be set before Marko's own `config` hook reads it, because Marko only optimizes in Vite's `production` mode and `--mode worker` is not that), then Marko, vanilla-extract, then the platform's. **The platform is Vite's `--mode`**: `platformOf` returns `worker` for `--mode worker` and node for every other mode. Not `--target` (Vite's language level for `vite build`) and not a custom flag: Vite refuses an option it does not know (`CACError: Unknown option`) before it reads the configuration, so `vite --platform=…` cannot work; mode is also what selects `.env.worker`. Settings a plugin supplies are **defaults under the user's** (`withDefaults`: `mergeConfig(defaults, config)` written back into the config object), never returned from the `config` hook, because a returned value overrides the file and the command line and `pnpm compile` could not change the output directory or format. Node (`builder/node.ts`): `edgy:node` sets `ssr.noExternal: true` (`command === 'build'` only: under `vite` the runner leaves `node_modules` to Node), `builder: {}` (so `vite build` builds every environment: the server first, the browser second, because `@marko/vite` learns each page's browser entries from the server build and patches `__MARKO_MANIFEST__` into the server chunks that need it; no `--app` flag), `target: 'node24'`, `assetsDir: 'chunks'`, the entry `src/main.ts` as `index.mjs` and a shebang banner; `devServerPlugin`; `nodeOutput` (`builder/output.ts`: `package.json` is emitted as an asset in the SSR environment's `generateBundle`, and the executable bit is set in the client environment's `closeBundle`, the first moment the file is final, since Marko patches it while the browser side is built; a Worker build has no `index.mjs` and gets neither); `nodeOutput` also refuses a build whose run-time dependencies ship a native addon (`builder/native.ts`: the bundle inlines every package, which cannot load a `.node` file); `nodePreview` (`builder/preview.ts`: `configurePreviewServer`, registered directly so it precedes Vite's static handler and the build output is never served as files; it starts the built server as `pnpm start` does on a free port and proxies the preview address to it, kills it when the preview closes, and fails with "run `pnpm build` first" when `dist/server/index.mjs` is missing; Vite's preview does not build). Worker (`builder/worker.ts`): `edgy:worker` (`builder.buildApp` writing Marko's order out so the Cloudflare plugin does not build the Worker twice; a plain error when `wrangler.jsonc` is missing), `releaseSsrExternal` (vanilla-extract sets `ssr.external`, the Cloudflare plugin refuses it), then `cloudflare()`, imported only for this platform; `CLOUDFLARE_LOAD_DEV_VARS_FROM_DOT_ENV=false` is set first (the plugin would otherwise read `.env.local` over the `wrangler.jsonc` vars and copy it into `dist/worker/.dev.vars`; a Worker's local overrides are `.dev.vars`). Minification is Vite's `--minify` (it applies to the server; the browser assets are always minified); there are no custom build flags. **`wrangler.jsonc` is the only source of the Worker's settings**, `DATABASE_AUTO_MIGRATE` included, for `dev`, `preview` and `deploy` alike. `pnpm run deploy` is `pnpm build --mode worker --minify` then `wrangler deploy`, so what `preview --mode worker` runs is what `deploy` ships. `pnpm compile` is the one script (`builder/compile.ts`): the same configuration with overrides (one CJS file: `format: 'cjs'`, `codeSplitting: false`, no banner, `import.meta` defined as `({})`) in a temp directory, then Node's `--experimental-sea-config`, a copy of `node`, and postject; its settings are constants in the script. The edge cases are covered by `tests/platform.test.ts`, `tests/node_output.test.ts`, `tests/vite_config.test.ts` (the address, env, command-line and user-config precedence, platform selection; the Worker case runs in a child process because its lazy `import()` needs Vite's default config loader, not a test runner's, and `configLoader: 'runner'` fails the same way) and `tests/dev_server.test.ts`; `nodePreview` was not exercised (it needs a port).
- **Never import a Node-only module from the Worker's import graph.** `src/worker.ts` reaches `app.ts`, `services.ts`, `database/d1.ts`, `database/service.ts`, `observer/` and `kernel/`; none may import `node:sqlite`, `layers.ts`, `database/layer.ts`, `database/sqlite.ts`, `server.ts` or `@effect/platform-node`. A violation breaks the Worker bundle (`pnpm preview --mode worker` and `pnpm dev --mode worker` fail to start).
- **SQLite connection lifecycle** lives in `SqliteDatabaseLayer`: opens `node:sqlite` once per scope, creates the parent directory, destroys on scope close. Nothing else may open a connection. On open it sets a 5 s busy timeout and `journal_mode = WAL` (not for `:memory:`), so `migrate:*` and the server can share one file; WAL leaves `-wal`/`-shm` files next to the database.
- **`--remote` points the migrate commands at the real D1 database** (`migrate:up`, `migrate:down`, `migrate:status`; `remoteFlag` and `announceRemote` in `command/helper.ts`). `Command.provide` takes the layer as a function of the parsed input, so the flag reaches `databaseLayer({ remote })` (`database/layer.ts`), which forces the D1 driver. `d1BindingNodeLayer` (`database/d1_node.ts`, Node only: `d1.ts` is shared with the Worker bundle and must not import `node:fs`) writes a copy of the project's Wrangler configuration beside it (`wrangler.remote-<pid>.tmp.json`, JSONC read by `parseJsonc`, the binding named by `D1_BINDING` marked `remote: true` by `withRemoteD1`, removed when the scope closes) and starts `getPlatformProxy({ configPath, remoteBindings: true })`, which needs the Cloudflare login. `migrate:reset` and `migrate:seed` do not take it, on purpose: production data is never wiped or filled from the CLI. The path was exercised as far as Wrangler's own auth demand (`CLOUDFLARE_API_TOKEN` in a non-interactive run); a run against a real account has not been seen. Concurrent isolates under `DATABASE_AUTO_MIGRATE` can still race, which is why production migrates first.
- **D1 specifics.** The dialect (`dialect/d1-*.ts`, adapted from `kysely-d1`, MIT) declares its own `D1Database` type instead of `@cloudflare/workers-types`. D1 has no interactive transactions, so `transaction` fails with `DatabaseError` there. Kysely's SQLite introspector reads columns through `pragma_table_info`, which D1 rejects (`SQLITE_AUTH`) and which breaks the migrator; `D1Introspector` lists tables from `sqlite_master` only, with empty `columns` — anything needing column metadata must not run on D1. `DATABASE_AUTO_MIGRATE` applies migrations at Worker start; isolates starting together can race on the first migration, so `wrangler.jsonc` sets it `true` (a new D1 needs no separate step, and `dev`, `preview` and `deploy` agree) and a deployment whose schema exists turns it off with `pnpm run deploy --var DATABASE_AUTO_MIGRATE:false`.
- **D1 on Node is local only.** `D1BindingNodeLayer` (in `src/database/d1.ts`, next to the portable layer) gets the binding from wrangler's `getPlatformProxy`, which reads the same `wrangler.jsonc` and `.wrangler/` state as `wrangler dev`: `DATABASE_DRIVER=d1 pnpm app migrate:up` prepares what `pnpm dev --mode worker` and `pnpm preview --mode worker` serve. `wrangler` is imported through a variable (`WRANGLER`) on purpose: a literal import is followed by the bundler and adds ~20 MB (wrangler, miniflare, sharp) to the build (`/* @vite-ignore */` silences Vite's warning for the same reason).
- **There is no `transaction` on the service**, on purpose. Kysely's `transaction().execute` takes no signal, so a callback that never settles would hold the single SQLite connection and no cancellation could free it, and D1 has none. The first endpoint that needs one adds it with a bound (a deadline, and a `signal` its callback must honour) rather than the old unbounded form. The driver's own transactions (`BEGIN IMMEDIATE`, used by the migrator) remain.
- **The connection caches prepared statements** (`NodeSQLiteConnection`, 128 entries, least recently used evicted): Kysely emits the same SQL text for the same query shape, so `prepare` runs once per shape, not per call. Measured on a laptop at about 3 µs saved on a 5 µs primary-key read (`findById`), most of its cost. There is no mutex of our own: Kysely's `RuntimeDriver` serialises a single-connection adapter, and `DatabaseService.query` runs through `db.connection().execute(run, { signal })` on `node:sqlite`, so a query still waiting when its request is cancelled never runs (a `504` must not be able to create the row, which the client's retry would create again). A `transaction` callback cannot be cancelled that way and must not outlive its request.
- **Bounded work per request.** Lists are keyset-paged, so no request scans past the rows it returns. The repository stores `email` lowercase and `users_email_lower_idx` (migration `00000`) makes two spellings one user. `SqliteDatabaseLayer` runs WAL with `synchronous = NORMAL`. `HOST` defaults to `127.0.0.1`; a container sets `0.0.0.0`. A refused destructive CLI command (no terminal, no `--force`) is a `UserError`, so it exits non-zero. The catch-all is registered for every method but `HEAD`, because h3 serves a `HEAD` from the `GET` route only when no other route matches it first. The in-flight count (`provideRuntime`) ends when a response's body ends, is cancelled or fails, not when the handler returns, so a drain waits for streamed pages; every body is a stream, so a test that does not read a response leaves its request counted. `GET /health` shares one database round trip for a second (`Effect.cachedWithTTL`, failures included). A Worker that cannot build its app answers `503` through `startupFailureResponse` (the error envelope under `/api`, plain text elsewhere, a `req_` id also written to the Worker's log with the redacted cause), since there is no logger or error hook to use; the next request retries the build. A one-shot CLI command runs with `OTEL_SDK_DISABLED=true` unless set (`main.ts`; only `serve` exports telemetry), because exit would otherwise wait on the collector; the development OTLP ingestion key is refused with a collector that is not local (config check). The PROXY reader keeps an `'error'` listener on a socket until the header is read, since a reset in that window would otherwise crash the process.
- **The driver is synchronous** (`node:sqlite`): every query blocks the event loop for its duration. Fine for this workload; a long query or migration stalls requests, which is the known ceiling of the single-process design.
- **Uniqueness violations are a domain error.** `isUniqueViolation` (`src/database/service.ts`) recognises SQLite codes 2067 and 1555 on the `DatabaseError` cause (`node:sqlite`) and the text `UNIQUE constraint failed` (D1, which reports no code); the repository turns them into `Conflict`. Other constraint failures stay `DatabaseError` until a route needs them mapped.
- **Queries go through `DatabaseService.query`**, which maps any rejection to `DatabaseError`. Repositories, the migrator and seeders do not call `Effect.tryPromise` themselves. **Reads use `DatabaseService.read`**: identical on `sqlite`, but on D1 (`retryReads`) a transient failure — message matching network connection lost, storage operation timeout, overloaded, temporarily unavailable, timed out, `SQLITE_BUSY`, locked (`isTransientFailure`) — is repeated up to twice with jittered exponential backoff (50 ms base), logged at `Warn`; deterministic failures (constraint, no such table) are not. Never pass a write to `read`; the request timeout still caps the total.

## Development services

- **`compose.yaml` (repo root) runs what the app talks to, not the app**: ClickStack (`clickstack`, the all-in-one HyperDX image: UI on 8080, OTLP/HTTP on 4318; gRPC is deliberately not published), a one-shot `clickstack-init`, and Valkey (`valkey`, 6379, password `securedb`). Scripts: `compose:up` / `:down` / `:restart` / `:cleanup` (cleanup also deletes `./.storage`, where the services keep their data; `/.storage/` is git-ignored). Host ports are variables (`CLICKSTACK_UI_PORT`, `OTLP_HTTP_PORT`, `VALKEY_PORT`) because another stack on the machine may hold 8080, 4318 or 6379.
- **ClickStack has no collector pipelines until a team exists**, and a team exists only after someone registers; the collector then enforces an ingestion key. `clickstack-init` registers the development account through `POST /api/register/password` (409 = already there is fine) and `INGESTION_API_KEY` (honoured by the all-in-one image only) fixes the key the collector accepts, so telemetry works from the first `compose:up` with no clicking. The init waits for health by retrying (`depends_on: service_started`), because `service_healthy` would hold `up --detach` for a minute. Never reuse these credentials or key outside development.

## How to change it

- **New module / endpoint**: `src/modules/<resource>/` with `<resource>_schema.ts` (entity, request and response schemas, and the table type merged into `Database`; a new table also needs a migration + registry entry), `_repo.ts` and `_service.ts` (each a `Context.Service` with `static layer`; the service declares itself in `HttpServices`), `_handler.ts` (one `defineHandler` — or `definePagedHandler` for a collection — per endpoint; declare `params`/`body`/`query`/`response`), `_routes.ts` (a `defineRouteGroup`) → add the layers to `src/services.ts` and register the routes inside `apiRoutes` in `src/routes/route.ts` → a test beside the code → `docs/api-endpoint.md` row in the same commit.
- **New page**: `app/pages/<name>.marko` (+ `app/tags/*.marko`, `app/styles/*.css.ts` as needed) → `<module>_pages.ts` with a `definePageHandler` (lazy `template`) and a `defineRouteGroup` → register the group in `pageRoutes` in `src/routes/route.ts` → a test beside it (HTML, headers, a failure) → `pnpm typecheck` (runs `mtc`) → `docs/api-endpoint.md` row and, for a new concept, `docs/frontend.md` in the same commit.
- **New CLI command**: `src/command/<name>.ts` (`Command.make` + flags + handler) → register in `command/cli.ts` `withSubcommands` → `docs/commandline.md` entry in the same commit. Destructive? Add `--force` + `confirmDestructive` (`src/command/helper.ts`).
- **New config key**: add a field (`text`, `port`, `int`, `flag`, `milliseconds`, `ratio`, `secret`, `choice`, `choiceList`, `logLevel` from `src/kernel/config/field.ts`) to the section file in `src/kernel/config/` that owns the concern, with its default and description; read it as `(yield* ConfigService).<section>.<key>`. The same declaration feeds `.env.example`: run `pnpm app config:generate` and commit the result (a test fails when the file is stale) → `docs/configuration.md` row in the same commit. **New concern**: one new file exporting `<name>Config` (a `group` of fields with a `title`) and its inferred type, plus one line in `appConfig` in `config/service.ts`; cross-field checks go in the group's `transform` (CORS credentials with a wildcard origin fails at startup in `cors.ts`). A secret uses `secret()` (`Redacted`); its optional third argument is a development default for a service of the Compose stack and is written to `.env.example`, so it must never be a real credential.
- **Durations in configuration are whole milliseconds** (`milliseconds()`, with a `min`): `REQUEST_TIMEOUT=30000`. One unit, no suffix to read; `30 seconds` is refused at startup with a message naming the variable and the unit (parsed as text first, because Effect's integer parser would only say "expected a finite number"). The field still parses to a `Duration`, so consumers are unchanged. Variable names carry no `_MS` suffix, so every description and the generated example say `milliseconds`.
- **New migration**: `src/database/migrations/NNNNN_name.ts` exporting `up`/`down` → register in `migrations/index.ts` → run `pnpm app migrate:up`.

## Traps

- **Browser tests run under Playwright Test, not Vitest.** `e2e/*.spec.ts` (end-to-end) and `src/**/*.test.ts`, `tests/**/*.test.ts` (unit and integration) are told apart by suffix and by runner. Two attempts to run them under Vitest failed on the same fact: Vitest's browser mode runs the test file inside the browser on Vitest's own origin, so the server-rendered pages, their per-response CSP nonce and headers cannot be the page under test; and Playwright's library driven from Vitest has no UI mode, trace viewer or fixtures, which the owner wanted. `playwright.config.ts` starts the production build (`webServer`) and defines the four browser projects; the scenarios sit in `e2e/screens/`, one spec per page, and reach the page through its page object in `e2e/fixtures/`, with helpers in `e2e/utils/` and static inputs in `e2e/test-data/` (`users.json` must match the seeders: change one, change the other); a check every page needs (no policy violation, no console error) is `expectCleanLoad`, called from each page's spec rather than kept in one cross-page file. The checks that need a browser: hydration (the filter on `/users` narrows the list only once the page's script has run), the CSP (`securitypolicyviolation` events from `e2e/utils/policy.ts`, and an un-nonced inline script that must be blocked), the pager and the HTML-versus-JSON error split. CI installs Chromium (`pnpm e2e:install`) and runs `pnpm e2e --project Chromium`. The Worker build is not under test here.
- **Tests are Vitest with `@effect/vitest`** (`pnpm test`, files `src/**/*.test.ts` beside the code, shared helpers in `tests/`: `app.ts` (`makeTestApp`), `cache.ts` (`fakeBacking`, a shared-store stand-in that can fail or hang; `cacheEnvironment`), `ids.ts` (`MISSING_USER_ID`, `userRow`), `d1.ts` (`fakeD1`, counts statements, can inject transient read failures), `collector.ts` (`startCollector`, an in-process OTLP receiver passed as `makeTestApp(env, { fetch })`, so no port is opened and no global is stubbed — Effect caches the default `fetch`, which would leak between tests). `makeTestApp` builds the real app over an in-memory database and is called with `app.fetch`; the app's `console.log` lines (a test that raises `LOG_LEVEL`, or fails a request on purpose, makes some) are kept in `TestApp.logs`, not printed, and a test that needs another runtime builds it with `Logger.layer([])` for the same reason. CLI commands are tested through `runWith` (`src/command/cli.test.ts`) over a temporary SQLite file, with `console` spied and `--force` standing in for the prompt (a test run has no terminal). Effect tests use `it.effect` (TestClock by default) or `layer(...)(name, (scoped) => …)` to share a layer; never `Effect.provide(layer)` inside a test (lint `strict-effect-provide`) and never real `setTimeout` waits. Pass environment overrides the way an operator would (`makeTestApp({ RATE_LIMIT_MAX: '2' })`). Code outside Effect that reads `Date.now()` (the memory rate limiter's window) is not moved by TestClock; use Vitest's fake timers there. A green suite does not exercise the built bundle, the dev launcher or workerd: before claiming a change works also run `pnpm build` + `node dist/server/index.mjs serve`, `pnpm dev` for anything in `app/` or the dev wiring, and, if the Worker's import graph, the pages or the D1 path changed, `pnpm preview --mode worker`. A sandbox that forbids port binding rejects `serve` and `wrangler dev` with `EPERM`.
- **Edit races**: never batch multiple `edit_file` calls to the same file in one parallel block — one edit is silently lost. Sequential per file, verify after.
- **`exactOptionalPropertyTypes` is on**: optional properties in response/error types must be explicitly `| undefined`-compatible; Effect `Option` values from `Flag.optional` need `Option.isSome` before `.value`.
- **Effect v4 vs v3 docs**: this repo is Effect **v4** (`effect@4.0.5`) — v3-era APIs (`Effect.zipRight` as a standalone combinator name, old `Command`/`Prompt` shapes) do not match; the pinned `node_modules` types are the truth.
- **workerd forbids I/O, timers and random values at module load.** Anything like `crypto.randomUUID()`, `setTimeout` or `fetch` runs lazily (inside a layer or a handler), never at the top level of a module the Worker imports: `pnpm preview --mode worker` fails to start with "Disallowed operation called within global scope" otherwise (it did, for the telemetry instance id).
- **workerd is not Node.** `AsyncLocalStorage.enterWith` is not implemented (use `run`), `process.stdout` is not the log sink, there is no socket address, and `node:sqlite` does not exist. Anything shared with the Worker must be checked with `pnpm preview --mode worker`.
- **`pnpm app <command>` is plain Node** (`node ./src/main.ts`, native type stripping): migrations, `config:generate` and the rest need no Vite and run exactly as the built binary does. `serve` belongs to production (`node dist/server/index.mjs serve`, `pnpm start`); development is `pnpm dev`.

## Plan documents

A plan (`.llms/plans/plan-YYYYMMDD_HHMM.md`) is a contract with fixed shape — frontmatter (`status`, `updated`, `phases` with per-phase `status`/`note`), Objective, Current state (verified file:line facts), Decisions (dated, rejected alternatives named), execution rules, Phases (each with an objectively checkable validation line and a suggested commit message), test matrix, out-of-scope. It executes only on the owner's explicit instruction ("continue with phase N"); one atomic commit per phase; after the last phase, stop and recommend the closing commit message — never commit it unasked. Full spec: the `agent-docs` skill.
