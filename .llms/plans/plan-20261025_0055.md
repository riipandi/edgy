# Replace the node:sqlite driver with Turso

## Objective

The database driver becomes Turso's own stack, and Node's built-in `node:sqlite` leaves the tree:
`@tursodatabase/database` (embedded, native) for a local file, and
`@tursodatabase/serverless` (SQL over HTTP, pure JS) for a remote Turso database. Both are Turso SDKs;
`@libsql/client` is never added. `src/database/dialect/sqlite.ts` is deleted and replaced by
`src/database/dialect.ts`, a Kysely dialect adapted from `tursodatabase/kysely-libsql` — same shape
(`SqliteAdapter`, `SqliteIntrospector`, `SqliteQueryCompiler`, a driver whose connection executes
compiled queries) with the libsql client swapped for a Turso executor.

The configuration loses `DATABASE_DRIVER` (nothing else was ever selectable) and `DATABASE_PATH`, and
gains `DATABASE_URL` — one variable that resolves to a local database or a remote one — plus an optional
`DATABASE_TOKEN` for the remote transport.

## Engine probe results (phase 1, verified on `@tursodatabase/database@0.8.3`)

- **`prepare()` is synchronous at runtime but typed `Promise<Statement>`.** `db.prepare(sql)` returns a
  `Statement` directly — `db.prepare(sql).then` is `undefined` and `.run()` throws
  `TypeError: … .then is not a function`. `await db.prepare(sql)` is the shape that satisfies both the
  types and the runtime, so the dialect uses it. `Statement.all/run/iterate/get` are genuinely async.
- **Parameters normalize.** `all([1, 2])`, `all(1, 2)`, `db.all(sql, [1, 2])` and `db.all(sql, 1, 2)` all
  bind two parameters — so Kysely's `statement.all(parameters)` works as-is, with no spread adapter.
  `null`, `bigint` and `boolean` bind; `Object.freeze`d arrays are accepted.
- **`run()` returns `{ changes, lastInsertRowid }`** — not libSQL's `rowsAffected`/`lastInsertRowid`
  pair. The executor maps `changes → numAffectedRows` and `lastInsertRowid → insertId`. `select
  last_insert_rowid()` and `insert … returning` both work.
- **`Statement.reader` and `columns()` are synchronous**, so the local executor picks `all` vs `run`
  without a round trip.
- **Pragmas:** `{ timeout: 5_000 }` sets `busy_timeout` to 5000; a fresh file is already
  `journal_mode = wal`; `foreign_keys` is **0** by default, so `pragma foreign_keys = on` stays.
- **`connect()` does not create a missing parent directory** — it fails with
  `I/O error (statfs shared WAL coordination path): entity not found`. The `mkdirSync` + `chmod` in the
  old `openDatabase` stay.
- **The existing schema replays completely.** A fresh database built by the current migrations
  (`node:sqlite`) yields 42 DDL objects; all 42 replay into Turso — `STRICT` tables, every index, the
  `datetime('now')` defaults — and inserts into `users` and `rate_limits` succeed.
- **A statement issued while `BEGIN` is open executes immediately** (0.08 ms) and sees the transaction's
  uncommitted rows. This is the evidence for D4: the engine serializes single statements, not a
  transaction window, so the driver's lock is required, not defensive.
- **No experimental flag is needed.** `strict`, `views`, `triggers`, `generated_columns` and
  `without_rowid` are accepted as `experimental` values but the schema needs none of them (STRICT and
  indexes work without a flag; generated columns do require `generated_columns`, and the tree uses
  none). `multiprocess_wal` is rejected for `:memory:`.
- **Errors are `SqliteError` with `code: 'GenericFailure'`** and a message like
  `step failed: Parse error: no such table: …`.
- **Prepare costs ~8 µs**: 200 prepared `all()` calls take 0.5 ms against 2.2 ms for 200
  prepare-per-call queries — the same order as the 7.22 µs measured for `node:sqlite`, so D8 (no
  statement cache) is behavior-neutral.
- **Trap — copying a WAL-mode database needs its sidecars gone.** Copying only `app.db` leaves a stale
  `-wal` next to the destination, and the copy replays it: the probe's first run reported tables that
  existed only in the previous copy. Any compatibility probe (and this plan's own test fixtures) must
  delete `-wal` and `-shm` with the file.

## Decisions

- **D1 (2026-10-25): two transports behind one dialect, both Turso packages, never `@libsql/client`.**
  `DATABASE_URL` selects the transport: `file:…` URIs and bare paths take `@tursodatabase/database`,
  `libsql://`, `turso://`, `https://` and `http://` take `@tursodatabase/serverless`. The cost: two
  dependencies instead of one, and a small executor adapter per transport; the benefit: the configuration
  the owner asked for (one URL, optional token) is honest — a single package cannot reach a remote
  database at all.
- **D2 (2026-10-25, revised): a local database is a `file:` URI, and the URL contract is decided in one
  place.** `resolveDatabaseTarget(url)` in `src/kernel/config/database.ts` returns either
  `{ kind: 'local', path }` or `{ kind: 'remote', url, token }`. Local forms follow RFC 8089 as the
  file-URI scheme defines them: `file:/path` and `file:///path` reach this host, `file://localhost/path`
  too, `file:./relative/path` resolves against the working directory, and the path part is
  percent-decoded (`%20` is a space). `file://other/path` names another machine a local engine cannot
  open, and `file://path` — two slashes and no path separator — is the form the scheme calls invalid, so
  both are errors rather than a guess. A bare path without a scheme stays accepted as the one convenience
  form (`storage/data/app.db`), because it can only mean a local file. Remote forms: `libsql://`,
  `turso://`, `https://`, `http://` — the first two are what `turso db show --url` prints (SQLite-type and
  TursoDB databases respectively), and the serverless client normalizes both itself, so the scheme passes
  through untouched. Anything else — `postgres://`, `mysql://`, an empty string — is a configuration error
  naming the accepted forms, never a silent fallback to a local file. `:memory:` is **rejected with a
  message**: the driver has no in-memory mode, and treating the token as a filename would create a stray
  `:memory:` file. `DATABASE_TOKEN` with a local URL is ignored with one warning log line, so a token
  that does nothing is never silent.
- **D3 (2026-10-25): the dialect is `kysely-libsql`'s shape over a Turso executor.**
  `src/database/dialect.ts` exports `TursoDialect` (`createAdapter` → `SqliteAdapter`,
  `createIntrospector` → `SqliteIntrospector`, `createQueryCompiler` → `SqliteQueryCompiler`,
  `createDriver` → `TursoDriver`), `TursoDriver` and `TursoConnection` (`executeQuery`, `streamQuery`,
  `beginTransaction`, `commitTransaction`, `rollbackTransaction`). The connection talks to a
  `TursoExecutor`: `execute(sql, params) → { rows, insertId, numAffectedRows }`, `begin`/`commit`/`rollback`,
  `close`. The local executor prepares and branches on `reader` (`all` vs `run`) — in-process, so
  prepare is free; the remote executor uses the compat client's `execute({ sql, args })`, one round trip
  per statement, which is the libsql client's own contract without the libsql dependency. The cost: one
  interface and two ~40-line implementations instead of one direct client call.
- **D4 (2026-10-25, revised after reading the pinned Kysely source): the driver adds no lock of its own —
  Kysely's `ConnectionMutex` already serializes a transaction window.** `SqliteAdapter` reports
  `supportsMultipleConnections = false` (`node_modules/kysely/dist/dialect/sqlite/sqlite-adapter.js`), and
  `RuntimeDriver` therefore wraps every `acquireConnection` in a `ConnectionMutex`
  (`dist/driver/runtime-driver.js:31,62-70`): the lock is taken before the connection is handed out and
  released in `releaseConnection`. `Kysely.transaction` runs the whole `BEGIN … COMMIT` inside one
  `provideConnection` (`dist/kysely.js:682-697`), so the mutex is held across the entire transaction and a
  concurrent statement waits. The engine hazard the phase-1 probe found (a statement inside an open `BEGIN`
  executes immediately, 0.08 ms) is therefore closed one layer above the driver. The cost: nothing — the
  dialect stays ~120 lines and owns no lock; the obligation is a test that proves the wait through Kysely,
  not through the raw driver. Rejected: a second mutex inside `TursoDriver` (double locking, and it would
  mask a regression in the Kysely contract we depend on); `transactionAsync` (callback scoped; Kysely's
  driver API is connection scoped).
- **D5 (2026-10-25, revised): the configuration is `DATABASE_URL` + optional `DATABASE_TOKEN`, and nothing
  else.** `DATABASE_DRIVER` is deleted — `choice('DATABASE_DRIVER', ['sqlite'])` described a choice that did
  not exist. `DATABASE_PATH` becomes `DATABASE_URL` with the default `file:./storage/data/app.db`, so the
  documented shape is the `file:` URI the scheme defines and the relative reference says plainly that it is
  relative to the working directory; `DATABASE_TOKEN` is a `secret()`. `DATABASE_AUTO_MIGRATE` is
  untouched. The cost: every deployment environment renames one variable; `.env.local` is the owner's file
  and is **not** rewritten by this plan — it is listed as a required owner edit.
- **D6 (2026-10-25): the native module stays external, and the guard learns one allowlist.**
  `--mode standalone` cannot inline a `.node` binary, so the Turso packages are excluded from `noExternal`
  and named in the leak guard's allowlist; `Dockerfile` copies the resolved
  `node_modules/@tursodatabase/**` next to `entry.js`, and the image keeps working. The cost: `dist/` is
  no longer self-contained, the README's "single file, zero native dependencies" claim is retired, and
  the image grows by the prebuilt binaries (~15 MB). Rejected: dropping standalone mode for the container
  (a bigger deployment change than the driver swap itself); the WASM build `@tursodatabase/database-wasm`
  (+43 MB, WASI-threads, browser-oriented).
- **D7 (2026-10-25): the telemetry label stays `store: 'sqlite'`.** The engine is still SQLite-compatible,
  and the label feeds the Grafana dashboards and `dependencyDuration` series. Renaming it to `turso`
  would silently empty every existing panel for no signal. The cost: the label names the engine family,
  not the npm package.
- **D8 (2026-10-25): no statement cache and no prepared-statement reuse in this plan.** The parked roadmap
  item (`.llms/roadmap/parked-unlocks.md`, "Kysely statement cache over `node:sqlite`") stays parked; the
  new dialect prepares per query exactly like the old one did. The cost: the migration is behavior-neutral
  on the query path, which is what makes it reviewable.
- **D11 (2026-10-25): the Postgres stub goes with the driver swap — this tree is single-engine.**
  `src/database/dialect-helpers.ts` exists only to branch between SQLite and Postgres
  (`detectDialect`/`isPostgres` via `PostgresAdapter`), and its three exports resolve to the SQLite arm for
  every caller in the tree: `modifyEndQuery` → `sql\`STRICT\``, `currentTimestamp` →
  `sql\`(datetime('now'))\``, `binaryType` → `'blob'`. `DatabaseDialectType = 'sqlite' | 'postgres'`
  (`src/database/adapter.ts:9`) has no consumer beyond that file, and `DependencyStore`'s `'postgres'`
  member (`src/observer/dependencies.ts:3`) labels a store that cannot exist. All three go: the migration
  files spell the SQLite DDL directly, the type union disappears, and the telemetry store union becomes
  `'sqlite' | 'redis'`. The cost: adding Postgres later means reintroducing the branch — accepted, because
  there is no plan for a second engine and a dead arm is worse than a future edit. Rejected: keeping the
  helpers as a "seam" (a seam with one arm is a branch nobody can exercise).
- **D12 (2026-10-25): the repository database, its migrations and its seeds may be reset during this
  plan.** The owner authorized `migrate:reset` and a fresh `migrate:up`/`migrate:seed` against
  `storage/data/app.db` for this working session, so the compatibility probe is no longer limited to a
  copy: the swap is verified by rebuilding the real database from the migration registry and confirming
  `migrate:status` lists four executed migrations and `migrate:seed` re-creates the sample users. The
  constraint that survives: nothing outside this repository's `storage/` is reset, and the Turso Cloud
  databases from D10 stay untouchable.

- **D9 (2026-10-25): the remote path is proven against a scratch Turso Cloud database in `default-ap`, and
  the unit suite stays offline.** Because the owner's machine is authenticated, the remote transport is
  exercised for real: a database named `edgy-turso-probe-<stamp>` is created with
  `turso db create <name> --group default-ap --wait`, a short-lived token with
  `turso db tokens create <name> -e 1d`, the probes run against it, and `turso db destroy <name>` removes
  it — created and destroyed inside the same phase, never left behind. `vpr test` still never touches the
  network: the remote spec stubs `globalThis.fetch`, so CI needs no credentials and a flaky network cannot
  red the suite. The cost: the validation steps are manual commands recorded in the phase note rather than
  assertions in the suite; the benefit: the transport, the token handling and the migration-over-HTTP path
  are proven against the real platform, which no stub can do.
- **D10 (2026-10-25): no pre-existing database is ever deleted, and the probe is the only thing that can
  be.** A `turso db destroy` runs only against a name this plan created (`edgy-turso-probe-<stamp>`),
  confirmed by the name check before the command is issued; a probe database that cannot be destroyed
  stays in the account and is reported to the owner instead of being retried against a wider target.
  `mapscoffee-dev`, `sosialink-stg` and `wilayah` are never connected to — not for a `select 1`, not for a
  token — never migrated, never destroyed. Tokens are created with an expiry and never printed into a
  transcript, a log, the ledger, or a commit; they travel through an environment variable only.

## Execution rules

- **Atomic commit per phase** is authorized; each phase's heading names its suggested commit message;
  self-serve commits are allowed during this plan's working session.
- **Execution waits for the owner's explicit "continue with phase N".** When the phases have all landed,
  the agent stops and recommends the closing commit message with its paths — it does not commit the
  closing state on its own.
- **No backward compatibility and no legacy code** — the owner's standing waiver for this early-stage tree:
  `src/database/dialect/sqlite.ts` is deleted, `DATABASE_DRIVER` and `DATABASE_PATH` disappear, the Postgres
  stub in `dialect-helpers.ts` goes, and no alias, fallback, or deprecation shim keeps any of them alive.
- **`docs/commandline.md` is out of scope** — no command changes in this plan; if a phase finds that it
  must change, the phase stops and asks.
- **Destructive commands may run against this repository's own database** — the owner authorized resetting
  `storage/data/app.db` and re-running migrations and seeds during this plan (D12) — **and** against temp
  databases under `/tmp` or a temp directory, **and** against Turso Cloud databases this plan created in
  the `default-ap` group. Nothing else is destroyed: no pre-existing Turso database (D10), no other path.
  The owner's `.env.local` is never rewritten.
- **The owner's parallel work is untouchable:** `src/App.tsx`, `src/Document.tsx`,
  `src/kernel/http/api.ts`, `src/observer/tracing.ts`, `.zed/settings.json` — no phase stages or edits them.
- **Per-phase validation runs before each phase's commit.**

## Explicitly out of scope

- **`@libsql/client`** — never added, at any phase; `@tursodatabase/serverless` replaces it for the remote
  path.
- **Turso Sync / embedded replicas** (`@tursodatabase/sync`) — a different deployment model (local writes
  with push/pull); it needs its own plan.
- **A live Turso Cloud database is used only as a scratch probe** — `edgy-turso-probe-<stamp>` in
  `default-ap`, created and destroyed inside the phase that needs it (D9). The owner's existing databases
  (`mapscoffee-dev`, `sosialink-stg`, `wilayah`) are never connected to, migrated, or deleted (D10), and
  the plan does not configure the application against them.
- **`vpr test` stays offline** — the remote spec stubs `globalThis.fetch`, so the suite needs no
  credentials and a network failure cannot red CI; the real round trip is a phase validation, recorded in
  the phase note and the handover.
- **Statement cache / prepared-statement reuse** — stays parked in `.llms/roadmap/parked-unlocks.md` (D8).
- **Renaming the telemetry `store` label** — `sqlite` stays (D7); only the unreachable `postgres` member
  is removed (D11).
- **The Turso engine's concurrent-write features** — the application keeps one connection and single-writer
  semantics; a pool is a separate design.
- **Any second database engine** — the Postgres stub is deleted rather than kept as a seam (D11); a future
  engine arrives with its own plan.
- **The owner's `.env.local`** — needs a one-line edit by the owner (`DATABASE_PATH` → `DATABASE_URL`);
  the plan flags it and does not touch the file.
