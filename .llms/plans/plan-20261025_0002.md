# Make `src/command` match `docs/commandline.md` — the fixes from audit-20261024_2346

## Objective

Close every finding of `.llms/audit/audit-20261024_2346.md`: the global `--log-level` flag must actually set the log level, `serve` must keep its graceful shutdown whatever the argv order, `migrate:up --to` must never roll a schema back, `generate:config` must refuse every real dotenv path including symlinks, and the shutdown log lines must match the document for both signals and both Redis stores. After execution the CLI behaves exactly as `docs/commandline.md` says, and a command test suite holds it there. The plan does not edit `docs/commandline.md` (owner's standing instruction) and does not add a feature, a flag, or a config key the document does not already name.

## Current state (verified in the tree, 2026-10-24)

- **The global flags are cloned, and the clone breaks identity checks.** `src/command/cli.ts:27-38` maps `GlobalFlag.BuiltIns` through `Object.assign({}, builtIn, { flag: Flag.withHidden(...) })` for `Wizard`, `Completions` and `LogLevel`. `Command.run` compares against the canonical objects by identity: `activeFlags.includes(GlobalFlag.LogLevel)` (`node_modules/effect/src/cli/Command.ts:3455`) decides whether the parsed value is installed as `References.MinimumLogLevel`, and `flag === GlobalFlag.Wizard` (`:3413`) decides the wizard path. A probe over the current `cli.ts` shape: `--log-level error` printed INFO, `--log-level error` with the untouched `GlobalFlag.BuiltIns` printed only ERROR; `--wizard` exits `0` doing nothing.
- **The fix is proven against this app's own layer graph.** A probe running `Command.runWith(cmd, { version })(args)` with `CliConfig.layer({ builtIns: [GlobalFlag.Help, GlobalFlag.Version, GlobalFlag.LogLevel] })` provided together with `CoreLayer` (`src/kernel/layers.ts`) suppressed INFO on `--log-level error`, accepted `--log-level Error` once the argv value was lowercased, and rendered `--log-level <all|trace|…>` under `GLOBAL FLAGS`. `--wizard` and `--completions` became unrecognized options.
- **`serve` is detected by the literal second token.** `src/main.ts:9` sets `const isServe = process.argv[2] === 'serve'`; the documented invocation `vpr app --log-level <level> serve` therefore takes the `NodeRuntime.runMain` branch. Measured: `serve --auto-migrate` + `SIGINT` → `shutting down (received SIGINT)` … `application terminated`, exit `0`; `--log-level info serve --auto-migrate` + `SIGINT` → no `shutting down` line, no `application terminated` line, exit `130`.
- **`migrate:up --to` is bidirectional.** `src/command/migrate-up.ts:36` passes the user's target to `migrateTo`, and Kysely resolves an already-executed name to `{ direction: 'Down' }` (`node_modules/.pnpm/kysely@0.29.7/node_modules/kysely/dist/migration/migrator.js:183-192`). Measured on a fully migrated database: `migrate:up --to 00002_create_identity_table` rolled back `00004` and `00003`, exit `0`; the same command with `--dry-run` printed `no pending migrations`, so the two paths already disagree.
- **The dotenv refusal is existence-gated.** `src/command/generate-config.ts:82-90` calls `fs.realPath` only when `fs.exists(target)` is true; `exists` follows symlinks, so a dangling `.env.example -> .env` reports false and `:117` writes through the link. Measured in an empty directory: `ln -s .env .env.example` then `generate:config` → `Wrote .env.example (32 variables)` and a real `.env` appeared. A live symlink is refused correctly.
- **Two flag rules drift from the document.** `src/command/generate-config.ts:76` rejects `--force` without `--overwrite` (`--force only applies together with --overwrite`, exit `1`) although the document presents `--force` as a modifier; `--stdout` returns at `:79` before every check, so `--stdout --check` silently ignores `--check`. `:24` renders the `--output` description without the documented default.
- **The second-signal rule holds only for the same signal.** `src/kernel/graceful.ts:8-16` registers `process.once` for both signals; after the first fires, the other `once` listener stays and its `resume` is a no-op. Harness with a 6-second drain: `SIGINT` → exit `0` after 6.5 s; `SIGINT`+`SIGINT` → exit by signal after 1.2 s; `SIGINT`+`SIGTERM` → exit `0` after 6.5 s.
- **The Redis stores log one line, the document promises the database's two.** `src/kernel/cache.ts:132` and `src/middleware/rate-limit.ts:126` register a single `closing redis …` finalizer; the client itself is closed by the `NodeRedis.layer` scope (`node_modules/@effect/platform-node/src/NodeRedis.ts:63`, `Effect.acquireRelease` → `client.close()`), which the consumer cannot observe. `docs/commandline.md` says a Redis-backed store "logs its close the same way" as the database's `closing database connection` + `database connection closed`.
- **No test covers the command surface.** `find src/command -name '*.test.ts'` returns nothing; the suite's 22 files live under `src/database`, `src/kernel`, `src/middleware`, `src/modules`, `src/observer`.
- **The finding record** is `.llms/audit/audit-20261024_2346.md` (F-01…F-10, status `in_review`, 9 verified / 1 unverified).

## Decisions

- **D1 (2026-10-25): the built-in global flags stay canonical — no clone.** `cli.ts` provides `CliConfig.layer({ builtIns: [GlobalFlag.Help, GlobalFlag.Version, GlobalFlag.LogLevel] })`, so `--help`, `--version` and `--log-level` are the documented global flags, `--log-level` appears in help, and `Command.run`'s identity checks (`Command.ts:3413`, `:3455`) keep working. The cost: `--wizard` and `--completions` disappear from the CLI (they were never in the document, and `--wizard` is already broken by the clone — it exits `0` doing nothing).
  Rejected: hide-by-clone, the current shape — measured to break both identity checks; hiding is not worth a dead setting.
  Rejected: build a fresh `GlobalFlag.Setting('log-level')({ flag: Flag.withHidden(...) })` — `Setting` mints a new service key per construction (`GlobalFlag.ts:137-145`) and `Command.run` only installs the canonical `GlobalFlag.LogLevel` value, so the level would be parsed and dropped again.
- **D2 (2026-10-25): the `--log-level` value is case-normalized in argv before the command runs.** `cli.ts` lowercases the token following `--log-level` and hands the array to `Command.runWith(rootCmd, { version })`, so `--log-level Debug` and `--log-level debug` both work — the same vocabulary `LOG_LEVEL` already accepts capitalized (`LogLevel.values`). The cost: one argv pass in our own file, and `Command.run` (which reads `Stdio`) is replaced by `runWith`.
  Rejected: replace the canonical flag with a case-insensitive one — `Command.run` parses the level from `GlobalFlag.LogLevel.flag` (`Command.ts:3456`), so the swap has to mutate a library object.
  Rejected: document the casing split instead — the two casings for one vocabulary is the footgun F-05 reports.
- **D3 (2026-10-25): `serve` is detected by parsing argv, not by position.** `cli.ts` exports the argv helpers (`normalizeArgs`, `subcommandOf`), and `main.ts` asks `subcommandOf(process.argv.slice(2))` whether the run is the server. The scan skips global flags and the value token of `--log-level`, so a flag value can never be mistaken for the subcommand. The cost: argv parsing exists in two places conceptually (ours and Effect's) — accepted, ours only needs to find the first positional.
  Rejected: `process.argv.includes('serve')` — a flag value equal to `serve` would flip the process into server mode.
  Rejected: an env marker set by the handler — the branch has to be decided before the program runs, since it selects the runtime.
- **D4 (2026-10-25): `migrate:up --to <applied>` fails instead of rolling back.** The command reads `migrationStatus` once, refuses a target whose `executedAt` is set (`migration '<name>' is already applied`), and only then calls `migrateTo`; the dry-run branch reuses the same status read, so both paths agree. The cost: an operator loses the accidental rollback path — that is what `migrate:down --count` and `migrate:reset` exist for.
  Rejected: keep Kysely's bidirectional behavior and document it — a forward-only command that drops tables without confirmation is the defect, not the documentation gap.
  Rejected: ask for confirmation on the down direction — two destructive commands with two confirmation flows for one intent.
- **D5 (2026-10-25): `generate:config` resolves the link chain before deciding, and its flag rules follow the document.** The dotenv check walks `readLink` from the requested path (dangling or not) to the final component and refuses when that basename is a real dotenv name; `--force` alone becomes a no-op instead of an error; `--stdout` combined with `--check` is rejected as contradictory; the `--output` description carries the documented default. The cost: a symlink chain is followed by us rather than by `realPath`, so the loop is bounded and stops at the first non-link.
  Rejected: `lstat` only on the immediate path — misses `.env.example -> .env.production -> .env`.
  Rejected: keep `--force` alone as an error — the document presents it as a modifier of `--overwrite`, not as an invalid combination.
- **D6 (2026-10-25): the shutdown path owns its signals and its Redis scopes.** `awaitShutdownSignal` installs one handler per signal, resumes on the first and force-exits with `128 + signum` on any later one (so `SIGINT` then `SIGTERM` exits immediately, matching "a second signal exits immediately"). The Redis stores acquire their client scope with `Effect.acquireRelease`, log `closing …` before closing that scope and `… closed` after, so both lines bracket a close we control. The cost: the rate-limit layer's dependency chain moves from `Layer.provide` into an explicitly built context — more code in two files, and the layer graph's ordering is now ours to keep.
  Rejected: relax `docs/commandline.md` to one line — the document is frozen for this plan and the two-line shape is what the database already does.
  Rejected: leave `NodeRedis.layer`'s own scope close and add a second finalizer — finalizers run LIFO within a scope, so no consumer-side finalizer can run after the client's.
- **D7 (2026-10-25): the command surface gets a real test module, not a mock.** `src/command/*.test.ts` drives `Command.runWith` with `CliConfig.layer`, `NodeServices.layer`, and a real SQLite database in a temp directory (per-test `DATABASE_PATH` through a `ConfigProvider`), plus temp directories for `generate:config`. The cost: the tests touch the filesystem and a database — they are slower than pure unit tests, and they must clean up after themselves.
  Rejected: call the handlers directly — the flags, defaults and exit paths are exactly what the audit found broken.
  Rejected: shell probes only — they were how the audit found the defects, and nothing re-runs them.

## Execution rules

- **Atomic commit per phase** is authorized; each phase's heading names its suggested commit message; self-serve commits are allowed during this plan's working session.
- **Execution waits for the owner's explicit "continue with phase N".** When the phases have all landed, the agent stops and recommends the closing commit message with its paths — it does not commit the closing state on its own.
- **No backward compatibility and no legacy code** — the owner's standing waiver for this early-stage tree: `--wizard`/`--completions` are removed outright, the old `process.argv[2]` check is replaced, and no shim keeps either alive.
- **`docs/commandline.md` is read-only in this plan** — the code is brought to the document, not the other way round. If a phase finds a genuine contradiction inside the document, it stops and asks instead of editing it.
- **Destructive commands may run only against temp databases** created under `/tmp` for the probes; the repository's `storage/` database is never reset, dropped, or seeded during validation. The `redis` compose service may be started (`docker compose up -d redis`) for the close-line probe.
- **The owner's parallel work is untouchable:** `src/App.tsx`, `src/Document.tsx`, `src/kernel/http/api.ts`, `src/observer/tracing.ts`, `.zed/settings.json` carry uncommitted edits from another session; no phase stages or edits them.
- **Per-phase validation runs before each phase's commit.**
- **E2E is recorded n/a for every phase** — the diff touches no HTTP surface, no SSR path, and no container entry point; the container's `HEALTHCHECK` line is re-probed in the final phase instead.
