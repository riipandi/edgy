# Single-file module registration + standardized API response envelope

## Objective

Two owner decisions land together because the second reshapes every endpoint the first plan
touches:

1. **Module registration** (carried over from the prior draft of this plan, 2026-10-26): a new
   module currently requires editing two scattered kernel files
   (`kernel/layers.ts` and `kernel/http/api.ts`) with no file named for the job. This plan
   consolidates both into one file, **`kernel/registry.ts`**. The owner asked for this exact name.
   It is a different shape from the `kernel/registry.ts` deleted by plan-20261026_1227 — that file
   was a hand-maintained list of per-module *service* dependencies the kernel assembled itself;
   this one re-exports what each self-contained module already assembled (`api`,
   `moduleServiceLayer`, `moduleHandlerLayer`) from one place, so a module stays self-wired and the
   kernel still only names it once. Reusing the filename is intentional, not a reversion.
2. **API response envelope** (new, 2026-10-26, chat): every `/api/*` response — success and error
   alike — adopts the envelope in `.llms/api-response.md` (`{status, message?, data?, metadata,
   links?}` for success; `{status, message, error, metadata}` for error), plus cursor-based
   pagination (`PaginationParams` query fields, `ApiPagination` metadata). The owner chose the
   **schema-level** design: each endpoint's declared `success`/`error` schema *is* the full wire
   shape (not a transport-middleware rewrite), so `openapi.json` stays accurate. This is a
   wire-contract change; the project is early-stage, so there is **no backward-compatibility shim**
   — the current bare-array success bodies and flat `{"_tag":"NotFound"}` error bodies are replaced
   outright, not versioned alongside the new shape.

## Current state (verified in the tree, 2026-10-26)

### Module registration (unchanged from the prior draft, file name updated)

- `src/kernel/layers.ts:4,22-24` imports `identityLayer` from `#/modules/identity/module.ts`
  directly; `src/kernel/http/api.ts:15,27-28,52-54` separately imports `UsersApi`/`usersHandlers`
  from the same module, builds the `HttpApi.make(...).add(...)` chain, and provides
  `usersHandlers(api)`. Two files, two different edits, for one new module.
- `.llms/rules.md:37` claims "there is no central registry … adding a module means extending its
  own `module.ts`, not editing a shared file," which `.llms/rules.md:38` immediately contradicts.
  The code matches line 38.
- `.llms/rules.md:37` and `.llms/architecture.md:26` describe the module's exported service graph
  as `layer`; the real export (`src/modules/identity/module.ts:10`) is `identityLayer`.
- `.llms/rules.md:25` places endpoint schemas in `module.ts`; the real location, matching
  `rules.md:38` and `architecture.md:15`, is `<name>_route.ts`.
- Effect v4's `HttpApi.add<const A extends NonEmptyReadonlyArray<HttpApiGroup.Constraint>>(...groups:
  A)` (`HttpApi.d.ts:59`) needs a tuple-typed argument list; a `tsc --strict` probe confirmed

- `HealthApi`/`healthHandlers` (`src/kernel/healthcheck.ts`) are kernel-native, not a feature

### API response envelope — current wire shapes and gaps (verified 2026-10-26)

- **Success today:** `user_route.ts:12-32` — `listUsers` returns `Schema.Array(UserResponse)`, a
  bare array, no pagination at all; `getUser` → `HttpApiSchema.WithHeaders(UserResponse,
  CacheHeader)`; `createUser` → `UserResponse` + `status(201)`; `updateUser` → `UserResponse`;
  `deleteUser` → `HttpApiSchema.NoContent`. None carry `status`, `metadata`, or `links`.
- **Error today:** endpoints declare `HttpApiError.NotFound | HttpApiError.Conflict |
  HttpApiError.ServiceUnavailable` — Effect's built-in tagged errors, encoded directly by HttpApi
  from the endpoint's `error` set. They carry no `code`/`retryable`/`details`/`debug` fields, so
  they cannot satisfy `ApiErrorBody` as they stand.
- **Defects today:** `src/middleware/error-response.ts` (full file) rewrites die-level causes
  (decode failures, unmatched routes, unhandled defects) under `/api/*` into flat `{"_tag":
  "HttpApiDecodeError",...}` / `{"_tag":"NotFound"}` / `{"_tag":"InternalServerError"}` bodies.
  Declared endpoint errors never reach this middleware — they are encoded upstream by HttpApi
  itself. The envelope therefore needs to cover two independent paths today: declared errors (via
  the endpoint's `error` schema) and defects (via this middleware) — the owner's "no legacy code"
  instruction means both converge on one `ApiErrorBody` shape, not two.
- **`CacheStatus`** (`src/kernel/cache.ts:17-21`) is `'hit' | 'miss' | 'bypass' | 'disabled'` —
  four values. `.llms/api-response.md:32` currently documents three (no `disabled`). Decision D7
  below extends the spec to match the code.
- **`request_id`** (`src/middleware/request-id.ts:24-35`) is set only as the `x-request-id`
  **header** — there is no Context tag a handler can read it from today.
- **`trace_id`** has no existing source anywhere in the tree. `HttpMiddleware.tracer`
  (`src/middleware/tracer.ts:6-8`) creates the OpenTelemetry span; nothing reads
  `Effect.currentSpan`/the span's trace id back out as a string. This must be new code.
- **Rate-limit numbers** (`src/middleware/rate-limit.ts:217-260`) are set only as
  `ratelimit-limit`/`ratelimit-reset`/`ratelimit-remaining` **headers**; the `ConsumeVerdict`
  computed in-process (`:27-32`) is never placed in Context for a handler to read.
- **Effect v4 has no generic post-handler response-transform hook.** `HttpApiBuilder`'s exports are
  `layer`, `group`, `handler`, `endpoint`, `securityDecode`, `securitySetCookie` — nothing runs
  after a handler's effect resolves and before encoding to auto-wrap the return value.
  `HttpApiSchema.WithHeaders` (`HttpApiSchema.d.ts:565-641`) only splits `{body, headers}` at
  encode time; it cannot inject a `metadata` object into the body. **Confirms the owner's choice:**
  the envelope must be a literal schema each endpoint declares, built once as a reusable generic
  factory (`SuccessEnvelope<A,I>(data: Schema.Schema<A,I>)` / `ErrorEnvelope<A,I>(error:
  Schema.Schema<A,I>)`) — this factory pattern is not an attested example in `ai-docs`, but it
  follows the same `Schema.Struct({...})` combinator style already used at `user_route.ts:13`
  (`Schema.Array(UserResponse)`), so it is consistent with the real API surface.
- **Query params:** `HttpApiEndpoint` takes them through a `query:` constructor option (not a
  `.setUrlParams()` method — that name exists only on the HTTP *client* side,
  `HttpClientRequest.setUrlParams`). `HttpApiEndpoint.get(id, path, { query })` —
  `HttpApiEndpoint.d.ts:615,643`; `Query extends Schema.Top | Schema.Struct.Fields`, each field
  constrained to encode to a string/array (comment at line 547). No endpoint in the repo declares
  `query` today.
- **Schema field reuse:** `Schema.Struct` exposes a real `fields` property
  (`Schema.d.ts:2963`), and the documented pattern is spreading it: `Schema.Struct({
  ...Base.fields, extra })` (doc example, lines 2950-2962). There is no standalone `Schema.extend`/
  `pick`/`omit` for plain structs (only `Base.extend` on class constructors,
  `Schema.d.ts:~11026`). `Struct.mapFields` (`Schema.d.ts:2980`) is the built-in derive helper.
  This is how `PaginationParams`'s fields get reused across future list endpoints — a shared field
  record spread into each endpoint's own `query: Schema.Struct({...PaginationFields, ...})`.
- **Numeric query decoding:** `Schema.NumberFromString` (`Schema.d.ts:7470,7491`) accepts
  `NaN`/`Infinity`; `Schema.FiniteFromString` (`Schema.d.ts:7499,7518`) rejects them — the better
  fit for `limit`. Neither is used anywhere in the repo yet.
- **`/api/health`** (`src/kernel/healthcheck.ts`) has its own established shape — `{"status":"ok"|
  "unhealthy", ...}` — documented in `rules.md:16` as the alexliesenfeld/health convention,
  consumed by the healthcheck CLI and (per the same line) orchestration probes. Its own `status`
  field means something different (`ok`/`unhealthy`, an up/down verdict) than the envelope's
  `status` (`success`/`error`, a request-outcome verdict). This collision is addressed in D8.

## Decisions

- **D1 (module registration): one file, `kernel/registry.ts`.** It imports every module's
  group(s), handlers factory, and service layer — today `HealthApi`/`healthHandlers` from
  `kernel/healthcheck.ts` and `UsersApi`/`usersHandlers`/`identityLayer` from
  `modules/identity/module.ts` — and exports `api` (the `.add(...)` chain, moved here from
  `kernel/http/api.ts`), `moduleServiceLayer` (`Layer.mergeAll(identityLayer)`, consumed by
  `kernel/layers.ts`), and `moduleHandlerLayer(api)` (`Layer.mergeAll(healthHandlers(api),
  usersHandlers(api))`, consumed by `kernel/http/api.ts`'s `apiRoutes`).
  Rejected: a generic `AppModule` descriptor iterated by `.map`/`.reduce` — the `HttpApi.add` tuple
  constraint rules out building the chain from a runtime array without a cast, and with one or two
  real modules the descriptor type has no second shape to generalize over yet. Revisit once three
  or more feature modules exist.
- **D2 (docs correction):** `rules.md:37-38` names `kernel/registry.ts` as the one shared file a
  new module touches (replacing the false "no shared file" claim); keeps the module's actual
  export name (`identityLayer`, not a generic `layer`); `rules.md:25` is corrected to name
  `<name>_route.ts` as the endpoint-schema location.
- **D3 (envelope layer): schema-level, per endpoint.** `kernel/http/envelope.ts` exports
  `Metadata` (the flattened `{status_code, request_id, trace_id?, rate_limit?, cache?, limit?,
  has_more?, next_cursor?}` — `ApiPagination`'s fields spread directly into `Metadata`, matching
  `api-response.md`'s "`...ApiPagination`" note), `Links`, `SuccessEnvelope<S extends
  Schema.Top>(data: S)`, and `ErrorEnvelope<S extends Schema.Top>(error: S, statusCode: number)`
  — bound to `Schema.Top`, not the initially-tried `Schema.Schema<A>`. The narrower bound only
  tracks the decoded type and erased the richer Codec shape HttpApi's own inference needs; with it,
  any endpoint using these factories silently collapsed the whole composed `ApplicationLayer`'s
  requirements to `unknown` instead of `never` everywhere it is consumed (`main.ts`, `cli.ts`,
  `tests/kernel/http.test.ts`) — no local error at the factory or the endpoint, only a cryptic
  "`unknown` is not assignable to `never`" several layers away. Found by bisecting the whole
  identity-module diff down to a single minimal endpoint declaration. Every endpoint's
  `success`/`error` declaration is the literal envelope — `success: SuccessEnvelope(UserResponse)`,
  not `success: UserResponse`.
  Rejected: a transport-level rewrite middleware (reuse `error-response.ts`'s body-rewrite pattern
  for every `/api/*` response) — cheaper to build, but leaves `openapi.json` documenting bare
  domain payloads instead of the real wire shape, which the owner ruled out.
  Rejected: hybrid (schema-wrap success only, middleware-rewrite error only) — same OpenAPI-accuracy
  gap on the error side, and two different mechanisms for one concern.
- **D4 (error classes): generic, reusable, HTTP-semantic — not one bespoke class per domain
  concept.** `kernel/http/errors.ts` defines `Schema.TaggedError` classes shaped exactly as
  `ApiErrorBody` (`code`, `retryable`, `details?`, `details` typed `Schema.Unknown`, `debug?`):
  `ApiNotFoundError`, `ApiConflictError`, `ApiServiceUnavailableError`, `ApiValidationError`,
  `ApiRateLimitedError`, `ApiInternalError`. A module constructs the generic class with its own
  `code` string (`USER_NOT_FOUND`, `EMAIL_CONFLICT`, …) and `details` payload instead of declaring
  a new tagged class per concept — avoids a proliferating class per entity per failure mode across
  every future module (auth, OAuth, OIDC included) while keeping each error a first-class declared
  schema (`HttpApiEndpoint`'s `error` set stays `ErrorEnvelope(ApiNotFoundError) |
  ErrorEnvelope(ApiConflictError) | ...`). Effect's built-in `HttpApiError.NotFound` etc. are
  dropped outright — no backward-compatibility shim, per the owner's early-stage instruction.
- **D5 (ambient request metadata): two `Context.Reference`s, not one shared struct tag.**
  Landed as `kernel/http/request-context.ts`'s `RequestId` and `RateLimitVerdict` —
  `Context.Reference`s with a default (`''` / `Option.none()`), one per concern, matching this
  codebase's existing one-tag-per-service granularity (`Database`, `AppConfig`, `UserService` are
  each their own tag) rather than one struct two middlewares would have to read-then-merge into.
  `request-id.ts` and `rate-limit.ts` each `Effect.provideService` their own reference alongside
  the header they already set. `kernel/http/respond.ts` exports `respondSuccess(data, {
  statusCode?, message?, links?, cache?, pagination? })` and `respondError(error, statusCode,
  { message?, cache?, pagination? })` — both read `RequestId`, `RateLimitVerdict`, and
  `Effect.currentSpan` (`span.traceId`, confirmed in `Tracer.d.ts`; absent outside an active span
  via `Effect.catch`, not a failure) and assemble the full `Metadata` object, including folding a
  `ConsumeVerdict`'s relative `resetSeconds` into `ApiRateLimit`'s absolute unix `reset` via
  `Clock.currentTimeMillis`. A handler calls `return yield* respondSuccess(user)` instead of
  returning the bare domain value; the endpoint's declared `SuccessEnvelope(UserResponse)` schema
  then encodes exactly what `respondSuccess` produced. Covered by
  `kernel/http/respond.test.ts` (4 cases, including the rate-limit fold under `TestClock`).
  Rejected: assembling metadata by hand inside every handler — duplicates the same
  request-id/trace-id/rate-limit/cache lookup in every handler, the exact drift pattern D3 of
  plan-20261026_1227 already rejected for the HTTP middleware stack.
- **D6 (pagination): one shared field record, applied first to `listUsers`.**
  `kernel/http/pagination.ts` exports `PaginationFields = { limit: optional(FiniteFromString
  piped to an integer 1-100 range), cursor: optional(String), sort_by: optional(String),
  sort_order: optional(Literal('asc','desc')) }` (field record, spread per `Schema.Struct({
  ...PaginationFields })` into each list endpoint's `query`, per the `Struct.fields`-spread pattern
  found in `Schema.d.ts`). `listUsers` gains `query: Schema.Struct(PaginationFields)` and its
  `SuccessEnvelope`'s `metadata` carries `limit`/`has_more`/`next_cursor`. Landed in phase 6: real
  keyset pagination over `{sortValue, id}` (the sort column plus `id` as a tiebreaker), one extra
  row fetched past `limit` to detect `hasMore` without a second query, and the cursor a base64url
  JSON token of that pair (`encodeCursor`/`decodeCursor` in `pagination.ts`). `listUsers` narrows
  the shared `sort_by` field to `'id' | 'created_at'` by spreading `PaginationFields` and
  overriding that one key.
- **D7 (CacheStatus spec): extend `api-response.md` to four values.** `cache?: 'hit' | 'miss' |
  'bypass' | 'disabled'` — matches `src/kernel/cache.ts:17-21` exactly; no mapping/translation
  code needed, no information lost.
- **D8 (health scope, tentative — confirm or override at phase 8): `/api/health` stays outside the
  envelope.** Its `{"status":"ok"|"unhealthy",...}` shape is a stable machine contract
  (`rules.md:16`) shared with the healthcheck CLI and orchestration probes, not a typical API
  client surface; wrapping it would collide the envelope's `status` (`success`/`error`) with
  health's own `status` (`ok`/`unhealthy`) and risks breaking infra tooling that reads the flat
  shape today. This is a judgment call, not a verified requirement — phase 8 only records the
  decision in docs; if the owner disagrees when phase 8 starts, the health schema is revisited
  then instead.
- **D9 (defects): `error-response.ts` reshapes into the same `ApiErrorBody`/envelope the declared
  errors use — one shape, not two.** Landed in phase 7 via a new `errorBody` export
  (`kernel/http/respond.ts`) — the plain-value counterpart to `respondError` for callers that
  return an `HttpServerResponse` directly instead of failing an HttpApi handler's effect. The flat
  `{"_tag":...}` bodies are deleted outright. `api.ts`'s `apiFallback` (the `/api/*` wildcard 404)
  got the same treatment — not named in the original decision, but the same "every `/api/*`
  response is one shape" requirement applied to it too.

## Execution rules

- **Execution waits for the owner's explicit "continue with phase N."** This plan does not execute
  on its own creation. Atomic, self-serve commits are authorized per phase during the working
  session; the agent does not commit the closing state on its own — it recommends the final
  message and path list when every phase lands.
- **No backward compatibility, no legacy shape kept.** Per the owner's instruction (early-stage
  project): the bare-array success body, the flat `{"_tag":...}` error body, and
  `HttpApiError.NotFound`/`Conflict`/`ServiceUnavailable` usage are removed outright in the same
  phases that introduce their replacements — not kept alongside them, not versioned.
  Consequently `GET /api/openapi.json` is **expected to change** in this plan (unlike
  plan-20261026_1227's byte-identical bar) — the final-validation check is that it matches the
  envelope/pagination shapes this plan documents, not that it is unchanged from before the plan.
- **Per-phase validation runs before each phase's commit.**
- **E2E runs only when relevant to the phase.** Phases 1-3 (registry) do not change wire behavior —
  E2E was not run for them. Phase 6 turned out to need it despite the e2e suite never asserting
  raw API JSON directly: the client-side data bridge (`user_fn.ts`, not an endpoint file — easy to
  miss when scoping "the identity module") calls `fetch('/api/users')` and expected the old bare
  body; the unit suite had no coverage of that bridge against a live envelope shape, so only e2e's
  browser-side hydration caught the "Uncaught Client Exception" this produced. Lesson for any
  future wire-contract change: enumerate every consumer of the changed endpoint, not just its
  route/handler — client-side fetch bridges are a consumer too.
- Phases 9 ("docs/ sync"), 10 (".llms/ sync"), 11 (final validation), and 12 (handover) are
  mandatory regardless of what phases 4-8 end up touching, per the owner's instruction.
