# Close the observability gaps — resource walls, request identity, probe split, dependency truth, telemetry-loss signal, and capacity headroom

## Objective

The dashboard pass of 2026-10-23 provisioned eight dashboards and recorded the remaining gaps in
issue-20261023_2135; this plan closes the six open findings (O1–O6) and leaves O7 parked behind its
own trigger. After execution: the request metrics separate routes and exact status codes, the
process answers a liveness probe beside the readiness probe, dependency calls carry spans and a
duration series, dashboards report telemetry freshness with alerts, ClickHouse projects days of
disk headroom, and the compose stack runs the app with a memory limit scraped through cAdvisor.
The plan does not change the retention window (O7) or replace the OTEL pipeline the stack already
runs.

## Current state (verified in the tree, 2026-10-24)

- **HTTP metric labels are class-only.** `src/observer/metrics.ts:15` — `statusClass` renders
  `4xx`; `src/observer/metrics.ts:35-42` — `recordRequest` labels `http_requests` with
  `{method, status}` and `http_request_duration_seconds` with `{method}`; the comment at lines
  33-34 states the bound was deliberate. `src/middleware/request-log.ts:19,25` passes
  `statusClass(...)` and records every request, including the `/metrics` scrape.
- **Only `application-sli.json` reads these metrics.** `container/clickstack/dashboards/` — the
  four `Attributes['status']` queries sit at `application-sli.json:38,56,92,147`; the histogram
  name appears 3 times in the same file; no other dashboard reads `http_requests` or
  `http_request_duration_seconds`.
- **`/health` is readiness only.** `src/modules/health/module.ts:9-22` — one `GET /health` over
  `Database.ping`, `503` on `DatabaseError`. No liveness route: grep for `live|liveness` over
  `src/` returns nothing; `.llms/rules.md` states the readiness-only contract.
- **Dependency calls carry no telemetry.** `src/database/adapter.ts` exposes `query`, `read`,
  `ping` as bare `Effect.tryPromise`; `src/kernel/cache.ts` wires peek/get/invalidate without any
  span or metric; `src/middleware/rate-limit.ts` consumes the store without any span. Grep for
  `withSpan|Tracer` over those files finds nothing. Redis is optional
  (`src/kernel/config/redis.ts:31` — `REDIS_ENABLE` defaults false), so a slow cache or limiter is
  configuration-shaped and invisible.
- **The compose stack has five services, none of them the app.** `compose.yaml` — `clickstack`,
  `clickstack-init`, `redis-exporter`, `redis`, `mailpit`; the collector's extra config
  (`container/clickstack/otel-collector.yaml`) scrapes only `redis-exporter:9121`. The deployment
  shape is the standalone distroless image run host-networked (`package.json` docker scripts).
- **The provisioner provisions connections, sources, and dashboards and never alerts.**
  `container/clickstack/provision.sh:152-217` — dashboard validate/apply/stale-sweep is the last
  step; grep for `alert` in the file finds nothing. `GET /api/v2/alerts` answers on the running
  stack (verified 2026-10-23, issue-20261023_2135 item O5); from this host only port 8080 is
  published (the v2 API answers 200 only inside the compose network — verified today: 404 via
  :8080, so alert validation runs through the provisioner or `docker compose exec`).
- **The server span per request already exists and already receives the route attribute.**
  `src/middleware/tracer.ts` mounts `HttpMiddleware.tracer` (server span, span-named by the
  `SpanNameGenerator` reference); `node_modules/effect/dist/http/HttpRouter.js:149-153` writes
  `http.route = route.path` onto that span when sampled — the trace side needs no new plumbing;
  this plan's label work is the metrics side.
- **Standing records this plan extends.** `.llms/handover/handover-20261023_0745.md` — "No
  backward compatibility is required anywhere in this tree" (the owner waived compat standing);
  `.llms/roadmap/parked-unlocks.md` carries nothing that overlaps this scope.

## Decisions

- **D1 (2026-10-24, owner): scope is O1–O6; O7 stays parked.** The issue's statuses already carry
  this: O7 is `considering` with a named trigger, and its retention policy is the owner's call,
  not a default to invent. The cost: the O6 projection tile may eventually surface headroom below
  the 30-day window with no knob to turn — at that point O7's trigger fires on its own, with the
  projection as evidence.
- **D2 (2026-10-24, owner): O1 is the full compose path — the app runs as a compose service with
  a memory limit, scraped through cAdvisor.** Verified environment: the stack is up and the deploy
  target (the Dockerfile image) is the same lens cAdvisor sees, so the full signal set (memory
  working set vs limit, CPU throttling, restart/uptime reset) is real, not projected. Cost: one
  more compose service and a privileged cAdvisor container in dev; cAdvisor's volume layout is
  environment-sensitive, so the phase validates the three series arrive, and the compose run is
  undo-revertable without touching the app image. Rejected: the uptime-drop tile only — restarts
  become visible but OOM/throttle/memlimit stay invisible; and the split "cheap tile now, cAdvisor
  later" — double tile work for signals one phase delivers.
- **D3 (2026-10-24, owner): the alert channel is a generic webhook behind
  `CLICKSTACK_ALERT_WEBHOOK_URL`; unset, the provisioner skips alerts.** The name joins the
  existing `CLICKSTACK_*` provisioner family (`CLICKSTACK_INGESTION_KEY`, `CLICKSTACK_ACCESS_KEY`).
  Cost: a dev stack without the env gets the freshness verdict tile but no alert objects —
  intentional, not a gap. Rejected: email via the compose Mailpit — verified the stack carries it,
  but the channel then binds to email in every env and needs SMTP reachability from the alert
  target; rejected deferring alerts entirely — O5's half-landing leaves the loss signal
  dashboard-only, which is the finding itself.
- **D4 (2026-10-24): request metrics carry `{method, status_code, route}`.** `status_code` is the
  exact numeric code as a string; `route` is the matched route template from a route-label module
  that derives its table from the HttpApi contract at build time (`HttpApi.make(...)` groups →
  endpoint `path` values, verified introspectable: `node_modules/effect/dist/http-api/HttpApi.js:23-31`,
  `HttpApiEndpoint.d.ts:118`) plus two routing literals: the SSR catch-all (`GET *`) labels as
  `page` and the Prometheus scrape labels as `metrics`; anything else is `unmatched`. The class
  label dies — the standing no-compat waiver applies, and the four SLI queries re-derive the class
  band in SQL. The set stays bounded: the route table plus three fixed values. Cost: the label
  module must track the contract — it derives *from* the contract, so drift is structurally
  impossible; the real cost is series cardinality rising from ~40 to ~40 × distinct codes ×
  distinct routes (still bounded, but the bounded-labels contract in `.llms/rules.md` must be
  updated in the same phase). Rejected: keeping the class and adding a separate `status_code`
  label — two status labels on one series is the drift the old comment warns about; rejected
  adding exact code only if route proves coarse — the SLI tile needs both the 429 rate and the
  per-route split in the same dashboard pass anyway.
- **D5 (2026-10-24): the liveness surface is `GET /api/live` inside the existing `HealthApi`
  group.** The group is mounted under the `/api` prefix, so the literal path is `/api/live`; it
  answers `200 { status: 'ok' }` without touching the database and is declared in the endpoint
  contract like any endpoint, so the OpenAPI document and the api-endpoint docs carry it in the
  same change. `/health` keeps its readiness semantics. `Application SLI`'s `Health probe` tile pattern
  gains `/live`. Cost: a supervisor probe pointed at `/api/live` exercises the same HTTP stack as
  readiness — if an out-of-band liveness ever needed a bare path, that would be a separate
  surface; rejected `GET /live` at the root: it would need a router route outside the HttpApi
  contract, a second composition point for the same feature.
- **D6 (2026-10-24): dependency telemetry is one histogram plus bounded spans.**
  `dependency_duration_seconds { store, op }` with `store ∈ {sqlite, redis}` and `op` a bounded
  enum from the call sites (`query`, `read`, `ping`, `cache-get`, `cache-invalidate`,
  `rate-limit-consume`); each call site gets a span (`database.query`, `database.ping`,
  `cache.get`, `rate-limit.consume`, ...) carrying only bounded attributes — `store`, the
  verdict (`allowed|rejected|unavailable` for the limiter), the cache outcome
  (`hit|miss|bypass|disabled` — the `CacheStatus` union already exists). No key, no query string,
  no table name outside the fixed set — a table name in an attribute would grow the series by
  every new table. Cost: the `hit|miss` split for the cache rides the span only, not the metric
  label — adding a third label for the outcome is deliberately avoided; if a tile ever needs the
  hit rate label-side, that is a follow-up decision, not a silent addition.
- **D7 (2026-10-24): the capacity projection is a read-only SQL tile inside
  `clickhouse-database.json`, and the freshness verdict replaces the raw-timestamp tile in
  `application-sli.json`.** Projection: bytes-written rate over the selected range divided by
  free disk space, rendered as days of headroom, sources `system.query_log` and `system.disks`
  (the issue verified both are readable from the dashboard's connection). Freshness: newest
  `Timestamp` per signal table vs the tile clock, rendered fresh / stale / silent — thresholds
  are decisions made here, not defaults invented at the tile: `fresh` ≤ 2 min, `stale` > 2 min,
  `silent` > 10 min; the OTLP export interval is 5 s
  (`src/kernel/config/observability.ts:16`), so two minutes is a wide margin. The old
  `Silent signal check` timestamp tile is removed — early stage, no compat. Alert thresholds:
  no spans for 10 minutes; collector refused or failed counters above zero over a 5-minute
  window. The exact alerts-api payload shape is verified against the running v2 API inside
  phase 5 before the JSON files are written; if the API cannot express a condition, the fallback
  the phase reports is skipping that alert, not inventing a channel (D3 already made a silent
  channel impossible — the freshness tile answers "is anything arriving" without one).

## Execution rules

- **Execution waits for the owner's explicit go-ahead per phase** ("continue with the next phase"); the plan starts only on that instruction.
- **Atomic commit per phase** with the plan-named message; **self-serve commits are allowed during this plan's working session** — a phase may commit its own validation fixes before the phase commit lands.
- **Per-phase validation runs before each phase's commit.** A phase that cannot validate does not commit; it reports the blocker and stops.
- **Phases 4–6 validate against the running stack.** The stack is compose-managed (`docker compose up --detach`); phases do not build, migrate, or reset anything the stack owns; the compose shape grows only in phase 6's service additions.
- **No backward compatibility and no legacy shims** — the owner's standing waiver (handover-20261023_0745), re-granted for this plan: the class status label is retired outright, dashboards are edited in place, and the old `Silent signal check` tile is removed when its replacement lands.
- **O7 stays parked.** The retention window is untouched; if a phase observes the projection crossing the 30-day window, that is a report to the owner, not a change.
- **The riskiest phase names its undo.** Phase 6 (compose restructure) backs out as a single revert of that phase's commit — no data or telemetry state lives in the compose change itself; the `.storage/` volumes the stack already mounts are untouched by it.
- **After the last phase, the agent stops and recommends the closing commit message with its paths** — it does not commit the closing state unasked.
- **E2E is written only when relevant** and recorded n/a with the reason otherwise — see the matrix row and phase 8.

- **Alerts without a configured webhook** — the gate stays; no default silent channel is invented.

- **A bespoke dashboard for the app** — everything lands inside the eight provisioned dashboards; the dashboard set is provisioned and named, and a ninth file is a separate decision.
