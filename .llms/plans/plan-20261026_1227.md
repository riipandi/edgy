# Self-contained module DI — thin composition root for the identity module

## Objective

The owner judged the current dependency-injection and module-registration mechanism not
pragmatic or scalable (2026-10-26, chat). Effect v4 research (module dts + website links in
`.llms/effect-docs.md`) confirms the repository already uses the idiomatic service pattern
(`Context.Service` + `Layer.effect` + ambient context in handlers); what does not scale is the
wiring: a hand-maintained central registry, a kernel that imports a feature module's runtime
singleton, and a middleware merge duplicated across two compositions. After this plan lands,
each module exports its own service layer, API group, and handlers layer; `kernel/registry.ts`
is gone; the `ManagedRuntime` and the HTTP middleware stack are owned by the kernel. The plan
does not touch service contracts, endpoint schemas, or any wire behavior.

## Current state (verified in the tree, 2026-10-26)

- **Central hand wiring per module** — `src/kernel/registry.ts:5-8` merges `UserRepositoryLayer`
  and `UserCache.layer` into `userDeps`, then builds `applicationServices` from
  `UserServiceLayer.pipe(Layer.provide(userDeps))`. Every new module edits this file.
- **Kernel imports a feature module's runtime** — `src/kernel/http/api.ts:22` imports
  `applicationContext` and `disposeUserRuntime` from `#/modules/identity/user/user_ssr.ts`;
  `api.ts:75` awaits the context; `api.ts:107` disposes the runtime in the handler's `dispose`.
- **Runtime singleton at module import** — `src/modules/identity/user/user_ssr.ts:23` builds
  `ManagedRuntime.make(ApplicationLayer.pipe(Layer.provideMerge(CoreLayer)))` at module load;
  `user_ssr.ts:17-22` stores a `AsyncLocalStorage` in `globalThis` so separate server bundles
  share the request-scoped `UserService`.
- **Duplicated middleware composition** — `src/kernel/http/api.ts:86-98` and
  `src/kernel/http/serve.ts:26-36` each hand-merge the same middleware list (trust-proxy, tracer,
  cors, request-id, error-response, request-log, security-headers); serve adds the dispose
  finalizer (`serve.ts:36`), dev adds `Layer.succeedContext` (`api.ts:97-98`). Drift between the
  two lists is silent.
- **Handler pattern is already idiomatic** — `src/modules/identity/user/user_handler.ts:14`
  resolves services from ambient context (`Effect.flatMap(UserService, ...)`), and the group
  layer is provided into `HttpApiBuilder.layer` at `api.ts:57-60`. This pattern stays.
- **Effect v4 contract backing the target shape** — `HttpApiBuilder.layer` requires one
  `HttpApiGroup.Service` per group (`node_modules/effect/dist/http-api/HttpApiBuilder.d.ts:27-43`);
  `HttpApiBuilder.group` returns exactly that layer. `Layer.memoization` guarantees one instance
  per service across the merged graph, so self-wired module layers cannot duplicate singletons.
  v4 has no `HttpApiBuilder.api` (the v3 name) — the top-level entry is `layer`.
- **Module relocation already landed** — the module tree is `src/modules/identity/` with
  `module.ts` and `user/` (moved 2026-10-26, chat session; imports updated in kernel, routes,
  seeders, and `tests/fixtures/users.ts`).

## Decisions

- **D1 (2026-10-26): modules are self-contained; the composition root is thin.** Each feature
  module exports three things from its index — `layer` (the self-wired service graph),
  `group` (the `HttpApiGroup`), and `handlersLayer` (the `HttpApiBuilder.group` layer whose `R`
  is exactly the module's own services). `modules/identity/module.ts` merges the per-feature
  layers and re-exports the group; the kernel imports only module indexes. The cost: modules
  type-import `typeof api` from the kernel to build their handler layers (type-only, no runtime
  cycle — the same import `user_handler.ts:6` already makes).
  Rejected: declarative central registry (modules export a definition object that registry/api
  iterate) — one consumer today; the iteration machinery buys nothing over `Layer.mergeAll` and
  hides the graph behind indirection.
  Rejected: keep the manual registry — the per-module kernel edit is the complaint this plan
  answers.
- **D2 (2026-10-26): the `ManagedRuntime` and its disposal are kernel-owned.** A new
  `kernel/runtime.ts` builds the runtime from `ApplicationLayer + CoreLayer` and exposes
  `applicationContext` / `dispose`; `user_ssr.ts` keeps only the SSR bridge helpers
  (`withUserService`, the `AsyncLocalStorage` store, the `*FromService` functions) and receives
  the context instead of owning the runtime. The ALS `globalThis` store stays — Solid's
  production renderer cannot carry an Effect context into render, so the async-local bridge is
  the mechanism, moved to the right owner.
  Rejected: deleting the ALS in favor of context-only access — breaks the production SSR
  renderer (`architecture.md` "Runtime composition" records why the bridge exists).
- **D3 (2026-10-26): one shared HTTP stack.** `kernel/http/stack.ts` composes the middleware
  layers once; `serve.ts` adds the SSR router and the dispose finalizer on top, the dev handler
  in `api.ts` adds `Layer.succeedContext`. The dev/serve differences stay explicit at the edges,
  the shared middle stops drifting.
  Rejected: leaving both merges as they are — the duplication is the drift vector.

## Target shape

Directory tree after every phase lands (new files marked `+`, removed `-`, moved `→`):

```text
src/
  kernel/
    config/
      config.ts
    http/
      api.ts               (delta: imports runtime + module indexes from kernel only)
    + stack.ts             (D3 — shared middleware stack for serve and dev)
      serve.ts             (delta: consumes stack.ts; delta drops module runtime import)
      renderer.ts
      graceful.ts
    + runtime.ts           (D2 — owns ManagedRuntime, applicationContext, dispose)
      layers.ts            (delta: composes CoreLayer + database + module layers; registry import gone)
    - registry.ts          (deleted — wiring moves into the module)
      cache.ts  healthcheck.ts  redis-boot.ts  renderer.ts
  modules/
    identity/
      module.ts            (delta: exports layer + group + handlersLayer — the module contract)
      user/
    +   user_layer.ts      (D1 — UserServiceLayer self-wired: repo + cache provided inside)
        user_route.ts  user_handler.ts  user_service.ts  user_repo.ts
        user_schema.ts  user_fn.ts  user_ssr.ts  *.test.ts
```

The dependency graph — arrows read "depends on"; every module boundary crosses into the kernel
exactly once, through the module index:

```text
                       composition roots (kernel-owned)
  ┌──────────────────────────────┬───────────────────────────────────┐
  │  serve.ts (production)       │  api.ts apiHandler (vite dev)     │
  │  stack.ts + ssrRouter        │  stack.ts + succeedContext        │
  └──────────────┬───────────────┴───────────────┬───────────────────┘
                 │                               │
                 └───────────┬───────────────────┘
                             ▼
                     apiRoutes (HttpApiBuilder.layer)
                 provides: health handlers · identity handlersLayer
                             ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ ApplicationLayer = CoreLayer ⊕ DatabaseLayer ⊕ module layers │
   └───────┬──────────────────────┬──────────────────┬───────────┘
           ▼                      ▼                  ▼
     CoreLayer               DatabaseLayer     identity/module.ts
   (platform, config,       (connection,        layer ← user_layer.ts
    logger, telemetry)       migrations)          group ← user_route.ts
                                                  handlersLayer ← user_handler.ts
                             ▼
                     kernel/runtime.ts
        (ManagedRuntime over ApplicationLayer; ALS SSR bridge consumed
         by user_ssr.ts — the module never owns the runtime again)
```

Runtime flow through one request: the composition root builds the context once
(`kernel/runtime.ts`), the HTTP stack carries it into every handler fiber, handlers read
services from ambient context, and the SSR bridge (`user_ssr.ts`) hands the same
`UserService` to the Solid renderer through async-local storage.

## Execution rules

- **Atomic commit per phase** is authorized; each phase's heading names its suggested commit
  message; self-serve commits are allowed during this plan's working session.
- **Execution waits for the owner's explicit "continue with phase N".** When the phases have all
  landed, the agent stops and recommends the closing commit message with its paths — it does not
  commit the closing state on its own.
- No migration, no seed change, no wire-contract change: every phase must keep the endpoint
  paths, statuses, and error sets byte-identical (the route prefix from 2026-10-26 is already
  `.prefix('/users')`).
- **Per-phase validation runs before each phase's commit.**
- **E2E is relevant** — the SSR and API surfaces are touched; the e2e suite runs in the final
  validation.
- The riskiest phase is 2 (runtime ownership moves across the import graph); its undo is the
  phase's atomic revert — no cross-phase entanglement is created before it lands.

## Explicitly out of scope

- **New modules or endpoints** — the contract is defined so the next module follows it; none is
  built here.
- **The `AsyncLocalStorage` bridge redesign** — D2 moves its ownership, not its mechanism; a
  context-native replacement is reconsidered only if the Solid renderer gains a way to carry
  Effect context (parked, no trigger date).
- **F-06 (unauthenticated user emails)** — parked per the roadmap; untouched by this plan.
- **Rate-limit or middleware behavior changes** — D3 reorganizes composition only; no middleware
  gains or loses a path.
