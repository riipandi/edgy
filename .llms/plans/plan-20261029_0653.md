# Plan — audit-20261029_0650 fix round

## Objective

Resolve every finding from the second deep audit (`.llms/audit/audit-20261029_0650.md`): make the rate limiter's 429/503 responses conform to the API envelope contract, remove the dead error class by adopting it, normalize the rate-limit key fallback, gate the cache-bypass query param to non-production, and fix the dev-only renderer `distRoot` probe (I-1).

## Current state (verified)

- `src/kernel/http/stack.ts:20-26` — middleware order is `requestTracer → cors → routes → requestId → errorResponse → requestLog → securityHeaders`; the rate limiter answers inside routes, before `requestIdMiddleware` runs.
- `src/middleware/rate-limit.ts:296` — 503 store-failure body is `jsonUnsafe({ _tag: 'ServiceUnavailable' })` (flat, forbidden by the envelope contract).
- `src/middleware/rate-limit.ts:303-304` — 429 body is plain text `Too Many Requests`.
- `src/middleware/rate-limit.ts:288-290` — key = `remoteAddress ?? request.headers['x-forwarded-for']` (whole header string as fallback).
- `src/kernel/http/envelope.ts:7-48` — `ApiRateLimit`, `Metadata`, `ErrorEnvelope` schemas define the contract; `metadata.request_id` and optional `rate_limit` are the fields the 429 must carry.
- `src/middleware/request-id.ts:25-32` — `requestIdMiddleware` provides the request id through `RequestIdContext` (`#/kernel/http/request-context.ts`); consumers read it from that service.
- `src/kernel/http/errors.ts` — `ApiRateLimitedError` defined, zero usages outside the file (grep-verified); `ApiConflictError`/`ApiServiceUnavailableError` are used by `user_route.ts`/`user_handler.ts`.

- `tests/middleware/rate-limit.test.ts:60,188` — existing tests assert the plain-text 429 body; they must be updated with the envelope change.
- Baseline: 327/327 tests, typecheck 0 errors, `pnpm audit --prod` clean.

## Decisions

1. **2026-10-29 — F1 fix direction: build the 429/503 envelopes locally in the rate limiter** (owner picked the structural reorder first, then confirmed the delta after the probe). The initial pick — reordering `requestIdMiddleware` ahead of the routes — rested on the premise that the limiter sees an empty request id; the production probe disproved it (the 429 carries `x-request-id`, stamped by the `requestIdMiddleware` wrapper that sits outside the limiter, so `yield* RequestId` inside the limiter already resolves the real id). The fix is therefore local: build both bodies with `errorBody` from `#/kernel/http/respond.ts`, which reads `RequestId` and `RateLimitVerdict` from context. Consequence: no middleware-order change, minimal blast radius. Rejected: the reorder — no longer functionally needed and it would re-expose every middleware interaction to verification.
2. **2026-10-29 — F2: adopt `ApiRateLimitedError` as the 429 envelope error** rather than deleting it. It is the natural carrier for the conforming 429 body (code `RATE_LIMITED`, `retryable: true`, `details.retry_after`). Rejected: deleting it — the contract's `ApiErrorBody` code list names `RATE_LIMITED`, so the class earns its place once used.
3. **2026-10-29 — F3: normalize the XFF fallback to the rightmost untrusted entry**, reusing the rule `trust-proxy.ts` already implements. Rejected: dropping the header fallback — tests and header-stripping proxies rely on some key being derivable.
4. **2026-10-29 — F4: gate `?nocache=1` to non-production** (owner accepted this framing in the scope decision). In production the param is ignored; dev/test keep the bypass for debugging. Rejected: documenting it as a supported feature — an unauthenticated per-request cache bypass is not a product feature; rejected: removing outright — it is useful in development.
5. **2026-10-29 — I-1: fix the `distRoot` probe to resolve the server bundle correctly in the source dev layout** (dev-only 500; production unaffected). The probe must find the dev server bundle where the dev build actually puts it, or fall back to a clear error instead of a nonexistent path. Exact resolution target is confirmed against the dev build output at implementation time.
