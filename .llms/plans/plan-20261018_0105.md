# Replace Marko with SolidJS 2 and add the /rpc surface — cleanup first, no compatibility

> Plan rewritten 2026-10-18 (v2, supersedes the phase order drafted the same day: Marko
> cleanup now precedes the Solid build; data reaches pages over `/rpc`, not `load` → props).

## Objective

The pages layer moves from Marko 6 templates to SolidJS 2 components rendered by the existing
h3 + Effect handlers, and page data moves to an RPC surface: Effect v4's built-in `effect/rpc`
mounted at `/rpc` (internal, consumed by the Solid pages), while `/api` keeps serving external
integrations with today's envelope. Marko leaves the tree first — dependencies, builder wiring,
type-check pass, test project, templates — then Solid is built in its place. Early-stage tree:
no compatibility layer, replaced code deleted in the phase that replaces it.

## Current state (verified in the tree, 2026-10-18)

- **Pages are three `.marko` files** — `web/pages/home/page.marko`, `web/pages/users/page.marko`,
  `web/pages/error/page.marko`, one layout tag `web/tags/app-shell.marko`, one nested tag
  `web/pages/users/tags/user-list.marko` (the only interactive component: a client-side filter).
- **The kernel renders through one seam.** `src/kernel/http/page.ts` declares a page as `load`
  (an `Effect<A, AppError, HttpEnv>`) plus `template: () => Promise<{ default: HtmlTemplate<A> }>`;
  `src/kernel/http/html_response.ts` renders via `template.render({ ...input, $global })` into a
  streamed `Response`. The error page plugs into the same seam (`src/app.ts:41`,
  `src/kernel/http/error_page.ts:25`). CSP is nonce-driven because Marko's one inline script per
  page needs it (`html_response.ts`, policy `script-src 'self' 'nonce-…'`).
- **Marko is wired in the builder in three places** — `builder/edgy.ts:52` (`marko()` plugin),
  `builder/node.ts:13-14` (Marko reads the server build to find page browser entries and patches
  the manifest), `builder/worker.ts:9-10` ("Marko's order" for `buildApp`) + `dropServerStyles`,
  and `builder/output.ts:27-29` (executable bit timed to Marko's patching). `vitest.config.ts`
  loads `marko()` too (project `marko`, jsdom, `resolve.conditions: ['browser']`,
  `tests/components_setup.ts`); `pnpm typecheck` = `tsc -b --noEmit && mtc`
  (`@marko/type-check`); `web/marko.d.ts` declares the module shape.
- **`/api` is the only HTTP surface today.** `src/kernel/http/handler.ts` (defineHandler family),
  envelope + OpenAPI via `responder.ts`/`runProgram` (timeout, tracing, cancellation,
  `X-Cache`, request-id). Runtime services snapshot in `HttpRuntime` (`runtime.ts:28-49`).
- **Effect v4 ships the rpc module** — `node_modules/effect/src/rpc/` (verified exports
  `./rpc`); server mount `RpcServer.toHttpEffect(group)` returns an
  `Effect<HttpServerResponse, never, Scope | HttpServerRequest>`; serializations
  `RpcSerialization.layerNdjson | jsonRpc | schemaBinary`; client `RpcClient.make` +
  `RpcClient.layerProtocolHttp({ url })`. The npm package `@effect/rpc` is Effect v3 only —
  not installed. Verified usage pattern: `vendor/effect/packages/effect/test/rpc/RpcServer.test.ts`
  (toHttpEffect + `HttpEffect.toWebHandler` over a plain web `Request`).
- **Solid packages are already installed** (from the superseded first attempt, kept):
  `solid-js@2.0.0-rc.15`, `@solidjs/web@2.0.0-rc.15`, dev deps `@solidjs/vite-plugin@3.0.0-next.50`
  + `@solidjs/testing-library@0.8.10`; `pnpm peers check` clean. Not yet imported anywhere in
  `src/` or `web/`.
- **The roadmap parks Marko features** (`.llms/roadmap/roadmap-20261016_0809.md`: streaming,
  lazy-loading, patch protocol) — obsolete once Marko leaves.
- **The working tree holds one uncommitted change**: package.json/pnpm-lock (the Solid deps
  above). The superseded union adapter and its test were reverted before this plan landed.

## Decisions

- **D1 (2026-10-18): cleanup Marko first, then build Solid fresh.** The owner's call: the tree
  is early stage and the pages are minimal, so a two-renderer union in the kernel buys nothing —
  phase 1 deletes Marko end to end, phase 2-3 build Solid in its place. Between phase 1 and 3
  the pages are down (dev server serves `/` as a JSON-404 page handler absence is resolved in
  phase 3); the E2E suite runs first at phase 5. The cost: no green page-level e2e until
  phase 5 — accepted for this tree.
  Rejected: dual-renderer coexistence (v1 of this plan) — dead code kept alive for a window the
  owner does not need.
- **D2 (2026-10-18): page data comes over `/rpc` (Effect v4 `effect/rpc`), not `load` → props.**
  `definePageHandler`'s `load`/`template`-input contract dissolves: a page handler renders its
  Solid component with no server-passed data object. Pages call typed RPC procedures
  (`Rpc.make(tag, { payload, success, error })` over Effect Schema) served at `/rpc`.
  Consequences: the first HTML paint is a shell (data arrives after hydration — no server data
  in markup); error rendering for `/rpc` is its own policy, not the `/api` envelope. The cost:
  no server-rendered data content on first paint — accepted by the owner (RPC is the stated
  direction).
  Rejected: Solid's `"use server"` functions — a second serialization and its `/_server`
  endpoint; the Effect rpc module already in the pinned dependency does the same job with typed
  errors the repo already models.
  Rejected: keeping `load` for first-paint data — contradicts the owner's explicit direction.
- **D3 (2026-10-18): `/rpc` is internal surface; `/api` remains the external contract.**
  The rpc endpoint mounts as an h3 handler (`POST /rpc`, ndjson codec), runs through the same
  `HttpRuntime` snapshot (services, timeout, cancellation) as `/api` handlers, and is excluded
  from the `/api`-targeting middleware that does not apply (CORS posture and the response
  envelope — the codec owns the message shape). OpenAPI does not describe `/rpc`. The cost: two
  surfaces to keep distinct in docs and tests — enforced in phase 4's matrix rows.
  Rejected: mounting rpc under `/api` — would entangle the envelope/CORS/OpenAPI contracts that
  external integrations rely on.
- **D4 (2026-10-18): SolidJS 2 RC (`solid-js@2.0.0-rc.15`) with `@solidjs/vite-plugin` next.50.**
  The owner accepts the RC status. The plugin pair (vite plugin 3.x line is the v2-compatible
  one) is verified installed with clean peers. Hydration is whole-tree — no Marko-style selective
  islands; accepted for these small pages.
  Rejected: solid-js 1.9 — the v2 RC is the target the docs the owner studied describe; the
  version lifts to stable when 2.0 releases (out-of-scope watch item).
- **D5 (2026-10-18): the CSP nonce mechanism dies with Marko.** Solid hydrates from an external
  module script; the policy becomes `script-src 'self'` (no nonce, no inline script), and
  `cache-control: private, no-cache` loses its per-response reason — relaxed in phase 3 unless
  another reason surfaces. The un-nonced-inline-script E2E block test stays (the policy still
  blocks it).
- **D6 (2026-10-18): `app-shell` becomes the Solid document layout** owning `<html>`, the head
  and `HydrationScript`; the error page keeps a minimal standalone layout. Pages compose
  `app-shell`; no `onHead` machinery at three pages.
- **D7 (2026-10-18): hydration entries are explicit.** Marko's manifest patching
  (`builder/node.ts:13-14`) is not reproduced: each page with interactivity declares a
  `client.tsx` (`hydrate(...)`) listed in the browser build's `rollupOptions.input`; the page
  links its built asset. Enforced by the users E2E (missing entry → dead filter).

## Execution rules

- **Atomic commit per phase** is authorized; each phase's heading names its suggested commit
  message; self-serve commits are allowed during this plan's working session. After the last
  phase, stop and recommend the closing commit message — never commit it unasked.
- **Execution waits for the owner's explicit "continue with phase N".**
- **No backward compatibility, no legacy shims** — the owner's standing grant: replaced code is
  deleted in the phase that lands its replacement.
- **Per-phase validation runs before each phase's commit.** A phase whose validation fails is
  fixed before its commit, not committed broken.
- **E2E only when relevant** — phase 5 runs the Playwright suite; other phases record n/a with
  the reason.
- **The riskiest phase names its undo.** Phase 1 (Marko removal) is the keystone while pages are
  down: its undo is reverting the phase's commit (Marko packages return with the lockfile).
- **The Solid dependencies already installed** (verified above) are this plan's starting state —
  the phase-1 commit does not touch them.

## Explicitly out of scope

- **Migrating `/api` onto effect/rpc** — `/api` keeps its envelope + OpenAPI contract for
  external integrations (D3); an rpc-based `/api` is a separate future plan if ever wanted.
- **Solid `"use server"` functions** — the Effect rpc module is the transport (D2).
- **Solid Start / router ownership** — routing stays h3.
- **Streaming data / `live()` equivalents over `/rpc`** — pages read request/response today;
  Effect rpc streams exist if a page later needs them, no phase builds one now.
- **Styling changes** — Panda CSS stays exactly as configured; class names move verbatim.
- **Server-rendered first-paint data** — shell-first is accepted (D2); revisiting means
  reopening D2, not adding a parallel loader.
- **A `solid-js` stable-bump plan** — when 2.0 leaves RC, a roadmap entry tracks the lift.
