# Make the standalone container serve pages and harden the boot path — the fixes from audit-20261024_0636

## Objective

Execute the fix plan of the whole-system audit (`.llms/audit/audit-20261024_0636.md`): the
standalone container must render every page (F-01), the build must fail loudly when an external
import leaks into the standalone output again (F-02), a Redis outage at boot must degrade or wait
instead of killing serve (F-03), the runtime metrics sampler must run only when metrics are on
(F-04), and `APP_BASE_URL` validation must match its documented contract (F-05). After execution the
rebuilt container answers 200 on pages and API alike, and the audit's findings are flipped with
evidence. F-06 (unauthenticated user list) is deliberately not fixed here — it is parked with a
named trigger in the ledger phase. The plan does not add features, change any API contract, or
touch the observability provisioning surface.

## Current state (verified in the tree, 2026-10-24)

- **The standalone SSR bundle externalizes the Solid web runtime.** `dist/server/server.js:1` opens
  with `import{...}from"@solidjs/web"` and a second import from `@solidjs/web/server-functions`; the
  fresh distroless container (rebuilt from `c008135d1` during the audit) answers `500` on every SSR
  page with `Cannot find package '@solidjs/web' imported from /app/server/server.js` while
  `/api/users` answers `200`. The standalone branch in `src/builder/vite-plugin.ts` sets
  `resolve.noExternal: true` only inside `environments.effect` (the `entry.js` environment); the
  SSR bundle is emitted by the SolidStart plugin's own SSR environment, which keeps Vite's default
  SSR externalization. Present since `afaf0f3ec` (2026-10-18) introduced the standalone split.
- **Nothing in the local validation path can see it.** The e2e webServer runs
  `node dist/entry.js serve` from the repo root (`playwright.config.ts`), where `node_modules`
  resolves the external import; the audit's container probes had only ever hit API endpoints. The
  audit ran e2e against the container and got 24/28 failures, all from the 500s.
- **Redis unavailability kills serve at boot.** `src/kernel/cache.ts:112` wraps
  `Persistence.layerRedis`'s build in `Effect.orDie`, and `src/middleware/rate-limit.ts:120` wraps
  `RateLimitCounterLayerRedis` in `Layer.orDie`; `compose.yaml:172` sets `REDIS_ENABLE: 'true'` on
  the app while `compose.yaml:117` declares `depends_on: redis: { condition: service_started }` and
  the redis service defines a healthcheck nothing waits for. Reproduced on the standalone binary:
  `REDIS_ENABLE=true` against a dead Redis port exits before listening (`RedisError ECONNREFUSED`).
- **The runtime metrics sampler runs unconditionally.** `src/kernel/layers.ts:11` merges
  `RuntimeMetricsLayer` into `CoreLayer` with no config gate; the Prometheus HTTP layer in
  `kernel/http/serve.ts` is gated on `config.observability.metricsEnabled`, the sampler is not.
- **`parseBaseUrl` accepts the empty string.** `src/kernel/config/app.ts:13` returns
  `Effect.succeed('')` for an empty `APP_BASE_URL` although the doc comment says the value "must be
  an absolute http(s) URL". Harmless today (the platform hands the server absolute request URLs, so
  the consumers never need the base — verified live: all probes 200 with the empty value), but the
  contract and the implementation disagree.
- **The Dockerfile carries a duplicate env line.** `Dockerfile:69-70` sets `NODE_OPTIONS` and then
  immediately re-sets it to the same value in the next line.
- **The finding record** is `.llms/audit/audit-20261024_0636.md` (F-01…F-06, all verified, status
  `in_review`); F-06's parking decision and the carried `wont_fix` items live in that report.

## Decisions

- **D1 (2026-10-24): standalone inlining covers the SSR environment, mirroring the `effect`
  environment.** The fix adds the same `resolve.noExternal: true` (with the standalone
  `resolve.conditions`) to the environment that emits `server/server.js`, so the Solid web runtime
  is bundled into the SSR artifact exactly as every other dependency already is. The first step of
  phase 1 confirms the emitting environment with a build probe (the `effect` environment proves the
  mechanism works for `entry.js`). The cost the pick carries: a larger `server/server.js` (the Solid
  runtime inlines) — acceptable, the standalone mode already inlines everything else.
  Rejected: vendor `node_modules` into the distroless image — defeats the point of the standalone
  build and grows the image by the whole dependency tree.
  Rejected: runtime fallback to a CDN or dynamic import — adds a network dependency to page render
  and contradicts the no-legacy/no-shim stance.
- **D2 (2026-10-24): the leak guard is a build-time assertion inside the vite plugin, not a docs
  checklist.** In standalone mode, after the bundles emit, the plugin scans `server/server.js`,
  `entry.js`, and `dist/chunks/*.js` for static imports of bare package specifiers (anything not
  relative, not absolute, not `node:`) and fails the build naming the package and file. This turns
  F-01's class of defect into a red build instead of a silent 500. The cost: the scan is regex-based
  over emitted output — a false positive would fail an honest build, so the scan only inspects
  static `from "<bare>"` statements and excludes `node:` and relative specifiers.
  Rejected: a docs-only "remember to probe /" rule — the audit showed process notes do not hold.
  Rejected: running the container in e2e as the only guard — slower, and it cannot fail a build that
  never reaches CI.
- **D3 (2026-10-24): the Redis boot waits, then the stack gate closes the cold-start race.** The
  Redis layer builds (cache store and rate-limit store) get a bounded retry with backoff around the
  connection before the existing `orDie` — the app waits for Redis for a bounded window instead of
  dying on the first refused connection; `compose.yaml` moves the app's `depends_on` for redis to
  `condition: service_healthy` so the common cold start never races at all. Runtime read failures
  keep degrading exactly as today; the fail-closed 503 limiter semantics are untouched. The cost:
  a misconfigured Redis URL delays boot by the retry window (bounded, seconds — not a hang).
  Rejected: lazy/degraded boot (start unlimited, fail closed on first use) — the largest change to
  the layer graph, and it silently switches the rate limiter to fail-closed-forever when Redis never
  comes up.
  Rejected: compose-only healthiness gate — fixes the cold start but leaves a mid-run Redis outage
  followed by an app restart as a crash loop.
- **D4 (2026-10-24): `RuntimeMetricsLayer` joins the same gate as its consumer.** The layer is
  provided only when `config.observability.metricsEnabled` is true, exactly like
  `PrometheusMetrics.layerHttp` in the serve composition. Rejected: keep sampling unconditionally
  "for readiness" — nothing consumes the gauges when the endpoint is off.
- **D5 (2026-10-24): `parseBaseUrl` rejects the empty string.** The documented contract wins over
  the accidental tolerance; an empty `APP_BASE_URL` becomes a boot-time config error naming the
  variable. Rejected: keep accepting empty and document it — every consumer already requires a
  usable base, so the acceptance is dead tolerance, not a feature.
- **D6 (2026-10-24): F-06 is parked, not fixed.** The unauthenticated user list publishes emails
  today for seed data only; the audit's trigger (the first authenticated endpoint or real user data)
  is recorded in the roadmap so the reopening condition is explicit. Rejected: drop the email field
  now — it would change the scaffold API's contract without a driver.

   delayed-start Redis, serve waits and comes up; `vpr test src/middleware tests/middleware`;
   compose config renders (`docker compose config`). _Commit:
   `fix(boot): wait for redis instead of dying when it is unreachable`._

5. **Reject an empty APP_BASE_URL** — `parseBaseUrl` fails with the variable's config error on the
